# 技术核对与勘误

本文件记录需要外部权威资料核验的原文陈述、核验来源及译文处理。

## 已确认

- `ch01.html` P039：原文先比较 H100（约 900 GB/s）与 H800（约 400 GB/s）的 NVLink GPU 间互连带宽，随后却紧接 H100 的 3.35 TB/s HBM 显存带宽，称 H800 的吞吐受限会使数据传输慢得多，混淆了两条不同数据通路。
  - NVIDIA，《NVIDIA H100 Tensor Core GPU》产品规格资料：将 GPU memory bandwidth 与 NVLink bandwidth 分列为不同指标。当前可获取的 H100 NVL 资料列出 3,938 GB/s 峰值 HBM3 带宽；不同 H100 形态的具体 HBM 数字会不同。
  - DeepSeek-AI，《DeepSeek-V3 Technical Report》，arXiv:2412.19437v2，第 3.1 节：训练集群由 2,048 块 H800 组成，节点内采用 NVLink/NVSwitch，节点间采用 InfiniBand；报告强调充分利用 IB 与 NVLink 带宽的通信内核。
  - 处理：译文保留原文的 900/400 GB/s 与 3.35 TB/s 数字，但明确前者是 NVLink、后者是 HBM，并把此处瓶颈更正为 GPU 间互连吞吐量；EPUB 正文加入译注。

## 表述限定

- `ch04.html`，“Asynchronous Execution with Streams”：原文把不同 CUDA stream 中的操作描述为可直接并发，并把 NCCL 的“nonblocking call”与集合操作排入 CUDA stream 后主机提前返回混为一谈。不同 stream 只是提供并发可能，实际重叠仍受数据依赖、硬件并发能力、copy engine、SM 与内存/网络带宽竞争限制；NCCL host-side enqueue、GPU-side completion，以及 communicator 的 nonblocking 配置也属于不同语义。译文已区分，并要求用 event 或 stream 依赖保证消费者正确同步。
- 同节 PyTorch DDP 与同步：原文断言每个梯度 bucket 都在固定的专用通信 CUDA stream 上触发 NCCL all-reduce；DDP reducer、通信 hook、bucket 重建和具体 stream 行为属于实现细节，会随 PyTorch/后端版本变化。原文还把 `Tensor.item()` 概括为完整设备同步，并建议每次迭代末尾统一同步计时；`item()` 会等待生成目标值所需的设备工作，但不宜无条件称为全设备同步。微基准优先使用 CUDA event，端到端墙钟计时才在测量边界同步。
- `ch04.html`，“Reducing Communication Frequency and Volume”：仅在 PyTorch DDP 中累积多次 backward 不会自动减少 all-reduce；非同步微批次需要 `no_sync()` 或等效通信抑制机制。梯度压缩、量化和稀疏化也不保证无损模型质量或更快：需计入编解码、索引、额外缓冲及误差反馈成本。原文称 DDP 默认 bucket 为 25 MB；PyTorch API 文档对 `bucket_cap_mb` 的默认值 25 按 MiB 描述。译文保留参数名，修正单位并将默认值定位为需 profiling 的起点。
- `ch04.html`，“Achieving Maximal Overlap in Practice”：原文用“计算 10 ms、通信 12 ms”推导完全重叠后约 12 ms，并在表 4-1 给出约 30% 加速和约 50% 重叠；两段示例没有任何计时代码，这些数值只是概念示意。通信只能在梯度逐步就绪后启动，且存在最后 bucket 的通信尾部，NCCL 还可能与模型计算争用 SM/内存带宽，因此 `max(compute, comm)` 只是理想化下界，不能视为 DDP 的预期结果。更大模型或 batch 也不保证收益更大。
- 同节 DDP 梯度顺序：对示例的前馈网络，反向传播通常从输出侧 `fc3` 开始，再到 `fc2`、`fc1`。原文却称 `fc3` 梯度最后计算，同时称 `fc1`/`fc2` 已先完成归约，顺序相反。译文已修正，并说明 DDP 按 bucket 就绪而非简单按单层触发，第一轮还可能重建 bucket。
- 同节程序清单：第二段代码使用 `os.environ` 却没有 `import os`；两段均使用 `init_method="env://"`，但未设置 `MASTER_ADDR`/`MASTER_PORT`，单 GPU fallback 也仍需要有效 rendezvous 环境。程序清单按“代码原样保留”原则未改动，译文已明确运行前提和缺失 import，避免将其误当作开箱即用基准。
- 同节主机读取与同步：原文建议把 `.item()`/日志等操作移到“另一个 stream”，但需要把值返回 CPU 的操作最终仍必须等待相应设备工作，单纯更换 CUDA stream 不能消除主机等待。译文改为降低采样频率、延迟或批量消费；异步 D2H 需配合锁页缓冲区、event 和正确生命周期管理。原文关于手动同步“极少需要”的结论也限定为：自定义 stream、外部库、主机读取和缓冲区复用仍可能要求用户显式建立依赖。
- `ch04.html`，“NVIDIA Magnum IO Optimization Stack”：原文多次用“bypassing the CPU”概括 GDS 与 GPUDirect RDMA。两者的关键收益是让兼容设备与 GPU 内存直接 DMA，减少经 CPU 主存 bounce buffer 的数据复制；CPU 仍参与 I/O/通信提交、连接建立、控制与错误处理。译文统一改为“绕过主机内存 staging”，并明确所需的硬件、驱动、文件系统/网络和拓扑条件。
- 同节 SHARP 与 Ethernet：SHARP 是 NVIDIA Quantum InfiniBand 交换机的在网归约能力，启用还需要兼容固件、Aggregation Manager、插件及受支持 collective。原文称 Ethernet 集群通常缺少 SHARP，并据此解释许多超大规模系统不用 Ethernet，又断言 SHARP 应在可用时启用。Spectrum-X/RoCE 等 Ethernet 平台有不同的拥塞控制和加速能力；互连选择还取决于成本、运维、拓扑、可扩展性和工作负载。译文保留 SHARP 的产品边界，但删除由单项功能推导整体互连优劣的绝对结论，改为实测与系统级权衡。
- `ch04.html`，“High-Speed, Low-Overhead Data Transfers with RDMA”：原文把 RDMA/GPUDirect RDMA 描述为完全绕过 CPU。RDMA NIC 可绕过传统内核逐包数据路径并直接 DMA 已注册内存；GPUDirect RDMA 进一步减少 GPU 数据经主机内存 staging，但 CPU 仍负责内存注册、队列建立、work request、completion 和控制/错误处理。原文还称 RoCE GID 不匹配会直接阻止 GPUDirect 注册；GID 更直接影响寻址、端口选择与连接，GPU 内存注册和 RDMA 建链应分别验证。译文已修正。
- 同节 GPUDirect 验证：`lsmod | grep nvidia_peermem` 只验证 legacy peer-memory 路径。现代受支持配置也可使用 DMA-BUF，不一定加载 `nvidia_peermem`；`NCCL_DEBUG=INFO` 能显示 transport/plugin 选择，但仍应结合 GPU/NIC 计数器、拓扑和支持 CUDA 缓冲区的 RDMA perftest。原文所称回退后“数十 GB/s 降至数 Gb/s”及吞吐下降一个数量级均非通用比例。
- 同节 InfiniBand/RoCE/TCP：原文用不同线速网络比较 RDMA 与 TCP，并暗示 TCP 通常不超过 100 Gb/s；现代 TCP 同样可运行于 200/400 GbE 及更高速率，并利用多队列和 offload。公平比较需要相同线速、消息、并发和 NUMA 拓扑。原文无条件要求 MTU 9000，但 jumbo MTU 必须在端点、交换机、VLAN/隧道全路径一致；TCP socket buffer/CUBIC/BBR 调优只影响 TCP 路径，不影响已选择的 RoCE/InfiniBand RDMA transport。BBR 也不保证在所有数据中心 fabric 上优于 CUBIC。
- 同节 AWS EFA：原文把 EFA 概括为 placement group 内的“InfiniBand-level RDMA”。EFA 通过 libfabric 暴露 OS-bypass 能力并使用 AWS SRD 等传输机制，它不是 InfiniBand，GPUDirect 和可达性能依实例类型、EFA/NCCL plugin、placement 与云端配置而定。译文按 AWS 产品边界修正，并把跨本地/云路径改为要求确认 Direct Connect、VPN 或其他实际连接，而非笼统断言必经公网。
- 同节 CPU/IRQ 亲和性：原文建议把 NIC 中断或 polling thread 固定到与 NIC/GPU 同 NUMA 的“一个核心”。实际应结合 HCA 队列、RSS、irqbalance、通信 progress model 和 CPU 负载分散，避免把所有 IRQ 集中到单核。译文改为按队列与线程测量配置，并保留 NUMA 局部性原则。
- `ch04.html`，“Tuning Multinode Connectivity”：原文再次把 NVL72 的约 130 TB/s 称为 all-to-all bandwidth，并建议无条件优先 NVLink。该数字是 72 块 GPU 各约 1.8 TB/s 双向 NVLink 端口带宽的聚合（约 129.6 TB/s），不是任意 collective 或单作业的可达吞吐；NVLink fabric 与 InfiniBand/Ethernet scale-out 网络也承担不同范围的数据路径。译文明确聚合口径，并要求按通信域、拓扑和应用模式选择。
- 同节 NCCL multirail：原文建议用 `NCCL_NSOCKS_PERTHREAD`/`NCCL_SOCKET_NTHREADS` 优化多 NIC，并要求每块 NIC 位于不同子网。这两个变量只影响 socket transport 的 helper thread/socket 并行度，不是 RDMA multirail 开关；多 rail 的地址与子网设计取决于 IB fabric 或 RoCE VLAN/路由，并非机械要求“每 NIC 不同子网”。两条/四条 800 Gb/s 的 1.6/3.2 Tb/s 也只是标称聚合线速，collective 有效吞吐还受 PCIe、GPU/NIC 比例和协议影响。
- 同节 IBGDA/direct NIC：原文称 GPU 可在“没有 CPU 参与”下驱动满带宽 RDMA。IBGDA 可减少稳态数据路径中的 CPU proxy 与延迟，但初始化、内存注册、控制和错误处理仍依赖主机软件，达到线速也取决于支持矩阵、拓扑和消息模式。译文已限定。
- 同节诊断工具：原文把 `ibstat`、`ifstat` 都称为网络接口计数器。`ibstat` 主要显示 InfiniBand CA 与端口状态，`ifstat` 显示接口流量；IB/RoCE 的详细端口错误、拥塞和包计数通常需 `perfquery`、sysfs、`ethtool -S` 或厂商遥测。译文已按工具职责修正。
- `ch04.html`，“Multinode Communication Pitfalls / Gloo”：原文把 Gloo 称为 NCCL 失败后的 fallback，并断言 CUDA tensor 会自动经 CPU staging、训练仍正确但慢一个数量级。PyTorch/NCCL 初始化失败通常报错或 hang，并没有普遍的无声 Gloo fallback；Gloo 主要支持 CPU tensor，CUDA tensor 是否支持或如何处理依构建/版本而定。示例本身分配的是 CPU tensor，所以只能测 CPU/Gloo collective，不能证明 GPU staging 路径。译文已区分 backend、tensor device 与 transport。
- 同节 Gloo/NCCL 数值示例：程序清单省略计时代码，却给出 400 MB/200 ms 和 400 MB/4 ms 两条输出，并把后者简单除得 100 GB/s 后称为 800 Gb/s InfiniBand 线速。all-reduce 的 algorithm bandwidth 与 bus bandwidth 需按算法和 world size换算，payload/time 不能直接等同端口线速；代码中的 tensor 实为约 400 MiB，且改用 NCCL 还必须移动到 CUDA device。译文保留输出清单原样，明确它们不可由所示代码复现，并建议用 `nccl-tests` 报告统一口径。
- 同节 `NCCL_SOCKET_IFNAME`：原文要求固定为 `ib0`，并称这会让 bootstrap 经 HCA 后自动切换到最快 GPUDirect RDMA。接口名因 IPoIB/RoCE/系统命名而异；该变量选择 socket/bootstrap IP 接口，不直接选择 RDMA HCA，也不保证 GPUDirect。译文改为按网络设计选择并分别验证 bootstrap 与数据 transport。
- 同节 NCCL 版本：原文描述“PyTorch bundled NCCL 对抗 system libnccl”并断言必然 hang 或无声回退。单个进程最终加载一个具体 `libnccl.so`；实际风险是动态链接路径覆盖、跨 rank 版本不同、ABI/network plugin 不兼容等，结果可能是错误、hang 或路径变化，但非必然。原文示例 `torch.cuda.nccl.version() == ()` 的空元组也不是正常版本值。译文改为检查运行时版本、动态链接和各 rank 环境。
- 同节 bootstrap 端口：原文称 `50000 51000` 是建议的宽临时端口范围，但它仅约 1001 个端口，且 `ip_local_port_range` 只管理本地临时端口，不等同于开放防火墙或设置远端监听端口。译文改为按并发连接、TIME_WAIT、其他服务和安全策略容量规划，并通过 socket 状态与 NCCL 日志确认是否真的端口耗尽。
- `ch04.html`，“Multinode Communication Pitfalls / network bandwidth”：原文称 `nvidia-smi dmon` 可收集 NVLink/PCIe/Network 吞吐；该工具主要监控 GPU 利用率、功耗、温度、显存活动及版本支持的部分 PCIe 指标，不是通用 NIC/NVLink fabric 流量工具。译文改为使用 NIC/RDMA 端口计数器、`ethtool -S`、`ip -s` 与厂商遥测，并提示 namespace/offload 可见性。
- 同节 socket/RDMA 参数：原文先正确说明 `NCCL_NSOCKS_PERTHREAD`/`NCCL_SOCKET_NTHREADS` 只调 socket transport，却又称增加它们有助于同时利用两块 NIC。二者控制 helper thread 与 socket 并行度，不直接启用 RDMA multirail；示例“2 线程 × 2 socket = 每进程 4 连接”也不等同于每块 NIC 的固定分配。译文保留 NVIDIA 文档中的乘积上限 64，但要求按当前版本、CPU 开销和实际 transport 测量。
- `ch04.html`，“Straggler nodes or processes”：`torch.distributed.monitored_barrier` 的 PyTorch 文档要求 Gloo process group，不能直接作为 NCCL collective watchdog；可为诊断创建单独 Gloo group。NCCL asynchronous error handling 的变量和行为随 NCCL/PyTorch 版本演进，也主要检测通信错误/timeout，不等同于性能慢 rank 分析。译文已区分错误检测与阶段耗时监控。
- `ch04.html`，“GPU memory fragmentation under UCX/RDMA”：原文将 PyTorch caching allocator 的 reserved memory、GPU 内存碎片和 UCX registration pool 混为一体。`memory_reserved()` 与 `memory_allocated()` 的差值只能描述 PyTorch allocator 状态，不能证明 UCX 注册资源耗尽；UCX registration cache、NIC memory key 与 allocator 是不同层。示例没有初始化或调用 UCX，却注释缓冲区会被 UCX 注册，因果不成立。
- 同节示例输出：代码中的 `big_buffer` 在函数结束前始终存活并占用约 0.8 GB，因此每轮删除 `small`/`medium` 后 `memory_allocated()` 不可能降为输出所示的 0.000 GB；输出不是该代码的可信运行结果。按“代码原样保留”原则，两个清单未修改，译文明确矛盾。`empty_cache()` 只释放未占用缓存 block，不释放活跃 tensor、不保证整理碎片，也不等于清空 UCX registration cache。升级“最新 CUDA”也不是通用修复，应使用经验证的框架/驱动/CUDA/UCX/plugin 组合。
- `ch04.html`，“NCCL Communication Algorithms / Ring”：原文称 Ring “bandwidth-optimal”，并把每个 rank 的算法数据量与每条链路的传输量并列。该结论成立于经典环形 all-reduce 和理想均匀链路模型；多 rail、非均匀拓扑、协议开销及链路竞争都会影响应用可达带宽。译文保留标准数据量公式，但限定其模型和适用范围。
- 同节 Tree/NVLSTree：原文称设置 `NVLSTree` 就会启用 NVLink SHARP offload。实际还取决于 NCCL 版本、GPU/NVSwitch 平台、拓扑发现和运行时支持；算法名可用不等于每次 collective 都实际走交换机内归约。译文已补充这些前提。
- 同节 CollNet：原文将实现固定描述为“每组一个 leader GPU 参加第二层树归约”，并以此保证节点间低延迟和节点内高带宽。CollNet Direct/Chain 的数据流由 NCCL、网络插件和拓扑共同决定，SHARP 卸载也需要支持的 fabric、插件和 collective。译文改为分层通信的原则性说明，不把一种示意结构当成固定实现。
- 同节 PAT：原文把 PAT 描述为 Ring 与 Tree 的流水线混合体，声称对大消息达到近 Ring 吞吐、对小分块保持 Tree 延迟，并进一步称其通过多个 CUDA stream 交错 reduce-scatter/all-gather。NCCL PAT 是并行聚合树算法，最初主要面向 all-gather/reduce-scatter，其支持范围随版本演进；内部调度不等同于应用显式使用多个 CUDA stream，也没有对所有拓扑作上述性能保证。译文按版本与实测结果限定。
- 同节自动选择与数值：NCCL 使用拓扑发现和调优模型选择算法/协议，目标是良好性能，但不能保证对每个工作负载都选中“最快”组合。原文所引最高约 7.6 倍只是特定 NVLink 系统、中小消息和软件版本的测试结果，不是通用 all-reduce 加速比例；“几十 MB 以下使用 Tree”也不是固定阈值。译文要求在目标硬件上用 profiler 或 `nccl-tests` 验证。
- 同节 `NCCL_ALGO`：该变量用于限制/覆盖算法候选，算法名称和 collective 支持具有版本依赖性。示例 `NCCL_ALGO=NVLSTree,PAT` 不能保证两者在任意 NCCL 版本或操作上均可用；环境变量还必须在 communicator 初始化前设置。译文保留示例并加入版本核对与基准验证要求。
- `ch04.html`，“Distributed Data Parallel Strategies”导语：原文称 NCCL/NIXL 等机制可使系统以高效率扩展到“数千和数百万 GPU”，且并行策略是线性扩展的充分条件。现实可扩展性还受模型分解、网络、负载均衡、调度、故障域和软件栈限制，“数百万 GPU”缺少可复核的部署依据。梯度累积与激活检查点也会分别影响同步/有效 batch 和重计算成本，不能概括为不牺牲吞吐。译文已限定。
- 同节 FSDP：原文称 FSDP 分片 activations、gradients 和 parameters。PyTorch FSDP 的核心是分片参数、梯度和优化器状态；激活内存通常通过 activation checkpointing、重计算或其他并行方法管理，并非默认的 FSDP 分片状态。译文已更正。
- 同节 `DataParallel`：原文把反向路径描述为将梯度收集、平均到主 GPU 后再广播给其他 GPU。PyTorch `DataParallel` 在反向传播中把副本梯度归约到基础模块参数，优化器更新基础参数，下一次 forward 再复制模块；并非每步固定广播聚合梯度。原文还称模型只在第一次 forward 时复制，实际每次 forward 都会 replicate。译文已按 PyTorch 行为修正。
- 同节 DP/GIL：原文将 DP 的主要成本全部归因于 GIL，并断言各 GPU kernel launch 在 Python 中严格串行、超过 2–4 GPU 后超线性退化。实际还包括每次模型复制、scatter/gather、主设备输出与梯度集中、线程调度等成本；PyTorch 的 C++ 调用和 CUDA 异步入队也不能简化为所有 launch 都被 GIL 串行化。2–4 GPU 不是严格性能边界，译文改为遵循 PyTorch 官方对单机多 GPU 也优先 DDP 的建议，并要求实测。
- 同节设备编号：DP 示例使用默认 GPU 0 和 GPU 1，原文却称“GPU 1 and GPU 2”。译文按代码更正为 GPU 0/1。代码清单本身保持原样。
- 同节 DDP 示例：`after_ddp.py` 定义了 `train_ddp()`，结尾却调用未定义的 `main()`；没有任何计时或输出代码，因此无法产生书中“DDP step took 30.00 ms”。函数又用 `LOCAL_RANK` 覆盖传入的全局 `rank`，随后把它传给 `init_process_group(rank=...)`，多节点时会造成不同节点 rank 重复。按代码原样保留原则未改清单，译文明示其不可直接运行，并区分 global rank 与 local rank。

- `ch05.html`，“Sequential Versus Random Read Patterns”：小文件问题常来自 open/stat、目录和远端元数据请求，不只是“磁盘随机 seek”；现代 NVMe 随机 IOPS 也很高。Arrow/Parquet 对图像 payload 是否合适取决于编码、schema 和访问模式，少数超大文件还会降低并行度、增加重试/更新成本。译文改为选择适当 shard 大小并保留训练随机性。
- 同节 S3 对象合并：较大对象可摊薄请求开销并利用 range GET，但会牺牲细粒度更新、并行、负载均衡和失败重试。原文只给出“提前合并”单向建议，译文补充按请求、缓存和恢复选择 shard 大小。
- 同节 Python I/O：Python `open()` 的用户态 buffered I/O 与 Linux 内核 readahead 是不同层，原文把它们合称“OS read-ahead buffer”。1 MB 也不是相对 4 KB 永远最佳，需考虑 direct I/O 对齐、样本、缓存、设备和 queue depth。
- 同节 dataset API：`TFRecordDataset`、`IterableDataset`、`DataLoader` 不自动保证顺序读取；访问模式由 dataset、sampler、worker 分片与 shuffle buffer 决定。buffer/prefetch 还需与 worker 数和内存预算联合调优。
- 同节 `io_uring`：批量提交、固定文件/缓冲区和 polling 可减少部分 syscall/注册开销，但是否真正异步取决于内核、文件系统以及 buffered/direct I/O；polling 还会消耗 CPU。更高 queue depth 也可能增加缓存污染和尾延迟。
- 同节 XFS/EFS：`noatime` 可避免 atime 更新，但默认 `relatime` 已减少许多写入，收益需实测。Amazon EFS Max I/O 面向高度并行且可容忍更高单操作延迟的场景，不是所有负载的“最高性能”默认；EFS 当前 throughput mode 还包括 Elastic 等选项，原文只写 Bursting/Provisioned 已不完整。译文保留原链接并要求按最新 AWS 文档与 CloudWatch 验证。
- `ch05.html`，“Tuning NVMe and Filesystem for Throughput”：`blk-mq` 是 Linux 块层多队列架构，不是单个 I/O scheduler；`none` 与 `mq-deadline` 也不存在脱离 workload 的固定最优选择。译文改为同时比较吞吐、尾延迟、公平性和 CPU 开销，并提示核对 device-mapper/RAID 下实际可调的块设备层级。
- 同节 readahead：内核 readahead 可以提前或合并底层读取，但不会直接减少应用发出的 read syscall 数量。`blockdev --setra` 的参数单位为 512-byte sector，而 `/sys/block/<device>/queue/read_ahead_kb` 使用 KB；原文未区分这两个接口的单位，译文已明确。
- 同节 RAID/cache：RAID 0 提高聚合吞吐但没有冗余，不能称为兼顾性能与可靠性的通用方案。page cache 基准必须区分 cold 与 warm 状态；数据集大于 RAM 也不必然发生严格意义的 thrashing，应结合 cache hit、major fault、reclaim 和设备 I/O 判断。
- 同节 Grace memory：Grace CPU LPDDR 与 GPU HBM 可通过 NVLink-C2C coherent 访问，但仍是不同物理内存池，不能简单合并成均匀统一的“CPU + GPU cache”。PB 级数据仍需流式、分层缓存与容量规划。
- 同节 PyTorch DataLoader：`num_workers > 0` 使用 worker 进程而不是线程。`pin_memory=True` 与 `non_blocking=True` 只为异步 H2D copy 创造条件，真正和计算重叠还需要合适的 stream、依赖与 copy engine；`persistent_workers=True` 会保留 worker 内存和状态。磁盘 100% busy 也不等于最佳 training goodput，过深队列可能恶化尾延迟。
- 同节 Grace 核心数：原文把 “72-core Grace CPU” 用作 GB200/GB300 节点的统一描述，但 Grace 核心数与节点组合依具体 Superchip/Compute Tray/SKU 而异。译文改为示例并要求从实际系统核对核心、SMT 和容器 cpuset。
- `ch05.html`，“Using NVIDIA GDS”：原文多次称 GPU 主动从 SSD/NIC 发起或“拉取”数据。GDS 的关键是兼容存储设备或 NIC 与 GPU 内存直接 DMA、避免主机内存 bounce buffer；应用与 CPU 仍参与 I/O 提交、配置、完成和错误处理。译文已按数据路径与控制路径分别表述。
- 同节兼容范围：GDS 支持取决于 GPU、驱动/CUDA、内核、文件系统、协议、客户端、厂商插件和拓扑。厂商提供 GDS-aware 方案不表示所有企业 NAS、对象存储或并行文件系统均能开箱即用；仅“支持 RDMA”也不足以证明网络文件会走 GDS direct path。译文要求按当前 NVIDIA 与存储厂商兼容矩阵验证。
- 同节 `O_DIRECT` 与异步 API：`O_DIRECT` 的必要性及非 direct 文件描述符的兼容路径随 GDS/后端版本变化，对齐错误可能导致失败、额外复制或降速。`cuFileReadAsync`/`cuFileWriteAsync` 入 CUDA stream 也不自动保证与计算重叠，仍需正确依赖、后端支持与硬件资源。
- 同节性能数字：VAST 报告中的 A100 约 20%、H100 30% 以上提升属于特定厂商测试，不是 GDS 的通用收益；100 Gb/s 链路速率也不能等同应用吞吐。原文由 1 MB × 1,000 batch/s 直接断言 CPU copy 占用数个核心，同样缺少内存带宽、NUMA、copy 次数和预处理假设。译文保留示例和来源链接，但明确必须在目标 workload 上测量。
- `ch05.html`，“Checkpointing GPU State with cuda-checkpoint”：原 EPUB 在 `cuCheckpointProcessUnlock` 的 `ss` 之间夹入 U+2060 和 U+200B 隐藏字符，会破坏复制、搜索和 API 识别。译文已恢复真实函数名，同时保留原有 code 节点结构。
- 同节流程边界：`cuda-checkpoint` 在 suspend 路径中排空工作、把 device memory 转入 driver 管理的 host allocation，再由 CRIU 持久化进程映像；这不是 GPU memory 到存储的 GDS direct DMA。挂起时间除内存映像/互连外，还包括 kernel 排空、同步、分配和驱动管理，需在目标系统实测。
- 同节恢复与迁移：相同 chip type 的 GPU remap 仍受 CUDA/driver 版本、支持对象、拓扑、CRIU、外部文件/网络资源和分布式状态约束，不能解读成任意节点间无条件迁移。CUDA 进程 checkpoint 也不能替代框架级 state dict/sharded checkpoint；模型、优化器、数据迭代器及分布式一致性仍需框架或应用管理。
- `ch05.html`，“Measuring GDS with gdsio”：原文把 GDS 提升 10%–20% 甚至更多描述为“不罕见”，并由一组 `8.0 GB/s → 9.6 GB/s`、`1.25 ms → 1.00 ms` 的输出得出系统收益，但未提供硬件、文件系统、cache 状态、重复次数或误差。两个 20% 的点估计算术正确；译文保留原命令和输出不变，但明确它们是示意数据而非可复现实验证据。
- 同节对比方法：CPU-mediated 与 GDS 路径的公平比较除保持 `gdsio` size、I/O size、read mode 和 transfer selector 一致外，还需控制目标文件、对齐、queue depth、并发、warm-up、page cache/direct-I/O 条件和 NUMA，并记录 CPU 利用率及多次运行分布。`-x 2`/`-x 0` 等参数语义也应按安装的 GDS 版本核对，不能把书中一次命令永久视为跨版本接口契约。
- `ch05.html`，“DeepSeek’s Fire-Flyer File System”：原文称 3FS 取消 cache 后“每个请求都直达 NVMe SSD”。3FS 的主数据路径可绕过 OS page cache，但请求仍经过 client、RDMA fabric、storage service、复制/纠删码及设备内部 cache；metadata 和异常路径也不能一概而论。译文将结论限定为减少 kernel page-cache 参与和 host-side copy。
- 同节 3FS/RDMA/GDS：3FS 的 client-storage RDMA 数据路径不自动等于 NVIDIA GDS 或 GPUDirect 直接进入 GPU memory。原文又断言任何 FUSE 文件系统都不可能提供 GDS；实际兼容性取决于 GDS 版本、kernel/client integration、厂商插件、文件描述符路径、`O_DIRECT` 与对齐。普通 FUSE read/write 路径通常不是 GDS direct path，但不能由“使用 FUSE”单一条件推出永久不支持。
- 同节 zero-copy 与重叠：即使 GDS 集成受支持，异步和 zero-copy 仍受 buffer registration、对齐、拓扑、fallback 及软件版本影响；prefetch/transfer 也只获得与 GPU kernel 重叠的可能性，实际并发取决于 buffer 生命周期、同步依赖和共享资源竞争。译文删除无条件“minimal overheads”和自动重叠的含义。
- 同节性能数字：7.3 TB/s、68 节点上的 6.6 TB/s foreground 加 1.4 TB/s background，以及 Ceph 约 1.1 TB/s，均为特定集群和 benchmark 的聚合口径。网络描述中的“双 100 Gb/s”还需明确是每节点、每 NIC 或其他聚合口径；只有副本、数据布局、请求模式、节点/设备数、网络和软件配置一致时，3FS/Ceph 才能公平比较。译文保留数字和来源链接，但不将其外推为通用倍率。
- `ch05.html`，“Distributed, Parallel Filesystems and Object Stores”：原文把 NFS 限定为“少数节点”，并断言更大集群的单个 NFS server 即使高端也很可能成为瓶颈。可扩展性取决于单机/scale-out 实现、后端盘、NIC、metadata rate、数据布局和 workload，不能由协议名称或固定节点数决定。译文改为按聚合 bytes/s、ops/s、metadata 与尾延迟容量规划。
- 同节 NFS 参数：最大 `rsize/wsize`（示例为 1 MiB）并非 small/random I/O 的固定最优值；实际值还受 client/server 协商与版本影响。原文把 client mount 的 `async` 当成简单性能开关，却未讨论其具体版本语义与写入持久性风险；`actimeo=60,lookupcache=pos` 也不等于笼统“把属性和目录项都缓存 60 秒”。译文保留原参数字符串，但要求依据一致性、durability 和当前 NFS 文档测试。
- 同节 NFS 存储：NVMe 或 striping 可以增加吞吐，但 RAID 0 没有冗余，任一盘故障会影响整个 stripe。训练数据只有在可重建或另有可靠副本时才适合采用这种容量/性能方案。
- 同节 S3：range request 不是“越大越好”，需要权衡固定请求开销、首 batch latency、并行度、无用字节、重试粒度和内存；并行线程过多还可能导致 throttling、重试与尾延迟。数据预置到 NVMe 或 FSx 等层也必须计入启动时间、增量同步、cache warm-up 和容量成本。
- 同节 Lustre striping：大型文件跨 OST 条带化可以聚合带宽，但不是 OST 越多越好。stripe count/size 需匹配文件大小、reader 并发和 OST 负载，小文件过度 striping 会增加 metadata/锁开销。4 × 500 MB/s = 2 GB/s 只是无其他瓶颈时的理论上限，实际还受客户端、网络、协议开销和共享竞争限制。
- `ch05.html`，“Tuning, Replicating, and Compressing Data”：`lfs setstripe` 的 4/8 OST 只是示例，stripe count/size 应按文件大小、reader 并发和 OST 负载选择。存储热点也不一定“最可能”来自 sharding；metadata、热门文件、重建、设备降速、客户端拓扑和其他 workload 都需排查。
- 同节全量复制：把数据集复制到每个计算节点可减少 steady-state 网络读取，但首次预置、cache miss、版本同步、epoch shuffle、故障恢复和弹性扩缩容仍需要网络与控制工作。额外容量也可能非常大，因此不能保证“立即获得性能提升”；收益取决于作业持续时间和副本重用率。
- 同节 Arrow/Parquet：原文将 JPEG 与“compressed text (Arrow and Parquet)”并列。JPEG 是编码/压缩格式；Arrow IPC 与 Parquet 是数据容器/列式格式，可在 buffer、column chunk 或 page 层使用不同 codec，但本身不等于“压缩文本”。译文按容器与 codec 分层表述，并指出 pipeline 每一步重复压缩可能产生转码开销。
- 同节硬件解压：nvJPEG、LZ4/Snappy/Deflate 硬件 decompression 的可用性取决于具体 GPU/SKU、CUDA API、codec、buffer/data path 和软件版本。专用引擎可能减少 SM 占用，但不能由 workload I/O-bound 就推出应优先采用这些 codec；还需比较压缩率、随机访问、decode latency 和端到端 samples/s。
- 同节 NVLink-C2C：最高约 900 GB/s 是特定 Grace Hopper/Blackwell 平台的双向聚合互连口径，不是任意 CPU-GPU 数据传输的单向应用吞吐，也不能自动防止 CPU-assisted stage 成为瓶颈。CPU LPDDR 与 GPU HBM 仍是不同物理内存池，实际访问受方向、放置、并发和流水线限制。
- `ch05.html`，“Monitoring Storage I/O”：原文称 `next(data_iterator)` 测得 GPU 等待下一 batch 的“总空闲时间”，且必然包含 background prefetch 与 H2D copy。实际测量的是主线程 iterator pull 的 wall time；prefetch 完成度会影响它，H2D 是否包含取决于代码边界。GPU idle 需结合 iteration critical path、CUDA timeline 和同步依赖判断。
- 同节 `num_workers=0`：该设置移除 PyTorch DataLoader worker 进程及后台 prefetch，不是原文所称的“后台线程调度”。它还会改变执行模型，所得同步 dataset/transform 时间不能直接外推正常多 worker 配置。异步 `.to("cuda")` 应用 CUDA event 或 profiler 测量，并结合 stream dependency 判断是否造成 stall。
- 同节 Nsight/DCGM：`--trace=gds` 与 `cuFile` tracing 的可用方式随 Nsight Systems、CUDA/GDS 版本变化；API timeline 不等同完整 NVMe peer-to-peer DMA 数据路径。DCGM 主要提供 GPU/显存/互连等受支持设备指标，不是通用文件系统监控器；需与 NVMe、filesystem、NIC/RDMA、client/server 和应用指标联合分析。
- 同节等待比例算术：原文把 GPU 等待占比从 30% 降至 5% 直接解释为训练 steps/s 提高 6 倍。若每步有效计算量不变，原总时间分别为 `compute/0.70` 与 `compute/0.95`，理想吞吐加速为 `0.95/0.70 ≈ 1.36×`。只有把等待时间本身相除才得到 6，但那不是总吞吐加速；译文已修正。
- `ch05.html`，“Efficient Data Loading and Preprocessing”：PyTorch `DataLoader(num_workers>0)` 使用 worker 进程；多 worker 只提供并行加载和 prefetch，不自动保证 H2D 与 GPU compute 重叠。真正 overlap 还需要 pinned source、nonblocking enqueue、独立 stream、正确依赖和可用 copy engine，并受带宽/计算竞争限制。
- 同节 pinned memory：`pin_memory=True` 与 `non_blocking=True` 为异步 H2D 创造条件，但锁页/注册、pinning thread、RAM 压力与 NUMA 放置有成本，不是原文所称“几乎总是有利”。`memlock` 应按并发 buffer 容量设置余量，不能为了避免失败无条件放宽为极大值。

- `ch05.html`，“Scaling Out Workers as You Scale Out Number of GPUs”：增加 GPU 不必然要求提高 global batch size；batch 策略还受优化收敛、显存、并行方式和 gradient accumulation 影响。ingestion 应按目标 aggregate samples/s、bytes/sample 与 per-rank workload 容量规划，而不是机械让 worker 数与 GPU 数同比增长。
- 同节 rank/shard：data-parallel sampler 通常划分逻辑样本索引，但不能自动保证每个 rank 读取不同的物理文件 shard 或本地存储。逻辑索引、manifest、文件布局与 cache 路由需协同；每节点固定本地 shard 还涉及 shuffle、replication、故障、再平衡和弹性扩缩容。
- 同节瓶颈判断：GPU 加速后 input pipeline 更可能暴露为瓶颈，但不是必然；通信、模型计算和同步也可能主导。CPU 总利用率不足以诊断 loader，应同时观察 per-core/NUMA、内存带宽、queue、storage/network、GPU idle 与端到端 goodput。
- `ch05.html`，“Multimodal Data Processing with NVIDIA DALI”：DALI 的 JPEG/video 路径是否使用 GPU、mixed decoder 或专用硬件，取决于 codec、operator、GPU、batch 和软件版本；并非所有 decode/augmentation 都“完全利用 GPU media hardware”。将预处理移到 GPU 还可能与模型争用 SM、memory bandwidth 和 decoder，只有 input-bound 且资源互补时才可能显著获益。

- `ch06.html`，“Threads, Warps, Blocks, and Grids / hierarchy”：单 block 最多 1,024 thread 是许多现代 NVIDIA GPU 的 device limit，还受每维上限、register/shared memory、launch bound 和目标 compute capability 限制。PyTorch/framework 生成 kernel 并调用 runtime，但 block 到 SM 的次序由硬件/runtime 调度，不应笼统称 framework “分配到所有 SM”。
- 同节 thread block cluster：该能力从 Hopper 等受支持架构引入，cluster 中 block 被协同调度到 GPU Processing Cluster 范围，并可使用 cluster barrier/DSMEM；不是所有现代 GPU/CUDA 组合都支持。使用前需核对 compute capability、portable/nonportable cluster size、launch API 和资源约束。
- 同节 DSMEM：DSMEM 为 cluster 内各 block 的 shared-memory segment 提供分布式地址映射，不是把所有 SM shared-memory bank 合并成均匀共享池。remote access 通常比 local shared memory 延迟更高，目标 block 必须保持存活至访问完成；它可减少部分 global-memory traffic，但仍有远端访问、barrier、cluster size 和 occupancy 成本。
- 同节 `__syncthreads()`：这是 block-wide barrier 及 shared/global memory ordering primitive，必须由 block 中所有未退出 thread 以一致控制流到达，否则可能 hang 或产生未定义行为。原文只强调 barrier overhead 并要求最小化同步，译文改为先保证依赖正确，再删除经证明冗余的 barrier。
- 同节 warp scheduling：硬件在 warp 因 dependency 无法 issue 时选择其他 ready warp，不是 CPU 风格的 context switch；是否能隐藏 global-memory/cache/pipeline latency 取决于 resident warp、独立工作、occupancy 和资源限制。
- 同节 warp/SIMT：原文把 warp 的 32 个 thread 一概描述为 lockstep execution。warp instruction 以 warp 为调度/发射单位，各 active lane 执行相应指令，但 independent thread scheduling、predication、divergence 和 reconvergence 使“lockstep”只是简化模型，不能据此假设任意 lane-level synchronization。
- 同节 occupancy：occupancy 是 SM 上 active warp 相对于硬件允许上限的比例，可增加 scheduler 找到 ready warp、隐藏 latency 的机会，但不直接等于 execution-unit utilization 或高性能。过度追求 occupancy 可能压缩 register/shared-memory budget，降低 instruction-level parallelism 或增加 spill；应结合 achieved occupancy、stall reason 和 throughput profile。
- 同节 register spilling：compiler spill 的值通常位于 CUDA local-memory address space，物理流量经过 cache/global-memory hierarchy，并非一个笼统的独立“slower memory”。实际代价受 cache hit、访问模式和 memory pressure 影响，需结合 compiler report 与 profiler 判断。
- 同节 block independence/compatibility：block 独立且次序无保证是 CUDA 可扩展调度的重要语义，但 grid–block–warp hierarchy 本身不能保证 kernel 在所有未来 GPU 上都无需修改。正确性与可运行性还受 memory/synchronization model、compute capability、binary/PTX compatibility、feature support 和资源上限约束，性能也需重新调优。
- 同节 warp divergence：divergent path 会以不同 active mask 执行，降低 useful lane utilization，但总时间不必然乘以 branch 数；成本取决于 path 长度、predication、active mask、memory behavior 和 architecture-specific reconvergence。不同 warp 采取不同 path 不构成同一 warp 内 divergence，却仍可能造成 path imbalance、tail effect、memory 或资源竞争。

- `ch06.html`，“Choosing Threads-per-Block and Blocks-per-Grid Sizes”：32 的整数倍通常可避免不完整 warp，是 block size 的合理起点，但不是最佳性能的充分条件；register/shared-memory demand、instruction mix、latency、memory access 和 workload shape 仍需 profile。小 block 也不保证较高 occupancy，可能受 active-block limit、资源粒度和工作划分约束。

- 同节局部变量：示例没有额外分配 output buffer，但不能据 source 断言除临时 `int idx` 外“不需要 memory”；compiler 可把 local scalar 放在 register，也可能因优化、debug build 或 register pressure 发生 spill。物理存放应由 compiler report/SASS/profiler 验证。
- `ch06.html`，“Configuring Launch Parameters”：256 threads/block 是常见调优起点，不是普遍最优值；512 也不保证在 Blackwell 上“maximize occupancy”。最佳值取决于每 thread register、每 block shared memory、allocation granularity、instruction/memory behavior、problem shape 和 active-block limit，应比较 occupancy calculator/API 与 profiler 中的 achieved occupancy、stall reason 和 throughput。
- 同节 SM residency：原文称“在一个 2,048-thread-capacity SM 上 launch 8 个 256-thread block”即可保持 pipeline busy。应用 launch 的是 grid，runtime/hardware 将 block 调度到 SM；程序不能用普通 launch parameter 指定某 SM 接收哪 8 个 block。2,048/256=8 也只是 thread-count 上界，register、shared memory 和 active-block limit 可能先限制 residency，高 occupancy 更不保证 pipeline busy。
- 同节 underfilled warp：非 32 整数倍的 block 会产生末尾不完整 warp，其 inactive lane 不贡献 useful work，但“occupy a scheduler slot”只是简化说法。实际 issue、active mask、resource allocation 和性能代价依指令与架构而定；32 的倍数是合理约束而非单独性能结论。
- 同节 ceiling division：`(N + threadsPerBlock - 1) / threadsPerBlock` 要求正的 divisor，且加法不能在所用 integer type 中 overflow；结果还须满足 grid-dimension limit。`N == 0` 时该公式产生 0 block，而零维 kernel launch 通常无效，因此调用方应跳过 launch或采用明确的空输入路径。大规模输入可使用宽类型、安全 ceiling division 与 grid-stride loop。
- `ch06.html`，“2D and 3D Kernel Inputs”：示例的 `h_image`/`d_image` 是线性 `float*` allocation，2D 仅是 logical thread coordinate 和 row-major `idx = y * width + x` 映射；2D grid/block 不会自动把 pointer 变成二维存储。若数据含 row stride、subview 或 `cudaMallocPitch` padding，索引必须使用实际 pitch，而不能固定假设 contiguous `width`。
- 同节 3D 推广：只把 grid/block 改成 `dim3(x,y,z)` 不足以“directly map volumetric data”。kernel 仍需显式计算 `(x,y,z)` 到 address 的映射，考虑 row pitch、slice pitch、layout、halo/boundary，并确保 `width * height * depth` 与 linear index 使用足够宽类型、不会 overflow；各 block dimension 的乘积也不得超过 device limit。
- 同节 2D 示例资源管理：清单用 `cudaMallocHost` 分配 `h_image`，但结束时未调用 `cudaFreeHost(h_image)`，造成 pinned host-memory leak；同时未检查 stream creation、allocation、copy、launch、synchronization 和 free 的返回值。程序清单按用户要求保持原样，译文正文和本勘误指出缺失项。
- 同节 async ordering：H2D copy、kernel、D2H copy、stream synchronize 与 `cudaFreeAsync` 都使用同一 stream，因此主要 dependency 顺序成立；`cudaFreeAsync` 在 synchronize 后 enqueue，随后 `cudaStreamDestroy` 会处理 stream teardown，但生产代码仍应检查 API error，并明确 allocator/memory-pool 与生命周期约束。
- `ch06.html`，“Asynchronous Memory Allocation and Memory Pools”：原文把传统 `cudaMalloc/cudaFree` 统一描述为每次执行 full-device synchronization 和 `mmap/ioctl`。这些 API 可能引入同步与 driver/OS memory-management overhead，尤其 `cudaFree` 的同步语义会影响 outstanding work，但具体内部调用、缓存和 fast path 依 CUDA/driver/platform，不能把示意系统调用当作固定实现。
- 同节 default pool：CUDA stream-ordered allocator 使用目标 device 的 default memory pool，也可使用显式 pool；原文所谓 runtime 维护一个“global pool”容易误解为跨 device/所有 context 的单一 pool。pool、device、IPC/access policy 和 current-pool selection 有明确作用域，应按 Runtime API 版本核对。
- 同节 `cudaFreeAsync`：该调用把 free enqueue 到 stream，并按 stream order 在先前工作之后生效；它不是在 host 上“waits for only stream1 to finish”。若 pointer 也被其他 stream 使用，应用必须用 event/dependency 或合适 reuse policy 建立 lifetime ordering，否则单一 stream 的顺序不足以防 use-after-free/reuse hazard。
- 同节 stream isolation：CUDA stream 是 ordered command sequence，不是完全 isolated channel。不同 stream 共享 execution/memory/copy resource，可通过 event、dependency、memory hazard 和 default-stream semantics 交互；`cudaStreamNonBlocking` 主要取消与 legacy default stream 的隐式同步关系，不保证 operation overlap。
- 同节 fragmentation/throughput：pool reuse 往往降低 allocation latency 和某些 external fragmentation，但 pool 也会保留 reserved memory，存在 size-class/internal fragmentation；切换 async allocator 不保证更一致或更高 throughput。应测量 allocated/reserved footprint、allocation latency、trim/release behavior 和 end-to-end throughput。
- 同节 release control：`cudaMemPoolAttrReleaseThreshold` 是在 synchronization opportunity 后尝试释放 reserved memory所依据的 threshold，不是严格 memory cap；`cudaMemPoolTrimTo` 是尽力把 reserved memory 缩减到目标附近，也不能直接“消除 fragmentation”。较低 retained footprint 与较低 allocation latency/更高复用率之间通常存在权衡。
- 同节 PyTorch allocator：PyTorch CUDA caching allocator 与 CUDA pool 思路相近，但具体 backend 和选项依 PyTorch version/configuration；`PYTORCH_ALLOC_CONF`（旧别名 `PYTORCH_CUDA_ALLOC_CONF`）的 native 与 `cudaMallocAsync` backend 语义不同，不能把所有选项或行为视为通用。
- `ch06.html`，“Understanding GPU Memory Hierarchy”开头：原文称 global allocation 来自“a stream's memory pool—including the default stream 0 memory pool”。stream-ordered allocator 的 default/current pool 以 device/allocator 为作用域，stream 提供 ordering；不存在一个专属于 stream 0 的独立 pool。传统 `cudaMalloc` 也不能无条件等同于从 stream pool 分配。
- 同节 TMEM/TMA：TMEM 是 Blackwell 上供特定 `tcgen05.*` Tensor Core path 使用的 per-SM tensor memory，普通 CUDA pointer 不能直接寻址。TMA 主要负责 global memory 与 SMEM 的 multidimensional async transfer；TMEM allocation/access 和 SMEM/TMEM movement 使用相应 tcgen05 instruction/control operand。原文把两者混成由 TMA 编排全部 movement，且括号未闭合。
- 同节 operand path：原文/图示把 operand A 固定放在 TMEM、B 放在 SMEM、accumulator 放在 TMEM。具体 tcgen05 MMA instruction form、descriptor 和 operand source 不同，不能把示意图升级为所有 UMMA 的通用路径；TMEM 常用于 accumulator/中间 tile，但数据布局和 movement 必须按 instruction specification。
- 同节 `cuda::memcpy_async`：高级 API 是否生成 TMA 依 architecture、shape、alignment、memory space、compiler 和 API overload，不能把任何 `cuda::memcpy_async` 都等同于硬件 TMA。译文保留其作为可能抽象并明确条件。
- 同节表 6-5 口径：表同时混合 architecture/device capacity、microbenchmark latency、理论 port bandwidth 和产品 HBM peak。约 10/20–30/200/数百至 1,000 cycle、每 SM TB/s 与总计约 8 TB/s 等不能跨 SKU/clock/access pattern 直接比较，也不是 CUDA contract；应以目标 B200/B300 specification、device attribute 和 microbenchmark/profiler 为准。
- 同节 register/constant memory：register read/write 并非无条件“single-cycle and free”，dependency、bank/port conflict、operand collector 和 scheduling 会影响 throughput/latency。constant cache 在 warp uniform cached address 时支持 broadcast，但“约 1 cycle、等同 register”也不是通用保证；不同 address 会按 distinct address serialization，miss 访问下层 memory。
- 同节 local memory：CUDA local memory 是 per-thread address space，物理存储通常位于 device memory 并可经过 L1/L2；不仅用于 spill，也可承载 compiler 放置的 local array/large object。其 capacity 受 address-space、allocation 和 device memory 限制，不是“near-unlimited”，其 traffic 也不能直接等同约 8 TB/s HBM peak。
- 同节 reuse 结论：register/shared-memory/cache reuse 通常减少 off-chip traffic，但 register/shared-memory 使用过多会降低 occupancy，cache hit 依 locality，local-memory access 也可能命中 cache。优化目标应是 end-to-end data movement 与 throughput，而非无条件最小化 global/local memory usage。
- 同节 register allocation/spill：每 SM 64 K 个 32-bit register、每 thread architecture limit 255 不等于 compiler 可任意连续使用；allocation granularity、resident warp/block、launch bound 和 live range 共同决定 occupancy/spill。spill 的 local-memory traffic 可命中 L1/L2，不能统一描述为每次直接付出完整 DRAM latency。
- 同节 shared-memory carveout：原文把 `cudaFuncAttributePreferredSharedMemoryCarveout` 与每 block 最大 dynamic shared-memory opt-in 混在一起。前者表达 L1/shared carveout preference，通常是 hint；需要超过默认 dynamic shared-memory limit 时使用的是 `cudaFuncAttributeMaxDynamicSharedMemorySize` 等相应 function attribute。static+dynamic allocation、per-block/per-SM limit 和保留量均须查询目标 device。
- 同节 shared-memory ownership：shared memory 是 block-scoped address space，block 驻留期间从 SM SRAM 分配；并非每个 block 在硬件中永久拥有一块独立 dedicated SRAM。bank conflict、instruction width、carveout 和 occupancy 会改变实际 latency/throughput。
- 同节 TMEM automation：原文称 TMA 用 descriptor 自动管理 global、SMEM、TMEM 的全部 data flow，从而让开发者无需手工管理 Tensor Core 数据。TMA 主要服务 global↔SMEM transfer；TMEM 使用 tcgen05 allocation/load/store/copy/MMA 等 instruction，library/compiler 仍需安排 descriptor、barrier、lifetime 和 pipeline。
- 同节 constant-memory use case：uniform cached address 可由 warp broadcast；不同 address 按 distinct address 数拆分/序列化，miss 访问下层 memory。RoPE、ALiBi、LayerNorm parameter 或 quantization scale 是否适合 constant memory 取决于 64 KB capacity、update/lifetime 与 warp access uniformity，不能保证所有 thread 访问都没有 L2/global traffic。
- 同节 L2/coalescing：原文要求所有 global load 构造成 128-byte aligned transaction，并把 128 byte 等同 cache line/最佳访问。现代 GPU memory request 会按 architecture-specific sector/transaction 处理；应让 active lane 访问连续、自然对齐并减少 sector 数，但实际 transaction 取决于 element width、active mask、cache policy 和 architecture，128-byte segment 不是普遍唯一单位。
- 同节 B200 dual-die：B200 对 CUDA 呈现单 GPU 与统一 global address space，原书给出双 die、约 10 TB/s die-to-die link 和各四个 HBM stack。统一寻址/单 GPU programming model 不证明跨 die/HBM access 在 latency、bandwidth 和 contention 上完全 uniform；应把物理 locality 与 fabric behavior 视为可测的微架构因素。
- 同节 PoC/coherency：原文把 point of coherency 简化为 thread、CTA、CTA cluster、device、system 五层。memory visibility/order 还取决于 memory space、cache/coherence domain、atomic/fence/barrier 和 scope；仅选择 scope 不会自动建立 happens-before，也不能修复 data race。cluster scope 还只适用于受支持架构与相应 DSMEM/cluster primitive。
- 同节 Nsight/peak：cache hit、spill 与 throughput counter 可辅助定位 data path，但接近某个“on-chip peak”不是普遍优化目标，counter definition 和采样口径需按 metric 文档解释。coalescing 主要由 warp address pattern 决定，L1/L2 负责 cache/reuse，不能把 cache 描述为主动把任意 HBM access 合并。
- `ch06.html`，“Unified Memory”：managed memory 提供 CPU/GPU 可使用的统一虚拟地址与 driver-managed placement；是否具有硬件 cache coherence、是否迁移或远程访问，以及可并发访问能力依 OS、GPU、interconnect、driver 和 device attribute。统一地址空间不等同于所有平台上无须同步的“single coherent memory”。
- 同节 Grace memory/带宽：原文称 NVLink-C2C 在“CPU HBM 与 GPU HBM3e”之间提供约 900 GB/s。Grace CPU 使用其 CPU memory subsystem（常见为 LPDDR5X），不是 HBM；约 900 GB/s 通常是 NVLink-C2C 双向聚合互连口径，也不是 fault-driven migration 或单向 application access 的保证带宽。
- 同节 fault behavior：GPU 访问不在理想位置的 managed page 时，可能 fault+migrate，也可能在受支持平台远程访问；互连不总是 NVLink-C2C。fault 会阻塞受影响 access/warp，并可能通过 batching/dependency 扩散，但不能一概称整个 GPU 停顿。page size、fault service、working set 和 CPU/GPU ping-pong 都影响表现。
- 同节 prefetch：`cudaMemPrefetchAsync` 是按 stream 排序的 placement/migration request，不保证在 kernel launch 前自动完成，也不保证 overlap；调用方必须把 kernel 放在同一 stream 后续或建立 event/dependency。prefetch range、destination、capacity 和后续 access 不匹配时仍会迁移或远程访问。
- 同节 advice：`cudaMemAdviseSetPreferredLocation` 是 preferred-placement hint；`cudaMemAdviseSetReadMostly` 表示主要读取，允许适用平台优化/复制 read-only page，但不是 C++ const 或禁止 write，写入可使 replica invalid。`cudaMemAdviseSetAccessedBy` 预先声明 device access/建立 mapping，不能保证 launch 时绝不迁移。
- 同节 stream attachment：`cudaStreamAttachMemAsync(..., cudaMemAttachSingle)` 改变 managed allocation 的 stream association，并要求 association 生效时仅由相应 stream 访问；其他 stream 并非被硬件安全阻止。它不保证只有该 stream 会 fault、不会自动把 migration overlap 到该 stream，也不能普遍消除 cross-stream synchronization。
- 同节 multi-GPU placement：向 specific device prefetch 是 placement request，不是把 page 永久“pin in nearest NUMA-local GPU memory”。GPU 与 CPU NUMA 的拓扑概念也不能混为一个自动最近位置；peer mapping、NVLink/PCIe route、capacity pressure 和后续访问可能导致 remote access 或 migration。`cudaMemcpyPeerAsync` 则是显式 peer copy，语义不同。
- 同节性能结论：prefetch/advice 有时可减少 first-touch fault 并接近显式 `cudaMemcpy`，但不能保证消除“大多数 surprise stall”或跨平台接近手工 copy。应比较 end-to-end time、fault/migration counter、interconnect traffic、capacity pressure 与 correctness，并为 oversubscription、irregular access 和多 writer 场景单独验证。
- `ch06.html`，“Maintaining High Occupancy and GPU Utilization”：occupancy 是 active warp 相对 architecture maximum 的比例；GPU utilization、SM Active、active-lane efficiency、FLOP/pipe utilization 和 throughput 是不同指标。高 occupancy 只增加 ready-warp 机会，不保证 compute unit busy；低 occupancy 也可能在高 ILP/compute-heavy kernel 中达到最佳性能。
- 同节 80%–100% 目标：原文建议现代 GPU 将 occupancy 推至 80%–100%，没有普遍依据。所需 occupancy 取决于 latency、eligible warp、instruction mix、register/shared-memory budget 和 bottleneck；过度压缩 register 或 shared memory 可能增加 spill/重复计算并降低性能。应以 throughput 与 stall/profile 选择最低充分 occupancy。
- 同节 Blackwell register：64 K register/SM 与 255 register/thread 只是容量/architecture limit，不能推出 Blackwell 更容易“many warps without spilling”。allocation granularity、block size、live range 和 compiler decision 会共同限制 residency，spill 与 occupancy 也不是单调关系。
- 同节 PyTorch loop：逐元素 Python loop 的问题不仅是低 occupancy；tensor indexing、scalar assignment、dispatcher/launch、temporary 和潜在 synchronization 会产生大量 overhead，实际 kernel 数依 PyTorch/backend，不能把它等同单个 `addSequential` kernel。Python launch 可异步排队，因此“serialize”也不是所有 device timeline 的精确描述。
- 同节 vectorized expression：eager PyTorch 的 `A + B` 通常启动 elementwise kernel，但 compiler/fusion/backend 可改变 launch 数和 implementation；并非所有 novel operation 都“几乎总有”最优 native implementation。需检查 fusion、layout、temporary allocation、numeric semantics 和 profiler timeline。
- 同节表 6-6 可复现性：原书给出 48.21/2.17 ms、1.5%/95% GPU utilization、1.3%/38.7% occupancy、3.1%/100% warp efficiency，但未注明 GPU、版本、warm-up、重复次数或精确 metric definition。所列 `ncu` 命令没有显式请求 warp-execution-efficiency metric，parallel 命令还未请求 duration；`nsys --stats` 也不天然输出一个统一定义的 GPU-utilization 百分比，因此表不能由命令直接完整复现。
- 同节 profiler 指标：Nsight Systems timeline-derived GPU activity、Nsight Compute SM Active、`sm__warps_active...pct_of_peak...` occupancy 和 warp execution efficiency 分母/时间窗口不同，不能互换或都解释为“SM 被 active warp 占满”。`ncu` replay 还会扰动 timing；报告必须记录精确 metric、tool version、range 和测试方法。
- 同节 22× 加速：`48.21 / 2.17 ≈ 22.2`，算术成立，但同时改变了 thread 数、lane utilization、device coverage、memory-level parallelism 和每 thread loop work；不能把加速归因于 occupancy 从 1.3% 增至 38.7%。表中的 3.1%≈1/32 与单 active lane 一致，但 95% GPU utilization 不能由此直接推出。
- 同节 timeline：图 6-20 是概念图，不是实测 trace。parallel warp 可覆盖部分 dependency stall，但 bandwidth saturation、barrier、tail effect、cache miss correlation 和 resource contention 仍会留下 gap；source code 不直接指示 scheduler 如何 interleave，hardware 根据 ready dependency/pipeline 发射。
- 同节 LLM decode：小 batch token-by-token decode 常呈低 arithmetic intensity、memory-bandwidth-sensitive，但每 layer/每 token 读取量受 batch、quantization、cache、parallelism、fusion 和 model architecture 影响。执行不是把整个模型一次搬入 register/shared memory，也不是把 weight 反复“移入移出 GPU”；weight 通常常驻 HBM并被各 layer kernel 流式读取，KV cache/activation 同样产生 traffic。
- 同节 compute/bandwidth 趋势：峰值 FLOP/s 增长常快于 off-chip bandwidth，但约 8 TB/s 是特定 Blackwell SKU/口径，不是所有 Blackwell 的统一值。是否 memory-bound 应由 arithmetic intensity、可达 bandwidth 和 roofline/profile 证明，而不是从模型规模或硬件趋势直接断言。
- `ch06.html`，“Tuning Occupancy with Launch Bounds”：`__launch_bounds__(maxThreadsPerBlock, minBlocksPerMultiprocessor)` 的第一个参数是 application/compile launch contract，不只是 hint；以超过该 maximum 的 block size 启动会失败。第二个参数用于 compiler 推导 resource/register threshold，但不保证 runtime 实际驻留该 block 数，shared memory、active-block/thread limit、grid size 等仍可先限制。
- 同节不可能的 `__launch_bounds__(256,16)`：在原书所述 2,048-thread/SM target 上，16×256=4,096 thread 不可实现。ptxas 可能警告 `.minnctapersm` 超范围并忽略相应 constraint，而不是原文所称把 request 自动“reduce to”8 block 并保留等价语义。warning 文本/行为依 Toolkit 与 target，应把此例视为错误配置演示。
- 同节 compiler register heuristic：launch bounds 可能让 compiler 降低 register use 以满足潜在 residency，也可能在不降低目标 block residency 时提高到可用 threshold，以减少 instruction；unrolling/inlining/spill 的变化不是固定结果。annotation 不保证避免 spill、更高 occupancy 或一致 throughput。
- 同节 spill 因果：spill 是 compile-time register pressure/constraint 和 allocation decision 的结果，不是 runtime 因“too many threads run out of registers”才发生。增加 residency target 可能迫使 compiler spill，但 actual launched thread 数不会动态耗尽一个可变 register pool 后再 spill。
- 同节 Occupancy API：`cudaOccupancyMaxPotentialBlockSize` 根据 kernel resource metadata、device limit 与 dynamic-smem input 计算潜在 occupancy candidate；它不运行 kernel、不测 timing，因此不是原文所称 performance autotuner，也不保证返回“optimal” block size。dynamic shared memory 随 block size 变化时应使用相应 callback/正确 API 形式。
- 同节 `minGridSize`：返回值表示为达到候选潜在 occupancy 所需的 minimum grid size，不是覆盖 N 的 correctness grid，也不保证任何 GPU-utilization metric 饱和。示例用 `max(minGridSize, ceil_div(N,bestBlockSize))` 可能为小 N 启动额外 thread，kernel 必须有 bounds check/grid-stride loop，并处理 N=0、overflow 与 grid limit。
- 同节候选验证：原文建议测试“±1–2 block sizes”，更合理的是测试相邻合法 warp-multiple/shape candidate，并执行 warm-up、重复计时和 correctness 检查。register、instruction count、shared memory、cache、coalescing 和 problem shape 均可能让 sub-maximal occupancy 更快。
- `ch06.html`，“Debugging Functional Correctness with NVIDIA Compute Sanitizer”：Compute Sanitizer 通过 instrumentation 检测所执行路径中的特定错误，运行开销可能很高；clean report 不证明程序无 bug，也不证明 performance。CI 应使用代表性小规模 test、固定 tool/CUDA version、保存日志和 timeout，并避免 kernel filter 过窄而漏掉跨 kernel/lifetime 问题。
- 同节 NVTX：Compute Sanitizer 可识别/报告 NVTX 相关上下文，具体 `--nvtx yes`、filter 和 leak-report 行为依版本/tool。NVTX annotation 主要改善 range/context 和可观测性，不会自动把所有 sanitizer instrumentation 严格限定到 region，也不能“minimize false positives”作为普遍保证。
- 同节 `--error-exitcode`：该选项用于在发现 tool error 时返回指定 exit code，适合 CI gate；仍需区分 application 自身 exit、sanitizer internal error、timeout 与 suppressed report，并核对当前 CLI syntax/默认值。索引原文把 Compute Sanitizer 误写为“Computer Sanitizer”，工作 XHTML 为保持索引属性未改，勘误在此指出。
- 同节 memcheck：memcheck 覆盖许多 global/local/shared out-of-bounds、misalignment、hardware exception 和 device allocation leak，但不能检测未执行路径、所有逻辑边界、host race 或 application-level correctness。`--check-device-heap` 等 option 的可用性与默认值应查对应 Toolkit 文档。
- 同节 racecheck：racecheck 重点分析 shared-memory hazard（RAW/WAR/WAW）及相应同步，不是通用 global-memory data-race detector。hazard severity 需结合 programming model，Volta+ independent thread scheduling 下依赖 implicit warp lockstep 的旧代码尤其需复核。
- 同节 initcheck：initcheck 主要检测未初始化 device global-memory read，不是“any uninitialized memory access”检查器；通常应先运行 memcheck，避免 invalid access 干扰 initialization report。它也不能推断所有逻辑 initialization invariant。
- 同节 synccheck：synccheck 检查一部分 barrier/warp synchronization misuse，例如 divergent barrier、invalid argument/mask 等，能力依 architecture/tool version；它不是完整 deadlock detector，也不会证明所有 memory ordering、fence 和跨 thread state 一致。

## 第 6 章补充勘误

- `ch06.html`，“Roofline Model”：原文在同一示例中先写约 80 TFLOPs，随后误写成水平线约 `80 FLOPs/sec`；正确量级为约 `80 TFLOP/s`。`80 TFLOP/s ÷ 8 TB/s = 10 FLOP/byte` 的山脊点算术成立，但计算 roof 与 bandwidth roof 必须采用一致的理论峰值或持续实测口径。算术强度的 byte 也必须明确对应 HBM、L2、L1 或算法流量；译文已以片外 HBM/global-memory traffic 为本例口径。
- 同节低精度与 Blackwell 解压：原文将 FP8 相对 FP16 概括为吞吐翻倍，并声称 4-bit/2-bit 权重会统一由硬件在加载时解压、转换为 FP16/FP32。位宽减半可以减少裸数据存储量，但实际吞吐取决于 Tensor Core 指令、累加精度、量化元数据、稀疏性口径和 kernel 效率；Blackwell 支持的低精度及硬件辅助解压也需要软件栈选中相应数据路径。译文保留其优化方向，但删除无条件吞吐保证。
- 同节 prefill/decode：原文称 attention layer 的 prefill 通常 compute-bound，而 matrix multiplication 的 decode 常 memory-bound，分类维度混乱。prefill 和 decode 都包含 attention 与矩阵运算；prefill 中较大的 GEMM 往往更易达到计算受限，逐 token decode 的小 batch 运算则常受权重/KV-cache bandwidth、launch 或 latency 限制，具体仍随 batch、sequence length、并行策略、量化和硬件变化。译文已修正。
- 同节 profiling：原文把高 DRAM 利用率、低 ALU 利用率直接等同于 warp 大多因 memory access stall，并把 global load efficiency 下降解释为 DRAM request 响应不够快。前者还需排除依赖、occupancy、分支、同步和 launch 等因素；后者主要表示请求有效字节与实际传输字节之比下降，常见于未合并或浪费的访问。原文还断言优化后 memory-pipe utilization 应趋近峰值，但减少总流量可能使该利用率下降而执行更快。译文改为结合 stall reason、cache、吞吐和端到端时间判断。
- 同节异步复制：原文将 `cudaMemcpyAsync` 与 kernel 重叠写成必然，并把未重叠归因于 default-stream synchronization 或缺少 pinned buffer。真正重叠还取决于 non-default stream、依赖关系、页锁定 host memory、copy engine、方向和硬件并发能力；NVTX host range 也不等同于设备操作的精确时间区间。译文已补足条件，并清除了原文第二处 `cudaMemcpyAsync` 内嵌的 U+200B/U+2060 字符，同时保留 `code` 标签。
- `ch06.html`，“Key Takeaways”：原文小标题 `threads → locks → grids` 是笔误，正确层次为 `thread → block → grid`。原文还建议在 dedicated stream 上使用 `cudaMallocAsync`/`cudaFreeAsync`；stream-ordered allocator 不要求固定专用 stream，关键是正确表达 allocation lifetime 与跨 stream dependency。译文已更正。
- 同节 TMEM/UMMA：原文称 TMEM、UMMA 与 FP8/FP4 结合可以把 kernel 从 memory-bound 转为 compute-bound。TMEM 是 Blackwell Tensor Core 路径中的专用片上存储，可减少部分 register/shared-memory traffic 并改善 pipeline，但是否改变 Roofline 区域取决于具体数据流与瓶颈，不能普遍保证。译文已限定。
- `ch06.html`，“Conclusion”：原文称降低 active thread 数会“为其他 thread 释放 register”。更准确地说，block size、每 thread register 数和 shared-memory 用量共同决定每个 SM 的 resident block/warp；降低并发配置可能允许每个 thread 使用更多 register、减少 spilling 或采用更大 tile，但仍受 per-thread 与 per-SM 上限约束。译文已修正。

## 第 7 章勘误

- `ch07.html`，“Coalesced Versus Uncoalesced Global Memory Access”：原文反复把现代 NVIDIA GPU 的 global-memory coalescing 描述为合并到单个 128-byte transaction，并称未对齐的连续 128-byte warp load 会产生两个完整 128-byte transaction。现代架构的分析应区分 cache line 与 32-byte sector；32 个 thread 各加载一个 FP32 值时，对齐的 128-byte 范围覆盖 4 个 sector，首地址偏移 4 字节通常覆盖 5 个 sector，并非必然传输 256 字节。译文改为按 requested bytes、sector bytes、首地址偏移和 cache 层级说明。
- 同节 Blackwell 带宽：原文把双 GPU 模块每侧约 8 TB/s 的 HBM bandwidth 相加为 16 TB/s，并写成在 GB200/GB300 中“增加到”该值。16 TB/s 是跨两个独立 GPU 的聚合口径，不是单个 kernel 可访问的统一共享 HBM bandwidth。译文已限定。
- 同节 Nsight Compute 指标：原文把 `Average Sectors per Request > 4.0` 一概视为 noncoalesced，并称接近 4.0 就必然完全合并。4.0 只适用于本例中满 warp、每 lane 4-byte scalar access 的理想值；FP64、vector load、部分 active mask 或其他指令的理想值不同。Global Memory Load Efficiency 与相关 metric 名称也随 Nsight Compute 版本变化。译文要求按访问宽度计算理论 sector 数，并结合 requested/actual throughput 与 source metric 判断。
- 同节 stride 2 示例：原文先将 stride 2 称为 misaligned access，后又称 PyTorch gather 必然生成 32 个 separate load/transaction。stride 2 是跨步而非地址未对齐；对 FP32 满 warp，它通常覆盖约 252 字节并触及约 8 个 32-byte sector，仍由一条 warp memory instruction 的 lane request 经 coalescer 形成 sector request，而非固定 32 个 DRAM transaction。输出 `out[idx]` 仍是连续写入。译文已分开说明读写路径。
- 同节 AoS/SoA：原文暗示 AoS 会使相邻 thread 必然跨步而 SoA 必然连续。效果取决于 thread 读取哪些字段、结构尺寸、对齐和访问模式；当相邻 thread 读取同一字段时 SoA 通常更有利，但读取整个紧凑结构时 AoS 也可能合并良好。译文已补足条件。
- 同节表 7-1：原书已注明数值为概念示意，且给出的 C++ 代码没有事件计时或 Nsight 命令，无法据此复现 25%→90%、4.8 ms→1.3 ms 等结果。译文保留原表数值，但明确不得将其视为任意 Blackwell GPU 上的实测保证；SM Active 也不直接等同于 ALU utilization。
- 同节 scalar/vectorized 过渡：原文称 fully coalesced warp 在底层仍进行 32 个独立 4-byte read，再由硬件拼成 128-byte transaction；又称 `float4` 可把它从 32 个 transaction 固定变为 4 个 128-byte transaction。Coalescer 本就依据 lane address 生成 sector request，scalar lane 数不等于 DRAM transaction 数。每 lane 使用 `float4` 会把一个满 warp 的搬运量从 128 字节增加到 512 字节，主要潜在收益是减少动态 load/store instruction 与地址计算，并非减少同等数据量的 sector 数。译文已更正。
- 同节 PyTorch：原文断言 contiguous tensor 的 `clone()` 底层使用 vectorized memory copy，并称它通常不会被 `torch.compile` 融合。实际 kernel 选择与编译器是否消除/保留 copy 取决于 dtype、layout、alignment、aliasing、mutation、graph 和版本；`max-autotune` 也不保证特定 schedule。译文已限定。

- `ch10.html`，“Warp Specialization and the Producer-Consumer Model”scheduler：Warp 并非各自拥有独立 scheduler；SM 的多个 scheduler 各自管理一组 resident warp。不同 warp 的 load/math/store 是否能在同一 cycle issue 取决于 architecture、partition、dependency 与 execution-pipeline availability。
- 同节 multi-issue：Warp specialization 可增加 independent ready instruction 与不同 pipeline overlap 的机会，但不创造新的 hardware issue capability，也不保证 instruction 连续执行或 load/math/store 同 cycle 并发。
- 同节论文案例：原文引用的 nearly perfect overlap 是特定论文 workload、hardware、schedule 与 metric 下的结果，不能作为 warp specialization 的通用保证；L2/Tensor Core utilization “in phase”也需结合 timeline definition 与 runtime 解读。
- 同节 CUTLASS ping-pong：`gemm_tma_warpspecialized_pingpong` 的名称、schedule 和 availability 依 CUTLASS version/architecture，不是稳定通用 API 名称。
- 同节 epilogue：Epilogue 可包含 accumulation、scaling、rearrangement 和 store，但并非所有 per-MMA epilogue 工作都必须在下一 MMA 前串行完成；dependency 由 buffer、accumulator 与 schedule 决定。
- 同节 TMA destination：TMA bulk tensor transfer 通常在 global memory 与 shared memory 之间进行，不是直接把 tile 搬入 register。Consumer 再按 MMA operand contract 从 shared memory 或相应 architecture-specific data path 取数。
- 同节 FlashAttention-3：Warp specialization 是其 Hopper optimization 的一部分，但 near-peak FLOP/s、所有 hardware unit busy 或固定 speedup 不是通用结果，需限定 dtype、shape、sequence/head dimension、GPU 与 benchmark。
- 同节 PyTorch/Triton：`torch.compile`/TorchInductor/Triton 是否生成 warp-specialized kernel 或使用 CUTLASS ping-pong schedule 依 version、backend、architecture、operator、shape 与 heuristic；barrier cost 也不应笼统称为 low-cost。
- `ch10.html`，“Using CUDA Pipeline API for Warp Specialization”scope：本节清单使用 unified CTA-scoped pipeline，其 acquire/commit/wait/release 是 participating CTA threads 的 collective；不能同时称为只同步特定 warp或“SM-wide”handoff。不同 warp 直接调用不同 primitive 需要 partitioned producer/consumer pipeline design。

- 同节 persistent terminology：跨 tile 循环本身不足以证明 persistent kernel；还需结合 launch grid、resident worker lifetime 与 global work assignment。
- 同节表 10-3 provenance：41.3/20.5/18.4 ms、68/92/96%、stall category、L2 throughput、instruction count 与 scaling 均无 device、shape、compiler、launch、metric definition 或 profiler report，是示意值而非可归因于清单的 benchmark。

- `ch10.html`，“PyTorch, CUDA Pipeline API, and Warp Specialization”compiler backend：`torch.compile` 不保证所有 GPU kernel 都由 Triton 实现；TorchInductor 可生成 Triton code，也可调用 ATen、cuBLAS、cuDNN 或其他 external/backend kernel。生成代码也不保证与 `<cuda/pipeline>` primitive 语义等价或采用 warp specialization。
- 同节 performance parity：看不到显式 `cuda::pipeline` 不足以证明底层一定存在相同 instruction/barrier；即使存在，也不保证与手写 pipeline 相同的 latency、throughput 或 occupancy。需检查 generated artifact 与 profiler。
- 同节 kernel count：Matmul→softmax→matmul 的 eager/compiled expression 不必固定对应三个 GPU kernel；dispatch、fusion、graph 和 backend 会改变 kernel count。
- 同节 SDPA dispatch：`scaled_dot_product_attention` 是 dispatcher，可选择 FlashAttention、memory-efficient、cuDNN 或 math fallback 等 path，依 device、dtype、shape、mask、dropout、causal setting 和 software version；不保证固定 loader/compute/storer warp，也不保证消除所有 intermediate HBM traffic。
- 同节 `torch.compile` suitability：Graph break、dynamic shape、compile overhead、unsupported op 与 backend selection 都会影响收益，不能称其对所有 performance-sensitive/irregular workload 都 ideal。
- 同节 linear scaling：Warp specialization 不保证 across-warp near-linear scaling或 maximize utilization；role imbalance、dependency、barrier、register/SMEM、instruction throughput 与 latency 均可能限制性能。
- `ch10.html`，“Persistent Kernels and Megakernels”queue scope：跨 CTA 共享的 work queue 通常位于 global memory；普通 shared memory 只在 CTA 内可见，DSMEM 也仅在 cluster scope，不能笼统称为全 grid shared queue。
- 同节 host signaling：Kernel 内轮询 host signal 需要 supported mapped/coherent memory、system-scope atomic/order 与 progress protocol；普通 device code不能任意把 CPU host memory 直接 copy 到 shared memory。
- 同节 launch/residency：Launch block 数等于 SM 数不保证 one-block-per-SM 固定映射或每 SM active；placement、residency 与 progress 依 scheduler、grid 和 resource usage。
- 同节程序清单 device symbol：`g_index` 声明为 `__device__` symbol 后，host 侧直接 `cudaMemset(&g_index, ...)` 通常不是正确 symbol initialization；应使用 `cudaMemsetToSymbol` 或显式 device allocation/pointer argument。清单按原书保留。
- 同节 atomic contention：让每个 thread 对单一 global counter 执行 `atomicAdd` 会形成 hot atomic，且 33,792 threads 争抢约 1,000 tasks 会有大量无效 dequeue；不能据此推出 high utilization。实际实现常用 chunked/workgroup dequeue、hierarchical queue 或其他 load-balancing design。
- 同节 timing arithmetic：1,000 tasks × 0.1 ms = 100 ms 是串行 work-time sum，不是 independent GPU task 的必然 wall-clock time。1,000 launches × 0.02 ms = 20 ms 也是 submission-overhead sum，可能与 execution overlap，并可由 batching/CUDA Graph 缓解。
- 同节 utilization/occupancy：原文的约 35% capacity 与 nearly 100% SM active 无测量依据。256/2048 = 12.5%，不是 12%；maximum threads/SM 依 compute capability，occupancy 还受 warp/block/register/SMEM limit 约束。
- 同节 TMA overhead：TMA 可减少 address-generation/per-element copy instruction，但仍使用 memory subsystem、barrier 和 issue/control resource；不能称为不对 SM compute pipeline 增加任何负担，也不保证 persistent kernel 特别有效。
- `ch10.html`，“Common Workloads for Persistent Kernels”idle guarantee：Dynamic work queue 可改善 load balance，但 queue starvation、tail imbalance、atomic contention、memory latency 与 ready-task 数量仍会使 SM idle；persistent kernel 不保证 no SM ever goes idle。
- 同节 divergence/deadlock：Warp divergence 通常导致 path serialization，不会单独使整个 kernel hang。Deadlock 更常来自 partial barrier participation、非法 grid synchronization、termination/memory-order bug 或 circular resource dependency。
- 同节 QoS：Long-running persistent kernel 可能占用 GPU resource并影响 concurrent workload、tail latency、preemption/watchdog 与 QoS；stream assignment 本身不保证公平，需要 grid sizing、priority、MIG/partition 或 runtime scheduling。
- 同节 universal gains：2–3× throughput、消除 launch overhead、maximize occupancy、全程保持 on-chip data 和 fully occupied SM 均非普遍保证；首次 launch、queue/polling、global spill、synchronization 与 resource pressure 仍存在。
- 同节 alternatives：对 small/irregular task 应同时比较 batching、CUDA Graph、library/framework scheduling 与普通 fused kernel；persistent design 不是唯一或默认最优方案。
- 同节 PyTorch：PyTorch/TorchInductor 不会普遍把任意 multistage graph 自动变成单一 megakernel，但特定 operator/backend 可已有 persistent/fused implementation。Custom megakernel 还可能受 code size、register/SMEM、barrier、load balance、numerical behavior 和 reduced concurrency 限制。
- `ch10.html`，“Megakernels for Inference”multi-GPU scope：普通 CUDA kernel 在单一 device context 上执行。所谓跨 GPU megakernel system 通常是在各 GPU 上运行 cooperating persistent kernel，并通过 communication/distributed scheduler 协同，不是一个 kernel launch 字面跨越多个 GPU。

- 同节 causal attribution：1.2×–6.7× 范围依 GPU、model、batch、vLLM/SGLang version/config 与 measurement，且可能同时来自 scheduling、fusion、memory traffic 和 baseline 差异，不能只归因于消除 repeated kernel launch或外推为通用收益。
- `ch10.html`，“Persistent Kernels and Warp Specialization”relationship：Warp specialization 与 persistent execution 可组合但互不依赖；不能说 thread block cluster 支持了 persistent kernel，“因此”也支持 warp specialization。
- 同节 launch scheduling：其他 kernel 占用资源时，普通 kernel 的 block 通常等待调度或以较低 concurrency 运行，不是整个 launch 必然失败。Cooperative launch、cluster launch 或依赖 all-worker residency 的协议才有更严格 capacity requirement，并可能因 oversubscription 失败或 deadlock。
- 同节 cluster placement：Thread block cluster 提供 cluster-level co-scheduling/synchronization/DSMEM semantics，但不保证 blocks 分别占据多个“邻近 SM”，也不允许程序固定 block-to-SM mapping；cluster 可在一个或多个 SM 上实现，依 architecture 与 resource placement。
- `ch10.html`，“Cooperative Groups”group granularity：Cooperative Groups 只支持定义明确的 group type 与成员关系，不是任意 thread 集合/任意粒度都能同步；grid、cluster group 还需要相应 launch mode 与 hardware capability。
- 同节 softmax：稳定 softmax 通常涉及 max reduction 与 exp-sum reduction。Multi-kernel implementation 通常在 device global memory 交换 intermediate，不需要复制回 host。跨 block aggregate 也不能由其他 block 从某个 block 的 register或普通 shared memory读取，仍需 grid-visible storage/protocol。
- 同节 cooperative guarantee：Cooperative launch 保证 grid 满足 concurrent-residency capacity，不保证每个 thread 的控制流必然到达 `grid.sync()`；divergence、early return、fault 或无限循环仍会造成 deadlock。
- 同节 Hopper origin：Thread block cluster 与 DSMEM 从 Hopper compute capability 9.0 已提供，并非 Blackwell 才出现。它们只提供 cluster-scope cooperation，不替代 full-grid synchronization。
- 同节 on-chip claim：Cooperative grid barrier 不使 register/shared memory 跨 block 可见，也不保证 intermediate 保留 on-chip。增大 block 也可能降低 residency，并非避免 launch failure 的通用策略。
- 同节 atomics versus DSMEM：Global atomics/flags 不一定低于 cluster/DSMEM efficiency；选择取决于 coordination scope、architecture、mapping、contention 与 traffic。Cluster 不能用于任意全 grid coordination。
- `ch10.html`，“Cooperative Grid Synchronization and Persistent Kernels”launch reduction：单 kernel 替代 2,000 次 launch 是结构性示意，不等于恰好节省 2,000 次 launch overhead；barrier、queue、global-memory traffic、compilation/dispatch 与 device execution cost 仍存在。
- 同节 data lifetime：Per-thread register 与 per-CTA shared memory 可跨 `grid.sync()` 由各自 owner 保持，但不能跨 block 直接读取。Cross-block exchange 仍需 global memory 或适用 cluster/DSMEM。
- 同节 grid clamp：若 `((N + threads - 1) ÷ threads)` 超过 cooperative capacity，简单 clamp grid 会漏处理元素；应使用 grid-stride loop、分批 cooperative launch 或 non-cooperative fallback。
- 同节 capacity：不能把 modern GPU concurrent blocks 概括为几千；capacity 依 SM、block/warp、register、SMEM、kernel attributes 和 cooperative mode，必须目标 device 查询。
- 同节 persistent claim：Outer loop 不返回 host 只是 persistent-like shape，不自动证明长期 progress、安全 convergence、deadlock-free 或适合 LLM layer workload。
- `ch10.html`，“When to Combine Persistent Kernels and Cooperative Groups”one-block-per-SM：这是可能的 launch strategy，不是通用 best practice；block placement、occupancy、residency、resource footprint 与 scheduler 必须实测，不能保证最大化 occupancy 或防止 SM idle。
- 同节 decision table：Cluster 不等于 GPU resource partition，也不能保证 cooperative/persistent kernel 不影响其他 workload。需要 QoS 时应评估 grid sizing、stream/MPS/MIG 或专门 partition/scheduler。
- 同节 data locality/peak：`grid.sync()` 可减少 kernel boundary，但不保证所有 data 留在 register/SMEM、消除 global-memory exchange、保持 GPU 持续 busy 或接近 peak。
- `ch10.html`，“Thread Block Clusters and DSMEM”cooperative-vs-hardware：Cooperative Groups 是 software/API abstraction；thread block cluster 是 hardware/launch hierarchy。Cooperative group 的“任意 collective”不等于任意线程集合、visibility 或同步能力。
- 同节 resource isolation：Cluster 不自动“保留一部分 SM、剩余 SM 给其他 kernel”，cluster placement/residency 依 cluster size、grid、资源与 scheduler；也不是通用 GPU partition。
- 同节 GPC：GPC 是硬件分组，cluster 可在规定 GPC/GPC partition scope 内协同调度，但不应类比为 block 内线程必然固定在同一 SM，也不提供任意 block-to-SM mapping。
- 同节 multidie claims：Blackwell/GB 系列的 die、GPC partition、NV-HBI 与 cross-die cache coherence 依 SKU/architecture，不能只凭“two-die”推断逻辑 GPC 或 placement；应查目标产品文档/device attribute。
- 同节 DSMEM scope/performance：DSMEM 只在同一 cluster scope 可见，不能替代全 grid exchange；on-chip SRAM、capacity、latency 和 access path 依 architecture/address pattern，不保证“SM-to-SM speed”或完全避免 HBM。
- 同节 cluster launch control：`cluster launch control` 依 hardware/CUDA version/launch path，并非所有 GPU 自动提供；它不保证 persistent work queue load balance 或 warp-specialization efficiency。
- 同节 barrier speed：Cluster barrier 参与范围小于 grid barrier，可能更低开销，但“much faster”需按 cluster size、architecture、contention 与 workload 实测。
