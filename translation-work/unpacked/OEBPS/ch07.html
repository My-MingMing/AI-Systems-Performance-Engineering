第 7 章　分析与调优 GPU 内存访问模式

随着 AI 模型规模和复杂度增长，GPU memory system 往往成为理论计算能力与实际性能之间的瓶颈。正如第 6 章所述，现代 NVIDIA GPU 将大量面向吞吐优化的 core 与专用 Tensor Core 结合起来，并配有高带宽内存（HBM）、CPU-GPU 统一虚拟地址与一致性机制（具体能力随 Grace Blackwell Superchip 等平台而异）、片上 shared memory、cache，以及 Tensor Memory Accelerator（TMA）等专用数据搬运引擎。

本章将介绍多种 CUDA C++ 与 PyTorch 优化技术，包括合理组织和对齐数据以提高访存效率、消除重复加载，以及利用硬件能力让数据传输与计算重叠。

通过矩阵乘法、tensor operation 等优化前后的具体示例，你将看到 memory access pattern、tiling strategy 和异步数据传输方面的改动如何减少浪费的带宽并提高有效算术强度。它们可能改变 kernel 的主要瓶颈，但是否从 memory-bound 转为 compute-bound 仍需结合目标硬件和实测 Roofline 判断。

学完本章后，你将能够编写更有效利用 GPU memory hierarchy 与硬件数据传输引擎的 CUDA kernel。

合并与非合并的 global memory access

代码的 memory access pattern会显著影响性能。当 warp 中各 thread 访问相邻地址时，硬件通常能用最少的 memory transaction 覆盖所请求的数据。若地址分散或跨越额外边界，则会访问更多 32-byte sector，取回较多未使用字节并浪费带宽。现代 NVIDIA GPU 的 L2 cache line 与 sector 组织具有架构细节；进行 coalescing 分析时，应关注指令所请求的有效字节、实际访问的 sector 数及 cache 命中层级，而不能把所有访问简单等同为单个 128-byte transaction。

部分 Blackwell GPU 的单 GPU HBM3e 标称带宽可达约 8 TB/s；若把双 GPU 模块两侧的带宽相加，聚合值可写为约 16 TB/s，但这不是任一单 kernel 可访问的统一共享带宽。非合并访问会增加实际传输字节数，使有效带宽显著低于物理带宽上限。

在非合并情形中，warp 内各 thread 从分散地址加载数据，因而触及许多 sector。即使地址连续，若整个 warp 的访问范围没有按 sector 边界良好覆盖，也可能比理想情形多访问 sector；具体数量取决于每 thread 访问宽度、首地址偏移和 cache 层级。

以 32 个 thread 各读取一个 4-byte 值为例，连续且 128-byte 对齐的 128-byte 范围恰好覆盖 4 个 32-byte sector。若首地址只偏移 4 字节，这一连续范围通常会覆盖 5 个 sector，而不是原文所暗示的必然产生两个完整 128-byte 传输；更大的偏移或不同访问宽度会产生不同结果。判断浪费应比较 requested bytes 与实际 sector bytes。

在 kernel 代码中，这类问题通常表现为跨步（strided）或不规则索引，使 thread 触及不同 sector 乃至不同 cache line。此时一个 warp 的 global-memory instruction 需要访问更多 sector，而不是用最少数量覆盖连续有效数据。

在 Nsight Compute 中，Memory Workload Analysis 可显示 requested/actual throughput、sector 数和每 request 的 sector 数等指标；具体名称随版本变化。对每个 thread 加载 4-byte 的满 warp 指令，理想连续访问常对应 4 个 32-byte sector，但其他向量宽度、active mask 或 replay 情形不能套用固定阈值。低 load efficiency 或相对于 requested bytes 过多的 sector 表明存在带宽浪费；DRAM 吞吐低于峰值本身并不能证明 warp 正在等待 memory，也可能是 cache hit、低并行度、指令依赖或其他瓶颈。

若分析确认 kernel 因非合并访问而浪费带宽，可以重新组织数据，使 warp 的 32 个 thread 尽量访问连续元素。例如，以 input[idx] 访问数组，其中 idx = blockIdx.x * blockDim.x + threadIdx.x；也可以在按字段处理数据时，将 array of structures（AoS）改为 structure of arrays（SoA），使 thread i 访问字段数组中的元素 i。图 7-2展示两种布局：AoS 中相邻 thread 读取同一字段时可能形成跨步访问，而 SoA 可让 thread i 对应连续字段数组中的元素 i。AoS 并非天然低效；若 thread 读取整个紧凑结构，或结构宽度与访问模式合适，它也可能合并良好。

完成布局调整后，硬件通常能以更少的 sector request 完成 warp 的 global-memory load，从而提高返回数据中的有效字节比例。是否改善以及幅度多大，仍应通过 Nsight Compute 指标和 kernel 时间验证。

下面通过优化前后的示例，说明如何把跨步 global-memory access 改为连续访问。性能增益取决于目标 GPU、cache 行为和测量方法。

优化前示例（C++）：非合并的跨步访问。在这个示例中，每个 thread 以 stride 2 从输入数组复制元素，形成连续 thread 之间相隔 8 字节的访问。它是跨步访问，但不是通常所说的“地址未对齐”：

#include <cuda_runtime.h>
#include <iostream>

__global__ void uncoalescedCopy(const float* __restrict__ in, 
float* __restrict__ out, 
int N, int stride) {
    // n = 1048576, stride = 2
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    if (idx < N) {
        // Loads from in[] with a stride, causing 
        // multiple memory segments to be fetched
        out[idx] = in[idx * stride];
    }
}

int main() {
    const int N = 1 << 20;
    const int stride = 2;

    float* h_in = nullptr;
    float* h_out = nullptr;
    cudaMallocHost(&h_in, N * stride * sizeof(float));
    cudaMallocHost(&h_out, N * sizeof(float));

    for (int i = 0; i < N * stride; ++i) {
        h_in[i] = static_cast<float>(i);
    }

    float *d_in, *d_out;
    cudaMalloc(&d_in,  N * stride * sizeof(float));
    cudaMalloc(&d_out, N * sizeof(float));
    cudaMemcpy(d_in, h_in, N * stride * sizeof(float), 
      cudaMemcpyHostToDevice);

    // Number of threads per block (multiple of 32)
    const int threadsPerBlock = 256; 

    // Number of blocks per grid
    const int blocksPerGrid = (N + threadsPerBlock - 1) /
      threadsPerBlock;

    uncoalescedCopy<<<blocksPerGrid, 
      threadsPerBlock>>>(d_in, d_out, N, stride);
    cudaDeviceSynchronize();

    cudaFree(d_in);
    cudaFree(d_out);
    cudaFreeHost(h_in);
    cudaFreeHost(h_out);
    return 0;
}

该 CUDA C++ kernel 的相邻 thread 从间隔大于 1 个元素的地址执行 global-memory load，因此一个 warp 触及的 sector 多于连续访问。与此同时，输出侧的 out[idx] 写入仍是连续且可合并的；分析时应将读写两条路径分开。

优化前示例（PyTorch）。在 PyTorch 中，可以用跨步 index 的 gather 构造类似情形：

import torch

def uncoalesced_copy(input_tensor, stride):
    # Flatten to 1D so we know exactly
    #   which dimension we're indexing
    flat_tensor = input_tensor.contiguous().view(-1)

    # Generate indices with a fixed stride to gather
    assert flat_tensor.numel() % stride == 0,"stride must divide tensor length"
    idx = torch.arange(0, flat_tensor.numel(), stride, 
        device=flat_tensor.device, dtype=torch.long)
    # index_select uses a gather kernel that issues uncoalesced loads
    return torch.index_select(flat_tensor, 0, idx)

# Usage
n, stride = 1 << 20, 2
inp = torch.arange(n * stride, device='cuda', 
                   dtype=torch.float32)
out = uncoalesced_copy(inp, stride)

这段 PyTorch 代码使用带跨步 index pattern 的 torch.index_select，底层 gather kernel 会按 index 加载数据。对于 FP32 输入，相邻索引对应的地址间隔是 stride * 4 bytes；stride 为 2 时，一个满 warp 的请求覆盖约 252 字节范围并触及约 8 个 32-byte sector。

这里仍是一条 warp memory instruction 中的 32 个 lane request，不应描述成必然生成“32 个独立 memory transaction”。每个 thread 从 inp 加载一个值，硬件会按所触及的 sector 合并请求；stride 2 通常约为 8 个 sector，而更大 stride 或随机访问才可能逐渐接近每个 lane 一个 sector。图 7-3展示合并、跨步与随机访问模式。

原书给出的示意测量中，非合并版本的每个 warp request 平均触及 8 个 32-byte sector。对于 stride 2 的 FP32 满 warp load，这与其覆盖约 256 字节的范围相符；但实际 sector 数还受首地址对齐、active lane、cache 和生成指令影响，不能由“跨两条 128-byte cache line”这一说法单独推导。

相对于连续 FP32 满 warp load 通常触及的 4 个 sector，8 个 sector 意味着约一半加载字节未被该指令使用。表中的 Nsight Compute DRAM throughput 约为 sustained peak 的 25%，只是概念示意；低吞吐并不能单独证明 memory pipeline “饥饿”，需要结合 kernel duration、requested throughput 和 stall 指标解释。

现在把 thread 改为读取连续元素，使每个 warp 用更少的 sector 覆盖相同数量的有效数据。

优化后示例（C++）：合并访问。移除 stride（或设为 1）后，每个 thread 复制一个相邻元素，硬件可将 warp request 合并到最少的 32-byte sector：

#include <cuda_runtime.h>
#include <iostream>

__global__ void coalescedCopy(const float* __restrict__ in,
                             float* __restrict__ out,
                             int n) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    if (idx < n) {
        // Contiguous load
        // Threads copy neighboring elements
        out[idx] = in[idx];
    }
}

int main() {
    const int n = 1 << 20;
    const size_t bytes = n * sizeof(float);

    // 1) Allocate pinned host memory
    float *h_in = nullptr, *h_out = nullptr;
    cudaMallocHost(&h_in,  bytes);  // page-locked host alloc
    cudaMallocHost(&h_out, bytes);

    // 2) Initialize input
    for (int i = 0; i < n; ++i) {
        h_in[i] = static_cast<float>(i);
    }

    // 3) Allocate device memory
    float *d_in = nullptr, *d_out = nullptr;
    cudaMalloc(&d_in,  bytes);
    cudaMalloc(&d_out, bytes);

    // 4) Copy to device
    cudaMemcpy(d_in, h_in, bytes, 
      cudaMemcpyHostToDevice);

    // 5) Launch kernel
    dim3 block(256);
    dim3 grid((n + block.x - 1) / block.x);
    coalescedCopy<<<grid, block>>>(d_in, d_out, n);
    cudaDeviceSynchronize();

    // 6) Copy back to host
    cudaMemcpy(h_out, d_out, bytes, 
      cudaMemcpyDeviceToHost);

    // 7) Clean up
    cudaFree(d_in);
    cudaFree(d_out);
    cudaFreeHost(h_in);
    cudaFreeHost(h_out);

    return 0;
}

这里省略合并访问的 PyTorch 实现。对于 contiguous tensor，可写成 out = inp.clone() 来获得内容相同的新 tensor。其底层 copy kernel 通常会选择适合输入布局、dtype 与对齐条件的实现，但不能把所有版本和形状下的 clone() 都等同于固定的 vectorized memory copy。

还可以使用采用默认 TorchInductor backend 的 torch.compile，在语义允许时消除冗余 copy 或融合相邻 operation。是否保留、消除或融合 clone() 取决于 aliasing、mutation、graph capture 和编译器版本，不能仅因它是 device-to-device copy 就断定其行为。对稳定 shape，可测试 autotuning（如 mode="max-autotune"），但它会增加编译成本，也不保证所有算子采用特定的合并或向量化 schedule。第 13 和第 14 章将深入介绍 PyTorch compiler。

在这组示意数据中，调整 data layout 并合并 global-memory access 后，DRAM throughput 从峰值的 25% 上升到 90%，约为原来的 3.6 倍；kernel 执行时间从 4.8 ms 降至 1.3 ms，约改善 3.7 倍。这些数值只说明可能的趋势，不能作为该代码在任意 Blackwell GPU 上的预期结果。

示意的 Global Memory Load Efficiency 从 23% 上升到 99%，表示实际传输字节中更大比例是所请求的数据；同时 Average Sectors per Request 降至约 4.0。

只有在本例的访问宽度和 active mask 下，接近 4.0 才对应满 warp 各加载一个 FP32 值的理想连续访问：32 个 4-byte 值共 128 字节，覆盖 4 个 32-byte sector。对 FP64、vector load、部分 warp 或其他指令，理想 sector/request 值会不同。

对于满 warp 的 scalar load，极端分散访问可能接近 32 个 sector，因为每个 active lane 都可能落在不同的 32-byte sector。不能一概认为“高于 4.0 就是错误”，而应先根据每 lane 字节数和 active lane 数计算理想值，再比较 requested bytes 与 sector bytes。

本例约 4.0 sector/request，与连续 FP32 满 warp load 的理想覆盖一致。示意表中 SM Active 从 62% 升至 99%，但 SM Active 只表示至少有一个 warp active 的周期比例或相应版本定义，并不直接等同于计算单元利用率；应结合 duration 与其他 throughput/stall 指标判断。

总之，让相邻 thread 访问相邻地址，可以减少完成同一有效 load 所需的 sector 数，提高 Global Memory Load Efficiency。它可能改善 kernel 时间和 SM 活跃度，但结果取决于 cache、occupancy、指令组合及其他瓶颈。

至此可以看到，coalescing 优化的是一个 warp memory instruction 中 lane address 到 memory sector 的映射。32 个 thread 各自请求一个 4-byte 值，并不意味着硬件先执行 32 个独立 DRAM read 再把它们“拼接”为 128-byte transaction；coalescer 会依据地址直接生成所需 sector request。

下一节将讨论 vectorized memory access：让每个 thread 用一条更宽的 load/store instruction 获取对齐数据，例如 16-byte 的 float4。向量化主要减少动态指令数和地址计算开销；一个 warp 搬运的数据量也随每 thread 宽度增加，因此不能把它描述为把同样的数据从“32 个 transaction”固定变成“四个 128-byte transaction”。下面将介绍如何使用 CUDA 内置 vector type，并分析其对齐与边界条件。

向量化 memory access

Memory coalescing 是 NVIDIA GPU 在运行时根据 lane address 完成的硬件行为；vectorized memory access 则是在编译时让一条 load/store instruction 为每个 thread 显式搬运多个连续元素，例如使用 float4 搬运 16 字节。它主要减少完成同等数据搬运所需的动态指令数和地址计算，不存在需要额外消除的“拼接开销”。

高效的 global-memory access要求 warp 的 lane address 尽量覆盖连续、对齐的 sector。32 个 thread 各读取一个 4-byte float 时，coalescer 会直接生成覆盖这 128 字节所需的 sector request，并非先发出 32 个独立 DRAM request 再拼成一条 cache line。

在理想合并情形下，一个 warp 读取 32 个 4-byte word，并且访问范围按 128 字节对齐时，恰好覆盖 4 个 32-byte sector。Nsight Compute 的 sector 与 requested/actual byte 指标可揭示额外流量；对本访问宽度而言，未对齐、跨步或分散访问可能使 sector/request 高于 4.0，并降低 Global Memory Load Efficiency。其他 per-thread 宽度对应不同的理想 sector 数。

若 kernel 对同一连续数组逐元素执行多条 scalar load/store，可尝试让每个 thread 处理一个更宽且自然对齐的 vector。CUDA 内置 float4 将 4 个 4-byte float 组成一个大小与对齐要求均为 16 字节的类型。下面给出简化示意：

// Example of a custom float4 for illustration purposes.
// Note: it's recommended to use the built-in CUDA float4 type.
// Note: if N is not divisible by 4, handle the last N % 4 elements 
// (e.g., a short scalar cleanup) or assert divisibility in host code. The 
// input and output pointers must be 16-byte aligned for float4 loads/stores.
struct my_float4 {
    float x;  // 4 bytes
    float y;  // 4 bytes
    float z;  // 4 bytes
    float w;  // 4 bytes
};

当 warp 的 32 个 thread 各执行一次 float4 load 时，共请求 32 × 16 = 512 字节。若 lane address 连续且整体对齐，该范围覆盖 16 个 32-byte sector，也可按 4 个连续的 128-byte 范围理解。这里应报告每条 warp instruction 约 16 sector，而不是沿用 scalar FP32 示例的 4 sector/request；“每个 128-byte 范围含 4 个 sector”与 profiler 的“每条 request 含多少 sector”不是同一个分母。

若原代码每个 thread 用 4 条 scalar instruction 搬运 4 个相邻 float，改用一次 float4 load 可把这部分 load instruction 数降至四分之一。Coalescing efficiency 仍由所有 lane 的地址决定；向量化本身不会把理想 sector/request 固定为 4.0。

PyTorch compiler 等高层 GPU compiler在能够证明 alignment、contiguity、边界与 aliasing 条件时，可能生成 vectorized memory operation。与 vector width 匹配的 per-thread tile 有助于编译器选择这种 schedule，但实际代码生成必须检查 IR/PTX/SASS 或 profiler，不能假定 framework 一定减少 memory transaction。

如果原访问既未合并又能通过重新分组而改善，vectorization 与 layout 调整可能同时提高 load efficiency；但对本来已经连续合并的 scalar copy，向量化通常不会把 sector efficiency 从低值自动提升到接近 100%。更宽的 warp request 会访问相应更多的 sector。

Vectorized load 可减少每字节对应的 memory instruction 数，并可能提高有效带宽。指针必须满足所用 vector type/instruction 的 alignment 要求。CUDA Programming Guide 说明 runtime/driver allocation（如 cudaMalloc）返回的基址至少按 256 字节对齐，但切片偏移和自定义 allocator 仍可能破坏后续地址的对齐。

该基址足以满足 allocation 起点处 16-byte 或 32-byte 的对齐，但加上 element offset 后，只有字节偏移是 vector alignment 的整数倍时仍保持对齐。下面的 cast 只是向 compiler 表达预期类型，并不会在运行时修复或验证指针：

auto ptr4 = reinterpret_cast<const float4*>(ptr);

cast 前应确认指针值按 16 字节（4 个 float）对齐。虽然 cudaMalloc() 返回至少 256-byte aligned 的基址，但若 element offset 不是 4 个 float 的倍数，地址便不再满足 float4 alignment。尾部不足一个 vector 的元素还需要单独处理；否则示例中的 N/4 thread 会漏掉余数。

若 base address 与每 thread stride 都按 32 字节对齐，每个 thread 每轮读取 32 字节，则满 warp 共请求 1,024 字节，对应 32 个 32-byte sector，也可分为 8 个连续的 128-byte 范围。源码最终编译为两条 16-byte instruction 还是一条 32-byte instruction，取决于目标 compute capability、PTX/SASS instruction、数据类型和 compiler 证明；不能只由“Blackwell”这一名称保证。正确对齐可避免单个 lane vector 跨越额外边界。

截至原书写作时，CUDA的传统内置 vector type 中没有由 8 个 float32 组成的通用 `float8`。原文件名 <vector_types.h> 中还混入了零宽字符，译文已清除。可以定义含 8 个 float 的 struct，并以两个 float4 load 显式搬运；也可用 alignas(32) 表达 32-byte type alignment。`alignas` 只约束合法对象地址，是否生成单条 32-byte global load 必须查看目标 Blackwell 的实际 SASS，不能由 cast 或 alignment 单独保证。Hopper 与 Blackwell上的代码生成也会随 Toolkit 与编译选项变化。

每 thread 读取 32 字节（8 个 float × 4 byte）时，满 warp 搬运 1,024 字节，即 32 个 sector 或 8 个 128-byte 范围。每 thread 读取 16 字节（一个 float4）时，满 warp 搬运 512 字节，即 16 个 sector 或 4 个 128-byte 范围。base pointer 与 per-thread stride 的自然对齐有助于避免 split sector。若确实使用要求 32-byte alignment 的 256-bit type/instruction，就必须满足该对齐；但“对齐”是正确且高效代码的必要条件之一，不等于必然达到 peak throughput。

下面用一个简单 vector copy kernel 对比 scalar 与 vectorized memory access。需要注意，两版代码都采用连续索引，因此 scalar 版已经具备良好的 coalescing。

优化前示例（C++）：scalar copy。每个 thread 复制一个 float：

#include <cuda_runtime.h>

__global__ void copyScalar(
const float* __restrict__ in, 
float* __restrict__ out, int N) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    if (idx < N) {
        // Scalar load: 4-byte copy per thread
        out[idx] = in[idx];
    }
}

int main() {
    const int N = 1 << 20;

    float* h_in = nullptr;
    float* h_out = nullptr;
    cudaMallocHost(&h_in, N * sizeof(float));
    cudaMallocHost(&h_out, N * sizeof(float));

    for (int i = 0; i < N; ++i) h_in[i] = float(i);

    float *d_in, *d_out;
    cudaMalloc(&d_in, N * sizeof(float));
    cudaMalloc(&d_out, N * sizeof(float));
    cudaMemcpy(d_in, h_in, N * sizeof(float), cudaMemcpyHostToDevice);

    dim3 block(256), grid((N + 255) / 256);
    copyScalar<<<grid, block>>>(d_in, d_out, N);
    cudaDeviceSynchronize();

    cudaFree(d_in); cudaFree(d_out);
    cudaFreeHost(h_in); 
    cudaFreeHost(h_out);
    return 0;
}

对于连续、对齐的 4-byte scalar load，满 warp 的一条 instruction 请求 128 字节并覆盖 4 个 sector；轻微错位通常会多触及一个 sector。使用 float4 后，每条 warp instruction 搬运的数据增至 512 字节并覆盖 16 个 sector，但每个 thread 可用一条 vector instruction 代替 4 条 scalar instruction 来完成相同的总元素数。下面改用 vector load。

优化后示例（C++）：vectorized copy。每个 thread 复制一个 float4（16 字节）：

#include <cuda_runtime.h>

// 16-byte (128-bit) vector copy: one float4 per thread
static_assert(alignof(float4) == 16, "float4 alignment must be 16 bytes");
__global__ void copyVector16B(const float4* __restrict__ in,
                              float4* __restrict__ out,
                              int N4)  // number of float4 elements
{
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    if (idx < N4) {
        // Per-thread 16B load+store.
        // On sm_90, NVCC emits ld.global.v4.f32 / st.global.v4.f32.
        // for 16-byte vector loads and stores
        // On sm_90 (Hopper) (Blackwell), NVCC emits
        // ld.global.v8.f32 and st.global.v8.f32 for 32-byte aligned data
        out[idx] = in[idx];
    }
}

int main() {
    const int N  = 1 << 20;   // total number of floats
    const int N4 = N / 4;     // total number of float4s (16B chunks)

    float4 *d_in = nullptr, *d_out = nullptr;
    cudaMalloc(&d_in,  N4 * sizeof(float4));   // >=256B aligned
    cudaMalloc(&d_out, N4 * sizeof(float4));

    dim3 block(256);
    dim3 grid((N4 + block.x - 1) / block.x);
    copyVector16B<<<grid, block>>>(d_in, d_out, N4);
    cudaDeviceSynchronize();

    cudaFree(d_in);
    cudaFree(d_out);
    return 0;
}

这里使用 <cuda_runtime.h> 中的 CUDA 内置 float4 type，并启动 N/4 个 thread，使每个 thread 复制一个 float4（16 字节），即 4 个 float；满 warp 共处理 128 个 float，覆盖 16 个 sector。cudaMalloc 返回至少 256-byte aligned 的基址，满足 float4 要求；但 N 必须能被 4 整除或另行处理 tail，指针偏移也必须保持对齐。misaligned reinterpret cast 会产生未定义或不受支持的访问，而不仅仅是“失去 vectorization”。下面的代码尝试展示 32-byte aggregate 路径，但是否生成单条 Blackwell 32-byte instruction 仍需检查编译结果：

// --- Blackwell-only variant: 32-byte per-thread vector copy 
// (PTX: ld.global.v8.f32)
// Requires 32B alignment.
#include <cuda_runtime.h>

// Proof of 32-byte alignment
static_assert(alignof(float8) == 32, "float8 alignment must be 32 bytes");
struct alignas(32) float8 { float v[8]; };

__global__ void copyVector32B(const float8* __restrict__ in,
                              float8* __restrict__ out, int N8) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    if (idx < N8) {
        // Per-thread 32B load+store
        // NVCC emits ld.global.v8.f32/st.global.v8.f32 on sm_100
        out[idx] = in[idx];
    }
}

int main() {
    const int N = 1 << 20;
    const int N8 = N / 8;

    float8 *d_in, *d_out;
    // cudaMalloc returns pointers aligned to ≥256 bytes
    // This will allow the compiler to emit
    // optimized ld.global.v8.f32 and st.global.v8.f32 instructions
    cudaMalloc(&d_in,  N8 * sizeof(float8));  
    cudaMalloc(&d_out, N8 * sizeof(float8));

    dim3 block(256), grid((N8 + block.x - 1) / block.x);
    copyVector32B<<<grid, block>>>(d_in, d_out, N8);
    cudaDeviceSynchronize();

    cudaFree(d_in); cudaFree(d_out);
    return 0;
}

对 reshaped tensor 调用 clone() 会执行连续 copy，而前面的 Python loop 会启动大量逐元素 operation。`view(-1, 4)` 本身只是改变 shape metadata，不会要求 PyTorch copy kernel 按 float4 发射，也不会改变底层 contiguous storage；是否向量化由实现和编译结果决定。因此该 PyTorch 对照主要体现批量 operation 与 Python loop 的差异，不能用于量化 CUDA scalar 与 vector instruction 的收益。表 7-2保留原书示意数据，但不应视为这些代码的可复现结果。

原文将 Blackwell/CUDA 13 概括为把每 thread vector load/store 从 Hopper 的 16 字节翻倍到 32 字节。更准确地说，特定目标架构、类型和指令路径可能支持 32-byte operation，但源码是否生成单条相应 SASS instruction 取决于 compiler 能否证明 alignment 与其他合法性条件；否则可能拆成较窄 instruction。指令数增加可能带来开销，但在 memory-bandwidth-bound copy 中未必按比例降低性能。

使用正确对齐的 float4 vector load 时，每个 thread 每条 instruction 搬运 16 字节。它可能减少 instruction overhead，但原 scalar C++ kernel 已是连续合并访问，因此不能据此断言 memory bandwidth utilization 必然出现表 7-2所示幅度的改善。

表中的 average sectors/request 从 31.8 降至 4.0 也与本例的 request 宽度不相容：满 warp 的 float4 instruction 请求 512 字节，理想情况下覆盖 16 个 sector，而非 4 个。若 metric 按不同 instruction 或不同分组统计，必须给出准确 metric 名称与 source counter 后才能比较。

在合法且对齐的场景中，以一条 vector load 替代 4 条 scalar load 可以减少 instruction 数；若 scalar 访问原本分散，配套的 layout 改动还可提高 sector efficiency。但对已经合并的 copy，load efficiency 通常不会仅因向量化从 28% 跳到 97%，实际收益应以同等数据量、同一 kernel 语义和同一测量方法验证。

Vectorization 主要减少 instruction count；coalescing 与 alignment 主要减少完成给定 requested bytes 所需的额外 sector。两类效果应分别测量。

下面对比上一节的 coalesced global-memory access 与本节的 vectorized memory access。Coalescing 关注 warp 内各 lane 的地址能否由尽量少的 sector 覆盖；vectorization 关注每个 thread 能否用较少的宽 instruction 搬运多个相邻元素。表 7-3概括两者差异。

原文称 Blackwell 与 CUDA 13 之前每 thread global-memory vector load 一律限于 16 字节，并称两者新增通用 32-byte load/store instruction 与 type。实际可用宽度需按 compute capability、PTX ISA、SASS 与 CUDA header 中的具体 type 核对；CUDA Toolkit 版本本身不能让旧架构获得新硬件指令。

若目标架构与 toolchain 确实提供可用的 32-byte type/instruction，并且 profile 显示 instruction overhead 有意义，可以测试其用于 8-float aggregate；同时必须满足 alignment、tail 和 aliasing 条件。

普通自定义 8-float aggregate 可能被 compiler 拆为多条较窄 load。仅添加 32-byte alignment 也不保证生成单条 32-byte instruction，应检查 PTX/SASS，并以执行时间验证。

无论 per-thread instruction 宽度如何，coalescing 都应按 lane request 覆盖的 32-byte sector 分析。32 个 thread 各搬运 32 B 时总量为 1,024 B，对齐连续访问覆盖 32 个 sector；各搬运 16 B 时总量为 512 B，覆盖 16 个 sector。这里的算术与 GPU 型号无关，区别在于目标架构是否能用所期望的 instruction 数实现这些 per-thread access。正确对齐可达到 sector efficiency，但不自动保证整体性能最优。

使用 shared memory 进行 tiling 与数据复用

常见性能问题之一是反复从 global memory 读取相同数据。Tiling 将数据分块加载到更快的片上 shared memory，并让 block 内多个 thread 在同步与生命周期允许的范围内复用这些 tile。

例如，在朴素的 N × N matrix multiplication 中，每个 output element 都沿 K 维读取一行 A 与一列 B。若不考虑 cache，A[i,k] 会被同一输出行的 N 个列结果重复使用，B[k,j] 会被同一输出列的 N 个行结果重复使用，因此每个输入元素在整个计算中最多有 N 次逻辑读取，而不是原文所说“A 的每个元素对应 B 的每一行”。Blackwell 具有很高的计算吞吐，若复用无法被 cache 捕获，冗余内存流量会限制 SM 获得操作数的速度。

Tiling 让每个 thread block 将 A 与 B 的小型子矩阵（tile）协作加载到 shared memory，再由多个 thread 为多次 multiply-accumulate 复用。这里的“只加载一次”是指每个 block、每个 K tile 内的逻辑加载；同一输入 tile 仍可能被计算不同 output tile 的多个 block 分别加载。下面使用 32 × 32 tile 说明。

block 内的 thread 可以协作将 tile 载入 shared memory，再调用 __syncthreads()，确保所有参与 thread 完成写入后才开始读取。随后各 thread 使用 shared-memory 数据并行计算，使一次 global load 服务多次运算。示例按连续列安排 tile load，因此每个满 warp 各读取一行 32 个 FP32 值，覆盖连续 128 字节和 4 个 32-byte sector。

在每个 block 的 tile iteration 中，把所需元素从 DRAM载入 shared memory 一次并多次复用，可以减少相对于朴素实现的 global-memory traffic。下面以 N × N matrix multiplication 为例，先看朴素实现。

优化前示例（CUDA C++）：朴素 matrix multiplication。每个 thread 计算结果矩阵 C 的一个元素，并为该 output 沿 K 维读取 A 的一行和 B 的一列：

#include <cuda_runtime.h>
#include <iostream>

__global__ void naiveMatMul(const float* A, const float* B, float* C, int N) {
    int row = blockIdx.y * blockDim.y + threadIdx.y;
    int col = blockIdx.x * blockDim.x + threadIdx.x;
    if (row < N && col < N) {
        float sum = 0.0f;
        for (int k = 0; k < N; ++k) {
            // Each thread loads A[row, k] and B[k, col] 
            // from global memory for every k.
            // This is very memory heavy.
            sum += A[row * N + k] * B[k * N + col];
        }
        C[row * N + col] = sum;
    }
}

int main() {
    const int N = 1024;
    size_t bytes = N * N * sizeof(float);

    float* h_A = nullptr;
    float* h_B = nullptr;
    float* h_C = nullptr;
    cudaMallocHost(&h_A, N*N * sizeof(float));
    cudaMallocHost(&h_B, N*N * sizeof(float));
    cudaMallocHost(&h_C, N*N * sizeof(float));

    for (int i = 0; i < N*N; ++i) { h_A[i] = 1.0f; h_B[i] = 1.0f; }

    float *d_A, *d_B, *d_C;
    cudaMalloc(&d_A, bytes);
    cudaMalloc(&d_B, bytes);
    cudaMalloc(&d_C, bytes);
    cudaMemcpy(d_A, h_A, bytes, cudaMemcpyHostToDevice);
    cudaMemcpy(d_B, h_B, bytes, cudaMemcpyHostToDevice);

    dim3 block(32, 32);
    dim3 grid((N + 31) / 32, (N + 31) / 32);
    naiveMatMul<<<grid, block>>>(d_A, d_B, d_C, N);
    cudaDeviceSynchronize();

    cudaFree(d_A); 
    cudaFree(d_B); 
    cudaFree(d_C);
    cudaFreeHost(h_A); 
    cudaFreeHost(h_B); 
    cudaFreeHost(h_C);
    return 0;
}

这个 CUDA C++ kernel 在内层循环的每次乘法中发出 global-memory load。每个 thread 读取 A[row, k] 与 B[k, col]，并遍历每个 k。相邻 thread 在同一 k 上读取相同的 A 值，硬件可通过 warp broadcast/cache 服务部分复用；它们读取的 B 值则沿 col 连续并可合并。尽管如此，显式 shared-memory tiling 通常能提供更可控的跨 thread 复用。是否为 memory-bound、SM utilization 多低，必须通过 profile 判定。下面是朴素 PyTorch 版本：

import torch

def naive_matmul(A, B):
    N = A.size(0)
    C = torch.zeros((N, N), device='cuda')
    for i in range(N):
        for j in range(N):
            # Each dot product loads A[i,:] B[:,j] from global memory repeatedly
            C[i, j] = (A[i, :] * B[:, j]).sum()
    return C

# Usage
N = 1024
A = torch.ones((N, N), device='cuda', dtype=torch.float32)
B = torch.ones((N, N), device='cuda', dtype=torch.float32)
C = naive_matmul(A, B)

这个 PyTorch 实现使用嵌套 Python loop。每个 output element 都执行一次 tensor slice、elementwise multiply 与 reduction，产生大量 Python dispatch 和 GPU kernel launch；其慢速主要不只来自重复 global load，也来自极细粒度 operation 与同步/调度开销。因此它不能忠实模拟单个朴素 CUDA kernel 的 memory-bound 行为。

这段 PyTorch 代码故意采用极慢的逐 output Python loop，用于说明缺少批量化的反例，不适合作为 tiling benchmark。实际代码应使用 PyTorch 已优化的 matrix-multiplication operator。

接下来应用 tiling，将矩阵划分为 32 × 32 tile。该示例用 32 × 32 thread block，每个 warp 的 32 个 thread 协作加载 tile 的一行。两个 FP32 input tile 共占 2 × 32 × 32 × 4 = 8 KB shared memory；但 1,024-thread block 已达到每 block thread 上限，未必是所有架构或 GEMM 的最佳 tile/thread mapping。

每个 thread block 在一次 K-tile iteration 中将一个 32 × 32 A tile 和一个 32 × 32 B tile 载入 shared memory，并让每个 thread 为一个 output 累加 32 次乘加。同一 block 内，每个载入值最多被 32 个 output 复用；相比不利用 cache 的逻辑读取次数，这可将该层级的输入流量降低约 32 倍，但 HBM 实际流量还受 L1/L2 cache 与跨 block 重复加载影响。下面是使用 shared memory 缓存 tile 的版本：

#include <cuda_runtime.h>
#include <iostream>
#define TILE_SIZE 32

__global__ void tiledMatMul(const float* A, const float* B, float* C, int N) {
    __shared__ float sA[TILE_SIZE][TILE_SIZE];
    __shared__ float sB[TILE_SIZE][TILE_SIZE];

    int row = blockIdx.y * TILE_SIZE + threadIdx.y;
    int col = blockIdx.x * TILE_SIZE + threadIdx.x;
    float sum = 0.0f;

    // compute partial results using the tile
    // in shared memory
    for (int t = 0; t < N; t += TILE_SIZE) {
        // Cooperative load of a tile of A and B into shared memory
        // Load tile A with boundary check
        if (row < N && (t + threadIdx.x) < N) {
            sA[threadIdx.y][threadIdx.x] = A[row * N + t + threadIdx.x];
        } else {
            sA[threadIdx.y][threadIdx.x] = 0.0f;
        }

        // Load tile B with boundary check
        if ((t + threadIdx.y) < N && col < N) {
            sB[threadIdx.y][threadIdx.x] = B[(t + threadIdx.y) * N + col];
        } else {
            sB[threadIdx.y][threadIdx.x] = 0.0f;
        }

        // We will optimize this later to use a 
        // thread-block-scoped cooperative-groups barrier
        __syncthreads();

        // Compute using the tile loaded in shared memory
        for (int k = 0; k < TILE_SIZE; ++k) {
            sum += sA[threadIdx.y][k] * sB[k][threadIdx.x];
        }
        // We will optimize this later to use a 
        // thread-block-scoped cooperative-groups barrier
        __syncthreads();
    }

    if (row < N && col < N) {
        C[row * N + col] = sum;
    }
}

int main() {
    const int N = 1024;
    size_t bytes = N * N * sizeof(float);

    float* h_A = nullptr;
    float* h_B = nullptr;
    float* h_C = nullptr;
    cudaMallocHost(&h_A, N*N * sizeof(float));
    cudaMallocHost(&h_B, N*N * sizeof(float));
    cudaMallocHost(&h_C, N*N * sizeof(float));

    for (int i = 0; i < N*N; ++i) { h_A[i] = 1.0f; h_B[i] = 1.0f; }

    float *d_A, *d_B, *d_C;
    cudaMalloc(&d_A, bytes);
    cudaMalloc(&d_B, bytes);
    cudaMalloc(&d_C, bytes);
    cudaMemcpy(d_A, h_A, bytes, cudaMemcpyHostToDevice);
    cudaMemcpy(d_B, h_B, bytes, cudaMemcpyHostToDevice);

    dim3 block(TILE_SIZE, TILE_SIZE);
    dim3 grid((N + TILE_SIZE - 1) / TILE_SIZE, (N + TILE_SIZE - 1) / TILE_SIZE);
    tiledMatMul<<<grid, block>>>(d_A, d_B, d_C, N);

    // synchronize the kernel with the device 
    // for timing accuracy
    cudaDeviceSynchronize();

    cudaFree(d_A); 
    cudaFree(d_B); 
    cudaFree(d_C);
    cudaFreeHost(h_A); 
    cudaFreeHost(h_B); 
    cudaFreeHost(h_C);

    return 0;
}

在这个 tiled kernel 中，每个 block 协作把 A 的 32 × 32 tile 载入 sA，把 B 的 tile 载入 sB。加载位于 K-tile loop 开头，随后以 __syncthreads() 确保 tile 对 block 内所有 thread 可见。该示例假设 N 是 32 的倍数；否则最后一个 tile 的全局读取会越界，必须增加边界检查与 zero fill。

随后 block 使用 shared-memory tile 计算 32 × 32 个 output，每个 thread 的内层循环遍历 tile 内 32 个 k。在 block 范围内，每个 A 值被 32 个不同列 output 使用，每个 B 值被 32 个不同行 output 使用，因此相对于无 cache 的逻辑访问可获得最高约 32 倍复用；这不等于所有元素的实测 DRAM read 必然精确减少 32 倍。

完成全部 K tile 后，每个 thread 将累加结果写入 C。原文随后声称“每 thread global-memory access 减少 8 倍”，但没有给出与 tile size、N 或 load 计数一致的推导；这里应直接按每 block input load 与每 output FLOP 计算，或使用 profiler 的 sector/byte counter 实测。

这些示例关注 memory access pattern，使用普通 FP32 CUDA core instruction，而非低精度 Tensor Core path。第 9 章将介绍 16-bit、8-bit、4-bit 等低精度计算；其性能收益还取决于数据类型、精度要求和是否调用相应 Tensor Core instruction。

下面的 PyTorch 版本在 Python 中手动遍历 output tile，并对每对 K tile 调用 torch.mm。CUDA 上的 torch.mm 通常通过 ATen 调度到 cuBLAS/cuBLASLt 或其他选定 backend；不能笼统说它同时“使用 cuBLAS 和 CUTLASS”。每次小 tile 调用本身已经执行内部 tiling，并且 Python loop 会引入大量 launch 与临时 tensor 累加开销，因此该示例用于表达 block GEMM 数学分解，不代表高性能实现：

import torch

def tiled_matmul(A, B, tile_size=32):
    N = A.size(0)
    C = torch.zeros((N, N), device='cuda')
    for i in range(0, N, tile_size):
        for j in range(0, N, tile_size):
            C_block = torch.zeros((tile_size, tile_size), device='cuda')
            for k in range(0, N, tile_size):
                A_block = A[i:i+tile_size, k:k+tile_size]
                B_block = B[k:k+tile_size, j:j+tile_size]
                # torch.mm uses an optimized kernel (likely tiling internally)
                C_block += torch.mm(A_block, B_block)
            C[i:i+tile_size, j:j+tile_size] = C_block
    return C

# Usage
N = 1024
A = torch.ones((N, N), device='cuda', dtype=torch.float32)
B = torch.ones((N, N), device='cuda', dtype=torch.float32)
C = tiled_matmul(A, B)

原文称 32 × 32 tile 会因 warp 内 thread “访问同一列”而发生 shared-memory bank conflict，但本 CUDA kernel 的计算访问是 sA[ty][k] 与 sB[k][tx]：前者对同一 warp 是同地址 broadcast，后者随 tx 访问连续 bank，通常不会产生该断言所述的 32-way conflict。Padding 到 33 列常用于 naive transpose 等列访问模式，是否需要应按实际 lane address 与 bank width 分析。下一节将详细讨论 bank conflict。

表中的 achieved occupancy 从 42% 增到 89% 也不能解释为“stall 更少所以 resident warp 更多”。Occupancy 表示 active/resident warp 相对于架构上限的比例，主要受 block、register、shared memory 和调度状态影响；warp 是否因 memory stall 无法 issue 是另一类指标。需要核对具体 Nsight metric 才能解释变化。

引入 shared-memory tiling 会增加 block 的 shared-memory allocation，并可能改变每 thread register 使用；资源没有超过硬件上限只说明 kernel 可以 launch，不保证更高 occupancy。原文以每 SM 65,536 个 32-bit register、每 thread 最多 255 个 register 概括所有 Blackwell，但具体限制随 compute capability 与型号而变，并且 compiler allocation granularity 也会影响驻留。

即使架构允许每 thread 最多 255 个 register，也不能仅由源码确认该 tiled kernel 没有 spilling。应查看 compiler 的 `ptxas` register/spill 报告或 Nsight Compute；接近 per-thread 上限通常还会严重限制 resident warp。

原书用持续 FLOP rate 除以平均 DRAM bandwidth 估算算术强度：naive 版本 15 GFLOP/s ÷ 10 GB/s = 1.5 FLOP/byte；tiled 版本 170 GFLOP/s ÷ 21 GB/s ≈ 8.1 FLOP/byte，算术成立。但这里 tiled 版本的绝对 DRAM bandwidth 反而是 naive 的 2.1 倍，与表中“峰值百分比从 90% 降到 25%”在同一设备和定义下不相容。两组数字不能混作同一次 benchmark；可靠方法是用实际 FLOP 与 DRAM byte counter 按同一 kernel invocation 计算。

进一步把 output tile 增大到 64 × 64 或 128 × 128，可能提高复用并减少单位 FLOP 的片外流量，但也会增加 shared memory、register、同步和 instruction-level work。资源增加可能减少每个 SM 的 resident block 数。

例如，若某个目标 Blackwell 配置允许每 SM 约 228 KB shared memory，64 × 64 的单个 FP32 tile 占 16 KB（64 × 64 × 4 = 16,384 byte），A 与 B 两个 tile 合计 32 KB；double buffering 则可能再翻倍。除了 shared memory，还必须预算每 thread register 和 block/thread 限制。

原文继续假设每 SM 有 64K 个 32-bit register、每 thread 最多 255 个 register，并用 32 × 32 thread block（1,024 thread）计算 64 × 64 output tile，让每个 thread 负责 2 × 2 subtile、产生 4 个 output。这只是一个 mapping 示例，具体架构限制应查询目标 device attribute。

原文手工估算每 thread 需要 4 个 accumulator register、2 个 A 值、2 个 B 值，以及约 4 个 loop/index/address register，共约 12 个。真实 compiler allocation 还包含 pointer、predicate、temporary、unrolling 和 instruction scheduling 所需 register，不能由源码变量数可靠推断。

按这一简化假设，12 register/thread × 1,024 thread/block = 12,288 register/block；65,536 ÷ 12,288 的整数部分为 5。但 1,024-thread block 每个包含 32 个 warp，若目标 SM 最多驻留 2,048 thread/64 warp，则 thread/warp limit 会先把 resident block 限为 2。实际还要考虑 register allocation granularity、shared memory、block 上限与架构差异。

若 kernel 因 double buffering、vectorized load 等使用更多 register，可结合 compiler 输出、cudaOccupancyMaxPotentialBlockSize 系列 API 与 Nsight Compute occupancy report 重新计算。该 API 给出基于资源约束的 launch 建议，不替代实际 throughput benchmark。

原文又无推导地把同一 64 × 64 tile 改为 22 register/thread，即 22 × 1,024 = 22,528 register/block。65,536 个 register 理论上仍能容纳 2 个这样的 block（共 45,056），而第 3 个会超限；同时两个 block 已达到假设的 2,048-thread 上限。因此这里不是“occupancy 只有 2,048 thread”，而是在该假设下达到 100% thread/warp occupancy，只是 resident block 数为 2。原文所称每 SM 最多 16 block 也并非所有 Blackwell 型号的统一值。

较大 tile 如果降低 resident warp，可能削弱 latency hiding，但 occupancy 降低不一定损害性能：更高数据复用、较少 instruction 或更好的 ILP 可能抵消它。Tile dimension 必须满足 shared-memory、register、thread/block 等限制，并以 kernel 时间和端到端吞吐选择。

对于假设有约 228 KB 可分配 shared memory 的 GPU，64 × 64 FP32 input tile 每个约 16 KB，通常能够容纳。但 tile 边长翻倍时，tile 存储量增为 4 倍，而经典方形 GEMM 的 FLOP/byte 与每个输入元素的 block 内复用因子大致随边长线性增长，并非“复用因子平方”。因此会出现资源权衡与收益递减。

应测试不同 tile dimension，在片上复用、并行度、register、shared memory、bank mapping 与 pipeline stage 之间取舍。32 × 32 可作为教学起点，但真实高性能 GEMM 往往采用不同的 thread-block/warp/instruction tile 组合，不能把它当作通用默认最优值。

CUTLASS 等库提供 profiler，可在给定 operation、dtype、layout、shape 和硬件上搜索候选 kernel。它能找出候选集合中的较优配置，而不是证明跨所有输入的唯一“最优 tile size”。

总之，我们把只显式访问 global memory 的朴素 matrix multiplication 改为使用 shared memory 的 tiled 实现，从而在 block 内协作复用数据，并提高相对于片外流量的算术强度。CUDA C++ 示例直接展示这一机制；PyTorch 手写分块示例则调用了现成的 torch.mm，其行为与性能不能归因于同一层的手写 tiling。

高性能 GPU library 确实广泛使用多层 tiling，但实现远比上述 32 × 32 教学 kernel 复杂。例如，NVIDIA CUTLASS 提供构建 GEMM 的模板化组件，在 thread block、warp、instruction 等层级组织 tile，并利用 register、shared memory、异步 copy 和 Tensor Core pipeline 计算 partial result。

cuBLAS 与 cuDNN 的许多 kernel 也使用 blocking/tiling，但算法选择会随 operation、shape、dtype、layout 与硬件而变化，不能保证所有调用都接近 peak。NVIDIA 在 2025 年发布了 Python 风格的 cuTile 编程模型，使程序员以 tile 为中心描述计算；相关编译栈使用 tile-level IR。具体 API、IR 名称与可用性仍应以当前 CUDA/cuTile 文档为准。

其他高性能工具也封装 tiling pattern。CUTLASS 的 C++/Python 接口和 profiler 提供 tile abstraction 与配置搜索；TorchInductor 可根据 graph、shape 和 backend 生成 tiled kernel，常见 GPU codegen 路径会使用 Triton，但也可能调用 external kernel/library。它们降低了手写 boilerplate 的需求，不过仍需 profile 生成代码。

核心思想是在返回 DRAM 之前，尽可能在 register/shared memory/cache 中有效复用数据，同时不超过片上资源预算。优先使用经过验证的 library kernel；编写自定义 kernel 时，也可参考这些实现的 tiling 与 pipeline pattern。

例如，PyTorch 的 torch.mm 或直接调用 cublasSgemm 通常会选择包含某种 blocking、coalescing 与架构专用优化的 kernel，但不一定“恰好”采用本节的 32 × 32 shared-memory 方案。前面的 PyTorch 示例也没有提供能证明相同收益的实测。

生产代码通常应先采用 cuBLAS、PyTorch torch.matmul 等高性能 operator，并针对实际 shape、dtype 和精度设置 benchmark。直接使用 torch.mm 或 torch.matmul 往往优于 Python 手写分块，但 view、batch、broadcast 与 backend 选择会影响最终 kernel。

即使主要复用现有 tiling library 与 framework，理解其基本机制仍有助于诊断性能问题，并在通用实现不能覆盖特殊数据布局、融合或数值需求时编写 custom kernel。若改进具有通用价值，也可以向相关开源项目反馈或贡献。

Shared-memory bank conflict 取决于同一 warp 的 lane 如何映射到 bank，而不是仅由 tile 为 32 × 32 决定。本节 GEMM 访问通常使用 broadcast 与连续 bank；下一节将通过确实存在列式访问冲突的模式说明问题及优化方法。

避免 shared-memory bank conflict

在本节讨论的现代 NVIDIA GPU（包括相应 Blackwell 配置）上，shared memory 通常组织为 32 个 bank，常见 32-bit word 访问可按 4-byte bank 单元理解，即 bank index 对 32 循环（mod 32）。若 warp lane 的地址相隔 128 B（32 float × 4 B），它们会映射到同一 bank。多个 lane 在同一 instruction 中访问该 bank 的不同 word 时发生 bank conflict，硬件需要把请求拆成多个 wavefront/replay，而非必然让整个 memory system 完全串行。

代码中的 bank conflict 常由 shared-memory stride 使多个 lane 映射到同一 bank 的不同地址而产生。图 7-4展示两种无 conflict 的 bank access。

图中各 lane 在同一 instruction 中访问不同 bank，是理想情况。多个 lane 读取同一地址的 broadcast 是另一种无 conflict 情形。图 7-5展示 2-way 与 16-way bank conflict。

多个 lane 访问同一 bank 的不同 word 会产生 conflict，严重程度取决于 access pattern 与架构。经典示例是使用 32 × 32 shared-memory tile 的 matrix transpose。若 32 个 lane 读取 tile[i][threadIdx.x]，并且这里的 column index (threadIdx.x) 固定、row index 随 lane 改变（i），各地址跨 row 相隔 128 字节，可能形成 32-way conflict。原文变量描述含混；关键是不同 row、固定 column。

具体来说，在 row-major tile 中沿同一列读取时，warp lane 的 column index（threadIdx.x）固定、row index（i）变化。每行相隔 128 字节，因此 lane address 的差值为 128 字节的整数倍。

在 32 bank × 4 byte 的简化 mapping 中，bank index 每 128 字节重复。相隔 128 字节的地址会落到同一个 bank，但不一定是 bank 0；具体 bank 由起始地址决定。若 32 个 lane 访问该 bank 中 32 个不同 word，就形成 32-way conflict。

一个重要例外是：若 warp 的多个 lane 读取完全相同的 shared-memory word，硬件可 broadcast 该值，不构成 bank conflict。某些架构与访问宽度还具有 multicast 或不同的 bank 服务能力；同 bank 不同地址通常会增加 wavefront/replay，但不应笼统断言总是逐 lane完全串行。

另一个常见问题是使用与 bank 数相同的 element stride，本例为 32。若索引每次跨 32 个 float，每个 4 字节，则相邻 lane address 相差 128 字节，并映射到同一 bank。以下代码在基址对应 bank 0 时全部落入 bank 0：

// Allocate a shared buffer big enough for several warps (warpCount)
__shared__ float arr[32 * warpCount]; 

// Each thread reads from arr[threadIdx.x * 32]
float x = arr[threadIdx.x * 32];

这里以 float 为单位的 threadIdx.x * 32 对应字节偏移 (threadIdx.x * 32 * 4)。由于 32 * 4 = 128，每个 lane 的 load address 相对基址偏移 threadIdx.x * 128 字节，而 threadIdx.x * 128 mod 128 = 0。若各 lane 地址不同，它们会命中同一 bank 并形成 32-way conflict。

发生 conflict 时，一条 warp shared-memory request 会被拆成多个 wavefront/replay。Nsight Compute 可提供 shared-memory bank-conflict、wavefront 与相关 stall 指标，具体名称随版本变化。Shared-memory throughput 可能下降，也可能因重复服务而看似较高；Nsight Systems 通常不提供足以单独归因 bank conflict 的细粒度 per-kernel counter，应以 Nsight Compute 为主。

严重 bank conflict 会增加 shared-memory instruction 的服务周期并降低性能，但它只是潜在瓶颈之一。若 kernel 加速不及预期，应同时检查 global memory、occupancy、barrier、dependency 和 instruction throughput。

应根据同一 warp 的实际 lane address 选择 stride 与 data layout，使不同地址尽量分布到不同 bank；相同地址的合法 broadcast 无需刻意拆开。

常见解决方法是调整 shared-memory layout。Padding 会改变 row stride，使原本同 bank 的列访问分散。例如，把 32 × 32 tile 声明为 [32][33]，每行增加一个 padding element。这样 thread k 访问 tile[i][k] 时，相邻 row 的起始 bank 逐行偏移。图 7-6展示这一方法。

把 row stride 改为 33 个 float 后，沿列访问的 32 个 lane 会轮转到不同 bank，从而消除该特定 32-way conflict。其他 vector width、element size 或 tile pattern 仍需重新分析。

Padding 让 32-wide tile 的元素数增加 1/32，约 3.125%。对于 FP32 32 × 32 tile，原大小为 4,096 字节，增加一列只增加 32 × 4 = 128 字节，而不是原文所称的 1 KB。是否值得取决于 conflict 成本、shared-memory occupancy 与整体 kernel 时间；Blackwell 每 SM 容量也应按具体型号查询。

下面以简单 transpose kernel 展示如何消除 shared-memory bank conflict。naive 版本的转置读取使 warp lane 访问同一 bank 的不同 row，增加 shared-memory wavefront 数。以下是包含 conflict 的实现。

优化前示例（C++）：存在 bank conflict 的 naive transpose： 

#include <cuda_runtime.h>
#define TILE_DIM 32

__global__ void transposeNaive(const float *idata, float *odata, int width) {
    __shared__ float tile[TILE_DIM][TILE_DIM];
    int x = blockIdx.x * TILE_DIM + threadIdx.x;
    int y = blockIdx.y * TILE_DIM + threadIdx.y;

    // threads in a warp write a row
    tile[threadIdx.y][threadIdx.x] = idata[y * width + x];
    __syncthreads();

    // Read from shared memory with transposed indices
    // This is a classic case of all threads in a warp 
    // hitting the same bank causing a bank conflict
    // Read transposed from shared memory and write out
    odata[x * width + y] = tile[threadIdx.x][threadIdx.y];
}
 
int main() {
    const int N = 1024;
    size_t size = N * N * sizeof(float);
    float *h_idata = (float*)malloc(size);
    float *h_odata = (float*)malloc(size);
    // Initialize input h_idata...
    float *d_idata, *d_odata;
    cudaMalloc(&d_idata, size);
    cudaMalloc(&d_odata, size);
    cudaMemcpy(d_idata, h_idata, size, cudaMemcpyHostToDevice);

    dim3 block(TILE_DIM, TILE_DIM);
    dim3 grid(N / TILE_DIM, N / TILE_DIM);
    transposeNaive<<<grid, block>>>(d_idata, d_odata, N);
    cudaDeviceSynchronize();

    cudaFree(d_idata);
    cudaFree(d_odata);
    free(h_idata);
    free(h_odata);
    return 0;
}

该 kernel 写入 shared memory 的 tile 时使用 row-major tile[ty][tx]，同一 warp 的 tx 连续，因此访问不同 bank。（若写成 column-major tile[tx][ty]，同一 warp 中 tx 变化会使地址跨 row 相隔 128 字节，形成 32-way conflict。）随后以转置索引读取 tile：同一 warp 中 threadIdx.y 固定为 column index，而 threadIdx.x 变化并用作 row index；原文把二者说反了。

对给定 warp，thread 0–31 的 threadIdx.y 固定、threadIdx.x 变化，所以实际访问是 tile[varying_row][constant_col]。32 个地址位于不同 row 的同一列，每个相隔 128 字节并映射到同一 bank，形成 32-way conflict。原文把 tile 访问误写为同一 row 的不同 column；后者反而会连续映射到不同 bank。

本例假设 Blackwell shared memory有 32 个 bank，与 warp 的 32 个 lane 数相同。固定 column、改变 row 且 row stride 为 32 个 FP32 时，所有 lane 落入同一 bank 的不同 word，形成 32-way conflict。固定 row、改变 column 则无此问题。并非任何 misaligned warp access 都会全冲突；必须计算实际 bank index，并考虑 broadcast 与架构服务规则。

在该代码的典型对齐下，32 个 thread 读取 32 个不同地址，并映射到同一 bank，产生大量 replay。下面加入 padding 消除这一 conflict。

优化后示例（C++）：padded transpose（避免 bank conflict）。增加一个未使用的 padding column，使每个 shared-memory row 的起始 bank 相对前一行偏移 1：

#include <cuda_runtime.h>
#define TILE_DIM 32
#define PAD 1  // padding columns to avoid bank conflicts

__global__ void transposePadded(const float *idata, float *odata, int width) {
    // Each row is TILE_DIM+1 elements to shift bank mapping
    __shared__ float tile[TILE_DIM][TILE_DIM + PAD];
    int x = blockIdx.x * TILE_DIM + threadIdx.x;
    int y = blockIdx.y * TILE_DIM + threadIdx.y;

    tile[threadIdx.y][threadIdx.x] = idata[y * width + x];
    // We will optimize this later to use a thread-block-scoped 
    // cooperative-groups barrier
    __syncthreads();

    odata[x * width + y] = tile[threadIdx.x][threadIdx.y];
}

（host code 与 naive 版本相同，为简洁起见省略。）

PyTorch 没有用于直接声明 custom-kernel shared-memory padding 的高层 tensor API；可用 CUDA extension（如 torch.utils.cpp_extension）或 Triton/CUDA 等 custom kernel 路径实现。原文括号多写了一个 `)`。PyTorch operator 可能调度到 cuBLAS、cuDNN 或生成 kernel，它们会按具体算法处理 bank mapping，但不能保证所有 operator 无 conflict 或达到最大吞吐。

每个 shared-memory row 增加一个元素后，row stride 变为 33 个 float。对 tile[row][col] 的沿列访问，row 每增加 1，bank index 也偏移 1，使 32 个 lane 分布到 32 个 bank。这里应依据 word-address modulo 32 解释，而不是笼统称“地址低 5 bit”不同，因为 byte address 的低位还包含 4-byte word 内偏移。

padded kernel 实际读取的是 tile[threadIdx.x][threadIdx.y]，而不是原文写的相反索引。对于同一 warp，变化的 row index 配合 33-float stride，使 lane 映射到不同 bank，从而消除该特定 transpose read 的 conflict。表 7-5给出原书示意指标。

Swizzling 是 padding 的一种替代方案：通过 XOR、位重排或其他可逆 index transformation 改变 logical element 到 shared-memory address 的映射，使目标 lane access 分散到 bank。具体变换必须同时保持生产者与消费者使用一致 mapping，并满足 vector/Tensor Core layout。

Swizzling 可以不增加 tile element 数，但会增加 index/layout 复杂度，也不保证对所有访问阶段都实现“perfect bank parallelism”。Padding 较简单；swizzle 更适合经证明与目标 instruction layout 匹配的模式。

CUTLASS 等高性能 CUDA library 会在部分 tile layout/copy path 中使用 swizzle 或专用 layout，以满足 coalescing、bank conflict 与 Tensor Core instruction 的共同要求；不能概括为所有 iterator 都让每个 thread 永远映射到独立 bank。

总之，使用 shared memory 时，应按 warp instruction 分析 lane address、bank index、broadcast 与访问宽度。Padding 和 swizzling 可消除特定 conflict，但不保证“只要使用 shared memory 就一定提高性能”；还应测量额外资源、index 开销与整体 kernel 时间。

下一节讨论在 warp 内直接在线程之间交换 register value，从而在适用场景中省去 shared memory。

Warp shuffle intrinsic：避免 shared memory 与显式同步

上一节的 bank-conflict 优化假设 thread 通过 shared memory 通信。如果通信只发生在一个 warp 内，有些场景可以完全省去 shared memory，也就不存在相应 bank conflict。

NVIDIA GPU 提供 warp-level primitive，使同一 warp 的 lane 通过 shuffle 数据路径交换 register value，而不经过 shared memory。这些 primitive 的作用域限于一个 warp，并且只有 mask 中参与的 lane 才满足同步契约；用于 intrawarp communication 时不访问 memory bank，因此不会产生 shared-memory bank conflict。

最常见的是 __shfl_sync 系列 intrinsic。__shfl_sync 可以从指定 source lane 读取 value，从而实现 broadcast、permutation 或 warp-level reduction，而无需写 shared memory。`_sync` 后缀表示 mask 中所有非退出 lane 都必须以同一 mask 执行对应 intrinsic；它不是跨 warp synchronization。

现代 GPU 在多个 lane 读取 shared memory 中完全相同的地址时可 broadcast，因此这个单地址情形本就没有 bank conflict。Warp shuffle 则可按 lane id 交换多个不同 register value；它不是所有任意模式的无条件替代方案，仍受 mask、source lane 与数据类型规则约束。

假设需要对一个完整 warp 的 32 个 per-thread partial result 求和。shared-memory 方案可以让每个 thread 写入数组，再按 reduction tree 读取并同步；若布局正确，它不一定发生 bank conflict，但会增加 shared-memory instruction 与同步操作。

使用 __shfl_sync 系列可以在 register 中完成 tree reduction。下面使用 __shfl_down_sync，每轮从 lane id 加 offset 的 source lane 读取值。这是 down-shuffle reduction，并非通常由 XOR partner 构成的 butterfly all-reduce。示例假设 mask 对应完整的 32-lane warp；对任意部分 warp，必须按参与 lane 的连续性和数量调整算法，避免读取 inactive source lane：

unsigned mask = __activemask();
float val = threadVal;  // each thread’s partial sum

// Perform butterfly reduction: exchange values with increasingly distant lanes
for (int offset = 16; offset > 0; offset >>= 1) {
    float other = __shfl_down_sync(mask, val, offset);
    val += other;
}

// After the loop, lane 0 holds the warp’s total sum

每次 __shfl_down_sync 让 lane 读取指定 offset 处 source lane 的 register value。对完整 warp 的这个 reduction pattern，lane 0 最终得到总和；其他 lane 通常只得到部分后缀和。代码没有显式把“active thread 数减半”，所有参与 lane 仍执行循环，只是超出 width 的 source read 返回值语义需遵循 intrinsic 规则。通信不经过 shared memory，因此无 bank conflict，也不需要 block-wide barrier，但 `_sync` mask 本身承担 warp 参与约束。

总之，__shfl_sync 及其变体在 warp 内交换 register value，不使用 shared memory。它们常能减少 shared-memory load/store 与 barrier，但是否更快取决于 instruction dependency、mask、数据布局与目标架构。

许多高性能 warp-level reduction 使用 shuffle intrinsic，在少量 instruction 中交换 register value，绕过 shared memory。CUDA Cooperative Groups 提供 tiled partition 与 group collective；具体 shuffle API 属于支持相应操作的 thread-block tile/group type，并非任意 thread_group.shuffle() 都存在。__reduce_sync() 是独立的 warp reduce intrinsic，compiler 可映射为 target architecture 的 reduction instruction 或其他实现，不能断言最终总是展开为 shuffle pattern。

Shuffle 只在单个 warp 内工作。跨 warp reduction 可使用 shared memory 配合 block synchronization、Cooperative Groups collective，或在支持时使用 cluster distributed shared memory/cluster synchronization；这些机制并非“multiwarp shuffle”。第 10 章将讨论相关概念。

Shuffle 的 source/destination lane 限于同一 warp，常见 warp size 为 32。跨 warp 传递普通数据通常需要 shared/global memory 或架构支持的 cluster memory，并配合正确同步；也可通过更高层 collective/library 封装这些步骤。

第 10 章将讨论 Cooperative Groups synchronization、multiwarp pattern 与 thread-block cluster（CTA cluster）。它们可能使用 barrier、shared/distributed shared memory、shuffle 或其他硬件机制，并非最终都使用同一种 intrinsic。理解 intrawarp 与 interwarp communication 有助于定位 memory、synchronization 和 dependency bottleneck。

Read-only data cache

当多个 thread 读取相同value，或某个 thread 重复读取不变数据时，cache locality 会显著影响性能。例如，推理期间只读的 embedding/lookup table 可能被大量 thread 并行访问；若 working set 和访问分布适合 cache，片上 cache 可减少 HBM traffic。若访问随机且表远大于 cache，声明只读也不能创造 locality。

这里讨论的 read-only load path 与 64 KB constant address space/constant cache 机制不同。Constant memory 适合容量较小、warp 内地址较一致的数据；大型 embedding 通常位于 global memory，并通过 L2 与架构相应的 L1/texture/read-only cache path 服务。现代架构中这些路径可能共享或统一物理 cache，不能把 read-only cache 简单描述成专用于 immutable data 的独立“大缓存”。

现代 GPU 的 global-memory load至少经过 L2，并可按 architecture/cache operator 使用 L1/texture path。const __restrict__ 中，`const` 限制通过该 pointer 修改对象，`__restrict__` 是关于 aliasing 的 programmer promise；两者都不表示“non-coherent”或“read-mostly”。这些信息可能帮助 compiler 选择 read-only load 或进行其他优化，但 read-only traffic 仍会占用 cache capacity，也可能驱逐其他数据。

在支持的 CUDA target 上，compiler 常能为可证明只读的访问自动选择合适 load，因此通常无需显式调用 __ldg()。const __restrict__ 可能提供所需的 alias/immutability 信息，但不是生成特定 instruction 的保证。__ldg() 的可用性和实际 cache 行为随 compute capability 与 Toolkit 变化，应检查当前文档和 SASS。

若 programmer 能保证 buffer 的只读与 non-aliasing 语义，却没有向 compiler 表达这些信息，可能错失 load、code motion 或 scheduling 优化。但普通 global load 仍然可以命中 L1/L2；缺少 `__restrict__` 不会自动使每次访问都落到 DRAM，也不会必然造成“虚假 cache miss”。错误使用 `__restrict__` 反而会违反 aliasing contract并导致未定义行为。

性能分析时，应检查实际 SASS/cache operator、L1/TEX 与 L2 hit rate、requested/sector byte、DRAM byte 和 stall reason。Instruction stream 中没有 __ldg() 源码名称并不证明未使用 cache；现代 machine instruction 与 profiler counter 不一定沿用该名称。L2 hit rate 低也可能只是 working set 过大或访问缺乏 locality。

在语义真实成立时，可用 const __restrict__ 表达只读与 non-aliasing，或在支持且必要时测试 __ldg()。这是给 compiler 的语义/显式 load 选择，不是向 hardware 永久标记整个 allocation。现代 L1/texture/read-only 路径的物理组织和 latency 随架构变化。

对于 constant memory 的 warp-uniform address，constant cache 可 broadcast；某些 read-only/global load 路径也能合并相同地址请求。__constant__ 与旧架构上的 uniform __ldg() 不是同一种 cache 语义。Broadcast 可减少 transaction，但不是“免费”或保证单周期：cache miss、dependency、pipeline occupancy 与 contention 仍会影响 latency。

下面以大小 T = 1,024 的 table 为例，每个 thread 查找一个 value 并写入 output。FP32 table 只有 4 KB，而且 `t = idx % T` 使 warp 内访问连续、跨 warp 周期重复，因此它是高度 cache-friendly 的 microexample，并不能代表大型随机 embedding lookup。先看 CUDA C++：

#include <cuda_runtime.h>
#define T 1024

__global__ void naiveLookup(const float* table, float* out, int N) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    if (idx < N) {
        // __ldg not used here, each access goes to 
        // global memory without using read-only cache
        int t = idx % T;
        out[idx] = table[t];
    }
}

int main() {
    const int N = 1 << 20;

    float* h_table = nullptr;
    float* h_out = nullptr;
    cudaMallocHost(&h_table, T * sizeof(float));
    cudaMallocHost(&h_out, N * sizeof(float));

    for (int i = 0; i < T; ++i) h_table[i] = float(i);

    float *d_table, *d_out;
    cudaMalloc(&d_table, T * sizeof(float));
    cudaMalloc(&d_out, N * sizeof(float));
    cudaMemcpy(d_table, h_table, T * sizeof(float),
        cudaMemcpyHostToDevice);

    dim3 block(256), grid((N + 255) / 256);
    naiveLookup<<<grid, block>>>(d_table, d_out, N);
    cudaDeviceSynchronize();
    cudaMemcpy(h_out, d_out, N * sizeof(float), cudaMemcpyDeviceToHost);
    cudaFree(d_table);
    cudaFree(d_out);
    cudaFreeHost(h_table);
    cudaFreeHost(h_out);

    return 0;
}

#include <cuda_runtime.h>
#define T 1024

__global__ void lookup(const float* __restrict__ table,

    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    if (idx < N) {
        int t = idx % T;
        // Compiler can turn this into a load from the
        // read-only cache for faster loads
        out[idx] = table[t];
    }
}

Legacy texture reference 与 surface reference API 已弃用，texture object 与 surface object API 仍受支持。是否适合取决于 resource type、addressing、locality 与所需读写语义。对于一般 1D AI tensor，普通 global load 与 compiler/library 生成的 cache policy 通常更简单；constant memory 仅适合较小且 warp-uniform 的数据，不能与 read-only global cache 合并称为统一首选。

总之，只在语义成立时为 read-only data使用 const __restrict__，让 compiler 获得正确的只读/aliasing 信息；随后检查实际 codegen 与 cache metric。Texture/surface object 适合特定 multidimensional resource 与 addressing 需求，不是 regular cache 的普遍替代品。任何性能收益都取决于 locality、working set、架构与整体 kernel 瓶颈。

异步内存预取与 Tensor Memory Accelerator

前几节已经说明，将数十个 4-byte load 合并为一次 128-byte transaction，可以显著提高 global load 效率，并减少每个 request 中浪费的 sector。然而，即使 load 已经完美合并，warp 仍可能因等待完整的 DRAM 往返而停顿。

以 Blackwell 为例，在具体访问路径和系统状态不同的情况下，一次完整 DRAM 往返的延迟可能达到数百个 cycle，之后计算才能使用返回的数据。要隐藏这部分延迟，就需要让数据传输与计算重叠；这种 overlap 可以遮蔽相当一部分 DRAM latency。

CUDA Pipeline API 与 Tensor Memory Accelerator（TMA）硬件引擎将这一思路扩展到 thread block 层级。每个 warp 不必都通过 SM 的 load/store（LD/ST）单元从 global memory 取数；在满足目标架构、传输方向、对齐、shape 和 stride 等要求时，可以使用 TMA engine 将整个 tile 从 global memory 异步搬运到 shared memory，如图 7-7所示。

要发起异步传输，可以调用 cuda::memcpy_async()。在现代 GPU 架构上，cuda::memcpy_async() 与 cuda::pipeline 为 global-to-shared 异步传输提供了高级接口；当目标硬件以及方向、对齐、大小和布局等条件满足时，编译实现可以利用 TMA 或其他异步复制机制执行 bulk data transfer。因此，是否实际生成 TMA 指令，需要结合目标架构、CUDA toolchain 和编译结果确认。CUDA 写法如下：

cuda::memcpy_async(sharedBuf,
               globalPtr + offset,
               cuda::aligned_size_t<16>(bytes),
               pipe);
pipe.producer_commit();

在异步复制机制处理 bulk copy（包括合并访问、strided transfer，乃至 multidimensional transfer）的同时，kernel 可以计算前一个 tile。这种方法称为双缓冲（double buffering），也称乒乓缓冲（ping-ponging）。

使用 TMA 配合双缓冲，可以把一部分地址生成和数据搬运工作从常规 SM load/store 指令路径卸载出去。TMA 搬入下一个 tile 时，SM 中的 warp 处理前一个 tile；若 pipeline 深度、计算量、occupancy 和内存带宽等条件允许，这种重叠便能隐藏相当一部分 DRAM latency。这里的延迟不是固定的 800 cycle，而会随架构、cache 命中情况、访问模式和系统负载变化。

具体而言，TMA 支持 global memory 与 shared memory 之间的 1D–5D bulk copy，并能按 tensor descriptor 表达 multidimensional shape 和 stride。它可减少 kernel 显式发出的 LD/ST 指令，并使部分数据搬运与计算并行；但传输仍会占用内存与复制资源，也仍需要正确的 async barrier 或 pipeline phase 同步，不能理解为完全没有同步或调度开销。

下面的代码片段展示了如何通过 CUDA C++ Pipeline API 与相应的异步复制硬件，从 global memory 向 shared memory 发起异步复制；是否使用 TMA，取决于目标架构及相关约束：

#include <cuda/pipeline>
#include <cuda_runtime.h>
#include <cstdint>
#include <cassert>

#define TILE_SIZE 1024  // example tile size
// User-provided compute function operating on a shared-memory tile
__device__ void processTile(const float* tile);

__global__ void kernelWithTMA(const float* __restrict__ global_ptr,
                              int nTiles) {
    // Two ping-pong buffers in shared memory
    // On Blackwell (CUDA 13+), prefer 32B alignment for 256-bit vectors 
    // (v8.f32 / double4).
    __shared__ __align__(VEC_BYTES) float tile0[TILE_SIZE];
    __shared__ __align__(VEC_BYTES) float tile1[TILE_SIZE];

float* tiles[2] = { tile0, tile1 };
    
    // Alignment / size guards for vectorized copies
    // --- choose vector width -------------------------------------------------
    #ifndef VEC_BYTES
      // Prefer 32B vectors on CUDA 13+/Blackwell. 
      // Define -DUSE_256B_VEC to force.
      #if defined(USE_256B_VEC) || (defined(CUDA_VERSION)&&CUDA_VERSION >= 13000)
        #define VEC_BYTES 32      // 256-bit: v8.f32, double4
      #else
        #define VEC_BYTES 16      // 128-bit: v4.f32, float4
      #endif
    #endif
    constexpr int VEC_ELEMS = VEC_BYTES / sizeof(float); // 4 (128b) or 8 (256b)
    constexpr int WARP      = 32;

    // Alignment / size guards for vectorized copies/compute
    static_assert((TILE_SIZE % (WARP * VEC_ELEMS)) == 0,
                  "TILE_SIZE must be a multiple of WARP_SIZE * VEC_ELEMS");
    // Also guarantee the tile byte count
    //  is a multiple of the vector width
    static_assert(((TILE_SIZE * sizeof(float)) % VEC_BYTES) == 0,
                  "Tile byte size must be a multiple of VEC_BYTES");

    // On Blackwell (CUDA 13+), prefer 32B alignment 
    // for 256-bit vectors (v8.f32 / double4).

    assert((reinterpret_cast<std::uintptr_t>(global_ptr) % VEC_BYTES) == 0);

    size_t bytes = TILE_SIZE * sizeof(float);
    // Block-scoped pipeline for TMA
    __shared__ cuda::pipeline_shared_state<
        cuda::thread_scope_block, 2> state;

    auto pipe = 
        cuda::make_pipeline(cuda::this_thread_block(), 
            &state);

    // Prime pipeline with the first async copy into tile0
    pipe.producer_acquire();
    cuda::memcpy_async(tiles[0],
                       global_ptr + 0 * TILE_SIZE,
                       cuda::aligned_size_t<32>{bytes},
                       pipe);
    pipe.producer_commit();

    // Loop over the remaining tiles
    for (int t = 1; t < nTiles; ++t) {
        // Wait for the previous copy to finish, then compute on it
        pipe.consumer_wait();
        processTile(tiles[(t - 1) & 1]);
        pipe.consumer_release();

        // Enqueue the next async copy into the alternate buffer
        pipe.producer_acquire();
        cuda::memcpy_async(tiles[t & 1],
                           global_ptr + t * TILE_SIZE,
                           cuda::aligned_size_t<32>{bytes},,
                           pipe);
        pipe.producer_commit();
    }

    // Final wait and compute on the last tile
    pipe.consumer_wait();
    processTile(tiles[(nTiles - 1) & 1]);
    pipe.consumer_release();
}

kernel 启动后，每个 block 会分配两个 shared-memory tile（tile0 和 tile1），并构造一个 block scope 的 pipeline，使 thread block 中的所有 thread 按同一 pipeline phase 协调异步复制，如下所示：

__shared__ cuda::pipeline_shared_state<
    cuda::thread_scope_block, 2> state;

auto pipe = 
    cuda::make_pipeline(cuda::this_thread_block(),
        &state);

为了预热 pipeline，producer 先取得一个可写 stage，并提交从 global memory 到 tiles[0] 的异步复制，然后 commit 该 producer phase，如下所示。在满足硬件与 descriptor 等条件时，底层可以使用 TMA 完成 bulk、strided 或 multidimensional transfer；这里的 bytes 表示本次复制的数据量。

pipe.producer_acquire();
cuda::memcpy_async(tiles[0],
                   global_ptr + 0 * TILE_SIZE,
                   cuda::aligned_size_t<32>{bytes},
                   pipe);
pipe.producer_commit();

使用该数据之前，consumer 必须等待对应 stage 的复制完成；处理完毕后再 release 该 stage，使其能够被后续 producer phase 复用：

pipe.consumer_wait();
processTile(tiles[0]);
pipe.consumer_release();

在 main loop 中，两个 buffer 交替承担 consumer 与 producer 的角色：先通过 pipe.consumer_wait(); 等待前一个 tile 就绪，再调用 processTile() 处理它；处理结束后调用 pipe.consumer_release() 释放相应 stage。另一侧则通过 pipe.producer_acquire() 取得可写 stage，调用新的 cuda::memcpy_async() 将数据送入另一个 tile，最后用 pipe.producer_commit() 提交该 phase。随后重复这一过程。实际代码必须让所有参与 thread 遵守一致的 collective 调用与 phase 生命周期，不能仅把这些调用任意拼接。

在 tile0 与 tile1 之间进行乒乓切换后，每次新的 memcpy_async 都有机会与前一个 buffer 上的 processTile 重叠。若底层采用 TMA，部分搬运工作不再通过常规 per-thread LD/ST 指令完成，因此 SM load/store 路径的压力可能下降，并为计算留下更多 instruction issue 机会。不过，这种方法不会自动消除算法本身的重复 global load，也不会取消必要的 pipeline synchronization；收益应通过实际 counter 与执行时间验证。

从 global memory 到 shared memory 的异步预取，可以尝试用计算遮蔽数据传输延迟：thread 处理此前已经载入的数据时，pipeline 同时预取后续数据。

这种模式尤其适合具有可预测 tile 流、且存在足够计算可与传输重叠的 memory-bound loop 和 tensor computation。例如在现代 GPU 上处理当前 matrix-multiply tile 时，可以并行搬入下一个 tile；若计算过短、带宽已经饱和或 occupancy 因额外 shared memory 而下降，实际收益则可能受限。

在支持 TMA 的架构上搬运 2D 或 N-dimensional tile 时，TMA 是 global memory 与 SMEM 之间 tiled bulk copy 的重要路径；TMEM 是另一种具有特定指令和用途的片上存储，不能与普通 SMEM 路径混为一谈。可以在 block scope 使用 cuda::memcpy_async 与 cuda::pipeline 表达异步复制，但 Hopper/Blackwell 是否生成 TMA（cp.async.bulk.* family）指令，仍取决于具体 API overload、方向、对齐、shape、stride、destination 与 toolchain。不要仅凭源码 API 名称推断实际指令路径。

这种方法把许多分散的 global read 重组为较规则的 bulk global copy，再从 shared memory 多次复用数据。考虑到 DRAM 与片上 SRAM 的带宽和延迟差距，在具有充分数据复用的算法中通常更有利。表 7-7汇总了原文给出的 TMA 双缓冲实现前后 Nsight Compute 指标；这些数值缺少完整复现条件，应视为示意对照。

每个 request 的平均 sector 数从 6.4 降至约 4.0。对于常见的 32-byte sector 口径，4 个 sector 合计为 128 byte，但这本身并不能证明每个 request 都“整齐映射”为单个 cache line，还需结合 request 类型、地址分布和相关 sector counter。表中 DRAM throughput 从 peak 的 25% 上升到 90%，执行时间从 18 ms 降至 7 ms，按算术约加速 2.57×。这些数字可以说明某个具体实现可能通过 bulk copy 与 shared-memory 乒乓缓冲改善 overlap，但由于原文未提供复现实验配置，不能据此推导 TMA 的通用加速比或断言已隐藏大部分 DRAM latency。

NVIDIA CUDA pipeline API 与 TMA 可以视为 hardware-software codesign 的一个例子：高级 pipeline abstraction 能够表达异步 producer/consumer 操作，而支持的底层实现可将适合的 bulk 或 multidimensional copy 映射到 TMA。不过，Pipeline API 并不只对应 TMA，任意 cuda::memcpy_async 也不必然生成 TMA 指令。

API 与硬件复制能力相互配合，使开发者能够用较高层的 pipeline operation 表达接近硬件传输模型的工作流，并在依赖关系、资源和数据量允许时，让 memory movement 与 compute 有效重叠，从而改善性能。

为 global-to-shared tiling 编写 CUDA kernel 时，通常应优先考虑目标 CUDA 版本中受支持、抽象层次合适的 API，其中包括 CUDA Pipeline API（cuda::memcpy_async）。较高层 API 可能在条件满足时利用 TMA 执行 bulk、strided 或 2D/3D transfer，也可能支持结合 thread block cluster 的 TMA multicast；但 multicast 需要相应架构、cluster launch、shared-memory/descriptor 配置和专用路径，并非所有调用都会透明启用。升级 toolchain 后仍应检查 generated code、correctness 与性能，不能假定这些能力无需任何代码或配置变化即可“免费”获得。

总之，当 memory access 限制 kernel 性能时，可以把合理 tiling、双缓冲和 TMA 异步预取结合起来，尝试卸载并重叠数据搬运。将 tile 暂存到 shared memory，并正确配合 cuda::memcpy_async、pipe.producer_commit 和 pipe.consumer_wait，可以表达 global-to-shared 的异步复制；满足 TMA 条件时，底层可将相应 bulk 或 multidimensional transfer 交给 TMA。

使用 TMA 卸载部分 memory transfer，可能缓解 SM load/store instruction path 的压力，并帮助 compute pipeline 保持繁忙。需要注意的是，TMA 主要负责 global memory 与 shared memory 之间的特定搬运；数据进入 shared memory 后，kernel 对 shared memory 的常规访问仍由 SM 指令及相关片上资源完成。在 Blackwell 的高带宽 HBM3e 系统上，这些技术有机会隐藏 DRAM latency 并提高 throughput，但 kernel 是否从 memory-bound 接近 compute-bound，仍取决于 arithmetic intensity、传输重叠、bandwidth、stage 数、occupancy 与实际 profiler 结果。

关键要点

通过 coalescing、数据复用和异步传输优化 GPU memory access pattern，有可能缓解 kernel 的 memory bottleneck，使其更接近硬件能力上限。合理组织 thread、使用 shared memory、避免 bank conflict 等看似局部的代码调整，有时会带来显著性能收益，但效果取决于 workload、架构和实际瓶颈。以下是本章的关键要点：

全局内存合并访问

当一个 warp 的访问覆盖尽可能少的 memory sector/cache line 时，就形成了较好的 coalescing。应根据元素宽度和访问模式组织数据与 thread index，使相邻 active lane 尽量访问连续且正确对齐的地址。对于 32 个 lane 各读取一个连续 FP32 word 的完整 warp，常见 32-byte sector 口径下最低通常是 4 个 sector，但不同访问宽度、active mask 和 request 类型的最优值并不固定为 4.0。使用相应版本的 Nsight Compute 时，可以结合 sm__sass_data_bytes_mem_* counters 和 gpu__dram_throughput.avg.pct_of_peak_sustained_elapsed 等实际可用 metric，分析 requested/actual byte、sector 和 DRAM throughput，从而优化 memory coalescing。

向量化加载/存储

可以使用 float4 等内置 vector type 表达 16-byte vector access。对于 Blackwell 和相应 CUDA toolchain，只有在类型、指针和 offset 的 32-byte alignment 均可证明，且目标指令路径支持时，才考虑 double4 或自定义 alignas(32) { float v[8]; } 等 32-byte per-thread access。Vectorization 可能减少每 byte 的 instruction 数，但不会让任意 warp request 都保持 4.0 sectors/request；transaction 数会随总请求 byte、对齐和地址覆盖范围变化。cudaMalloc 返回的 base address 通常满足较高对齐要求，但后续 pointer offset 仍可能破坏 float4 所需的 16-byte alignment。应检查 PTX/SASS 和 profiler，而不是仅由源码类型推断实际 vector instruction。

避免 bank conflict

针对具体 lane address pattern 调整 shared-memory layout。例如，在典型 FP32 transpose 的列访问中，可把每行从 32 个 float pad 到 33 个，以打散同 bank 的 stride；这并不能保证所有访问模式下任意两个 thread 都不命中同一 bank。消除主要 bank conflict 可以减少 replay/wavefront，但 shared-memory throughput 仍受 instruction、带宽和其他资源限制。Swizzling 也可减少某些模式的冲突，不过必须与生产者、消费者及 Tensor Core layout 保持一致，且不一定总比 padding 更节省或更快。

Shared-memory tiling 与数据复用

把 working set 分块暂存到片上 shared memory，例如使用 32 × 32 matrix tile，使每个 block 在一个 tile iteration 中协作加载所需元素并多次复用。不同 block 仍可能重复读取同一输入数据，cache 也会影响实际 DRAM traffic。Tiling 可提高 arithmetic intensity，但是否使 kernel 转为 compute-bound，需要结合 shared-memory/register 占用、occupancy 和 Roofline/profile 数据判断。

只读数据与 cache

对于只通过某个 pointer 读取且确实不存在相关 alias 的 lookup table 或 coefficient，可以使用 const __restrict__ 向 compiler 提供语义信息；错误的 restrict 承诺会导致未定义行为。Compiler 是否采用特定 read-only/cache load path 取决于架构与代码生成。Warp-uniform access 有机会通过 broadcast 和片上 cache 减少 transaction，但 cache miss 时仍可能访问更低层 memory，延迟也不是固定值。

使用 stream 重叠 host–GPU copy

需要稳定重叠 H2D/D2H transfer 与 kernel execution 时，通常应使用 page-locked（pinned）host buffer，并通过显式 stream 和 event 调用 cudaMemcpyAsync。实际 overlap 还要求设备 copy engine、传输方向、stream dependency 和资源并发条件允许。对于 pageable memory，CUDA runtime 可能使用内部 staging 或表现出同步行为，语义和 overlap 能力会随方向及实现变化，不能简单视为所有情况下都“禁用 DMA overlap”。应确认实际使用的 host-memory 类型，并用 timeline 测量 PCIe、NVLink 或其他互连上的传输与计算是否真正重叠；可再次通过 cudaMemcpyAsync 的实测行为确认，观察到的速率会随该配置显著变化。

使用 TMA 与 Pipeline API 异步预取

可以用 C++ libcu++ barrier 与 pipeline API（cuda::barrier 和 cuda::pipeline）配合 cuda::memcpy_async 表达 global memory 到 shared memory 的异步 bulk copy。在目标架构以及 API overload、alignment、shape、direction 和 scope 等要求满足时，底层可能使用 TMA（包括相应的 cp.async.bulk.tensor 路径）。结合双缓冲，可让受支持的 strided 或 multidimensional copy 与计算重叠，并可能降低 SM LD/ST instruction path 的压力，使 SM 有更多机会执行计算。

libcu++ pipeline API 与 TMA 仍在演进。对于 two-stage ping-pong buffer，应正确使用 staged operation，例如 producer_acquire()、producer_commit()、consumer_wait() 和 consumer_release()，并维持一致的 phase 生命周期。除非确实需要且 API/硬件支持 cluster 或更大 scope 的协作，否则通常使用 block-scoped pipeline（如 cuda::thread_scope_block）或 block-scoped barrier（如 cuda::barrier<cuda::thread_scope_block>）；具体可用 scope 需以目标 CUDA 文档为准。

以 profiling 指导优化

使用目标版本 Nsight Compute 中实际可用的 Global Memory Load Efficiency、每 request 平均 sector 数、shared-memory wavefront/conflict、SM Active % 和 warp stall reason 等 metric。还应查看 Nsight Systems timeline，验证 transfer 与 compute overlap、发现宏观空隙；但具体 bank conflict 等微架构原因通常需要 Nsight Compute counter 才能归因。每项优化都应以同一 workload 的正确性和执行时间为最终验证依据。

总结

通过合并 global-memory load、针对实际访问模式避免 bank conflict、进行 tiling 与 vectorized fetch、合理利用 cache，并在适用时采用 TMA 异步预取，可以逐项缓解重要的数据搬运瓶颈。它们并不保证 SM 自动达到 full speed；最终效果取决于 kernel 的真实瓶颈和各项资源之间的权衡。

本章使用 Nsight Compute 与 Nsight Systems 分析 warp 在何处等待数据，并验证优化是否减少 stall 和无效 transaction、提高 sustained bandwidth。应根据工具各自的观测层级解释结果：Systems 适合查看时间线和并发，Compute 适合分析 kernel 内部 counter。调优新 kernel 时，始终以可复现 benchmark、正确性检查和相应 profiler 证据闭环验证每一步。
