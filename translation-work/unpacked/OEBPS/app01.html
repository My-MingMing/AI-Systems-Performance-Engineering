性能调优与成本优化思维

务实且有记录的闭环——先取得快速收益，再进行深入工作——可将工程时间转化为可衡量的投资回报率。先针对最大的运行时间和成本驱动因素，且始终在优化前后进行性能分析以验证影响。

结合自动调优、框架升级、云定价策略和利用率仪表板，获得高 ROI 收益；记录结果并优先选择简单、易维护的修复方案。在准确率允许时调节对吞吐量敏感的超参数。以下是性能调优与成本优化的思维建议：

优先优化最昂贵的部分

遵循 80/20 原则。找出运行时间的主要贡献者并集中处理。若 90% 的时间花在少数几个内核或某个通信阶段，深入优化它们远比微调只占 1% 时间的部分更有价值。各章技术应应用在最关键的地方。例如，若训练中数据加载占 40%、GPU 计算占 50%、通信占 10%，应先解决数据加载，因为可能将该开销减半；随后再研究 GPU 内核优化。

优化前后都进行性能分析

每次应用优化时都要测量影响。这听起来显而易见，但实践中许多调整基于理论，可能没有帮助，甚至造成损害。假设负载并不受内存限制，却决定为训练启用激活检查点：它可能通过增加计算来降低内存，反而使作业变慢。换言之，始终比较变更前后的吞吐量、延迟和利用率等关键指标。可使用内置分析器进行简单计时，例如统计 100 次迭代的平均时间。

采用自适应自动调优反馈闭环

实现利用实时性能反馈的高级自动调优框架，例如采用强化学习或贝叶斯优化动态调整系统参数。这使系统能响应不断变化的工作负载和运行条件，持续微调设置。

为优化时间编制预算

性能工程是一项迭代性投资，收益会递减。应先做容易取得的成果，例如启用 AMP 和数据预取，它们可能轻松带来 2 倍收益。编写自定义内核等较难优化的增益可能更小。始终权衡工程时间与节省的运行时间和成本。对于训练旗舰模型等大规模重复作业，即使 5% 的收益也可能节省数百万成本，足以证明数周调优合理；对一次性或小型负载，则应务实地关注更大的收益。

持续了解框架改进

我们讨论的许多优化，如混合精度、融合内核和分布式算法，仍在深度学习框架和库中不断改进。升级到最新版 PyTorch 或 TensorFlow 有时可立即加速，因为其中包含新的融合操作或更好的启发式策略。应利用这些近乎免费的收益，并阅读发行说明中的性能相关变更。

与供应商和社区成员协同设计

与硬件供应商和更广泛的性能工程社区保持联系，使软件优化适配最新硬件架构。通过按新硬件能力定制算法，这种协同设计方法可发现显著性能机会。定期查阅供应商文档、参与论坛并测试驱动或框架的 Beta 版；这些互动常能发现可集成到系统的新优化机会和最佳实践。整合新的驱动优化、库更新和硬件专用建议，可带来额外且有时显著的性能提升。

利用云的灵活性控制成本

在云环境中运行时，应明智使用更便宜的竞价实例或预留实例。它们可大幅降低成本，但竞价实例可能在数分钟前通知后被收回。也应考虑实例类型：若工作负载不需要绝对最新硬件，成本仅为一小部分的稍旧 GPU 实例有时可提供更好的性价比。我们对 H800 与 H100 的讨论表明，投入足够工程工作，也能在次优硬件上完成出色工作；云中也存在类似权衡。应在不同实例配置上进行基准测试，评估 CPU 数量、CPU 内存、GPU 数量、GPU 内存、L1/L2 缓存、统一内存、NVLink/NVSwitch 互连、网络带宽与延迟、以及本地磁盘配置等因素的成本/性能。计算每美元吞吐量等指标，以指导优化决策。

监控利用率指标

持续监控 GPU 利用率、SM 效率、内存带宽使用率，以及多节点场景下的网络利用率。使用 DCGM exporter、Prometheus 等建立仪表板，以便发现任一资源利用不足。若 GPU 利用率仅为 50%，应深入查找原因：很可能是等待数据/停顿或同步通信缓慢。若网络仅使用 10%，GPU 却在等数据，问题可能是锁等其他因素。这些指标有助于找准应关注的子系统。

迭代调节超参数以提升吞吐量

可调节某些模型超参数（如 batch 大小、序列长度和 MoE 活跃专家数）以提升吞吐量，而不降低最终准确率。例如，较大 batch 可带来更好吞吐量，但可能需要调节学习率计划来维持准确率。不要害怕调整这些参数，以找到速度与准确率的最佳平衡。这也是性能工程的一部分：有时可调整模型或训练过程以提高效率，例如使用激活检查点，或为相同有效 batch 增加计算步骤；可相应调整训练学习率计划。

记录并复用

记录已应用的优化及其影响，并写入代码或内部 wiki 式共享知识库。这会为未来项目建立知识基础。许多建议都是可复用模式，例如启用重叠或设置有助于集群运行的特定环境变量。积累这些历史，在启动新工作或让新成员加入性能调优时可节省时间。

平衡优化与复杂性

目标应是以最简单方案达到所需性能。例如，若原生 PyTorch 配合 torch.compile 已满足速度目标，可能无需编写自定义 CUDA 内核，从而避免额外维护。使用高度定制代码过度优化会让系统变得脆弱。既快速又易维护的方案具有优雅性。因此，应先采用带来所需收益的侵入性最小优化，仅在必要时升级为更复杂的方法。

优化 AI 驱动的性能

利用机器学习模型分析历史遥测数据并预测系统瓶颈，使系统能实时自动调整参数，优化资源分配和吞吐量。

可复现性与文档最佳实践

性能收益若不能复现、版本化并持续检查，便无法持久，且会随时间悄然回退。应将文档、CI 基准测试和共享知识视为保留加速成果、加快成员入职和审计的粘合剂。

在源代码管理中锁定版本、配置和基准，以便重复实验并追踪回退。将性能检查引入 CI/CD，实施端到端监控与告警，并使优化配合安全措施和详尽文档，从而建立持久、可审计的实践。以下是提高可复现性和文档质量的建议：

严格的版本控制

对所有系统配置、框架/驱动版本、OS 设置、优化脚本和基准测试实施全面版本控制。使用 Git（或类似系统）追踪变更并标记发布版本。这样可精确复现实验，也能轻松识别性能回退。

用于性能回退的持续集成

将自动化性能基准和实时监控集成到 CI/CD 流水线。这可确保从代码更新到配置变更的每项变化，均以一组性能指标验证，帮助尽早发现回退并保持一致、可量化的性能提升。采用 MLPerf 等行业标准基准，建立可靠性能基线并长期跟踪改进。

端到端工作流优化

确保优化整体应用于整个 AI 流水线——从数据摄取和预处理，到训练和推理部署。协调的跨系统调优能发现孤立调整可能错过的协同效应，从而实现更显著的总体性能提升。

自动化监控与诊断

部署端到端监控方案，收集跨硬件、网络和应用层的实时指标。将其集成到 Prometheus/Grafana 等仪表板，并配置自动告警，以迅速发现 GPU 利用率突然下降或网络延迟激增等异常。

容错与自动恢复

通过分布式检查点、冗余硬件配置和动态作业重调度，将容错纳入系统设计。这一策略可最小化停机时间，并在硬件或网络故障时保持性能。

编译器与构建优化

在构建过程中利用激进的编译器标志和基于性能分析的优化，从代码中提取最大性能。定期更新和调优构建配置，并通过严格基准验证每项变更的影响，以确保最佳执行效果。

安全性、合规性与性能

整合并协同设计安全性、合规性与性能。定期审计配置，执行访问控制，并保持符合行业标准的保障措施，包括加密、安全数据通道、零信任网络、硬件安全模块（HSM）和安全隔离区。确保性能调优绝不损害系统安全；同样也要确保安全机制不会产生不必要的性能开销。

全面的文档与知识共享

详细记录所有优化步骤、系统配置和性能基准。建立内部知识库以促进团队协作和快速入职，确保最佳实践可在项目之间保留并复用。

面向未来与可扩展性规划

设计模块化、可适应的系统架构，以便轻松纳入新兴硬件和软件技术。持续评估可扩展性需求，并更新优化策略，使系统在工作负载增长时仍保持有竞争力的性能。

系统架构与硬件规划

硬件、互连和数据路径决定性能和成本效益的上限——软件调整无法弥补 GPU 长期缺料。应将加速器、CPU/DRAM/I/O 与散热/供电匹配到工作负载，按每美元/每瓦的有效吞吐量规划，从一开始就避免瓶颈。

具体而言，应面向有效吞吐量（每美元/每瓦的有用工作），而非仅面向原始 FLOPS 进行设计。使加速器和互连适配工作负载，适当配置 CPU/内存/I/O 以持续供给 GPU，保持数据本地，并规划电力和散热以使硬件维持峰值时钟。增加 GPU 前先评估扩展效率。以下是优化系统架构和提高硬件规划效率的建议：

面向有效吞吐量与效率设计

将有用吞吐量视为目标。规模化场景中，每一点性能提升都可转化为巨大的成本节省。应着力最大化每美元/每瓦的生产性工作，而非只关注原始 FLOPS。

选择合适的加速器

优先考虑具有更佳每瓦性能和内存容量的现代 GPU。较新架构提供原生 FP8、FP4 精度支持等特性，以及更快的互连；与旧代 GPU 和系统相比，这些能力可带来显著加速。

利用高带宽互连

对于多 GPU 工作负载，应优先使用具备 NVLink/NVSwitch 的系统（如 GB200/GB300 NVL72），而不是仅有 PCIe 连接的系统。NVLink 5 的 GPU 间双向带宽最高可达 1.8 TB/s（超过 PCIe Gen5 的 14 倍），可能实现近线性 GPU 扩展。NVLink Switch 域可通过二级交换机扩展，在一个 NVLink 域中连接最多 576 块 GPU。这样可实现分层集合通信，尽可能保持在 NVLink 内，再回退到机架间网络。

平衡 CPU/GPU 与内存配比

为每张 GPU 配置足够的 CPU 核、DRAM 和存储吞吐量。例如，可为每张 GPU 分配约一个快速 CPU 核来承担数据加载和网络任务。确保系统 RAM 和 I/O 能以所需速率（每 GPU 数百 MB/s 量级）供给 GPU，避免其饥饿。

规划数据局部性

若跨多个节点训练，应最小化节点外通信。尽可能将紧耦合工作负载留在同一 NVLink/NVSwitch 域内以利用完整带宽，并使用可获得的最高速互连。理想情况下，节点内和机架内通信使用 NVLink，机架间通信使用 InfiniBand。

避免链路中的瓶颈

找出最慢环节——CPU、内存、磁盘或网络——并扩展它。例如，若 I/O 导致 GPU 利用率低，应投资更快存储或缓存，而不是增加更多 GPU。端到端设计中各组件良好匹配，可避免浪费 GPU 周期。

选择合适的集群规模

增加 GPU 时要警惕边际收益递减。超过某个集群规模后，开销会增长，应确保加速收益足以证明成本合理。通常应先提高 N 张 GPU 的利用率（例如达到 95%），再扩展到 2N 张 GPU。

面向散热与供电设计

确保数据中心能承受 GPU 的散热和供电需求。GB200/GB300 等高性能系统具有很高 TDP。应提供充足的散热（可能为液冷）和供电能力，使 GPU 能在不降频的情况下维持加速时钟。

统一 CPU-GPU“超级芯片”架构

统一内存和封装内链路能在将合适数据放在合适层级时容纳更大模型并降低拷贝开销。将 Grace 用于预处理、将 HBM 用于“热”张量，可使超级芯片成为停顿更少的紧耦合引擎。

在 Grace Blackwell 超级芯片上，应将 CPU 和 GPU 视为共享内存复合体。将热权重/激活保留在 HBM，将溢出或低频数据通过 NVLink-C2C 放入 Grace LPDDR。利用封装内 Grace CPU 进行预处理/编排，并采用预取或流水线管理内存来隐藏超大模型的延迟。可按以下方式利用超级芯片架构：

利用统一 CPU-GPU 内存

利用 Grace Blackwell（GB200/GB300）超级芯片的统一内存空间。两张 Blackwell GPU 与一颗 72 核 Grace CPU 通过 NVLink-C2C（900 GB/s）共享一致性内存池。可将 CPU 的大容量内存（例如 480 GB LPDDR5X）作为超大模型的扩展，同时将“热”数据保留在 GPU HBM 中以获得速度。

按局部性放置数据

即使采用统一内存，也应优先考虑数据放置。将模型权重、激活和其他频繁访问的数据放在具有更高本地带宽的 GPU HBM3e 中，让低频或溢出数据驻留在 CPU RAM。这样可避免 900 GB/s NVLink-C2C 链路成为关键数据的瓶颈。

在可用时利用 CPU-GPU 直接内存访问

在 GB200、GB300 等组合 CPU-GPU 超级芯片上，利用 GPU 直接访问 CPU 内存的能力。GPU 可经 NVLink-C2C 一致性地读写 Grace LPDDR 内存，无需经主机 PCIe 中转。其带宽和延迟仍逊于 HBM，因此应预取托管指针、分阶段准备数据并流水化传输以隐藏延迟。建议将热激活和 KV 缓存保留在 HBM，将 CPU 内存作为较低层级缓存并显式预取。

高效使用 Grace CPU

封装内 Grace CPU 提供 72 个高性能核心，应充分利用。将数据预处理、增强和其他适合 CPU 的任务卸载给这些核心。它们可通过 NVLink-C2C 快速供给 GPU，本质上充当 GPU 的超高速 I/O 和计算伙伴。

规划超大模型

对于超过 GPU 内存的万亿参数模型训练，GB200/GB300 系统允许将 CPU 内存作为模型内存池的一部分。优先使用框架的缓存分配器，并在自定义代码中使用 cudaMallocAsync 以减少碎片并启用图捕获。使用 CUDA Unified Memory 或托管内存 API 平稳处理溢出，并考虑显式预取即将使用的层（如 cudaMemPrefetchAsync），将数据从 CPU → GPU 内存分阶段迁移以隐藏延迟。

考虑针对超级芯片优化的算法

SuperOffload 是一组针对超级芯片优化的算法示例，重点提升卸载和张量转换/拷贝策略的效率。其创新包括先推测后验证（STV）、异构优化器计算和基于 ARM 的 CPU 优化器。SuperOffload 专为 NVIDIA 超级芯片（如 Grace Hopper、Grace Blackwell、Vera Rubin）设计；与传统卸载策略相比，可能提高 token 处理吞吐量和芯片利用率，具体收益取决于模型与实现。

多 GPU 扩展与互连优化

只有通信快速且具备拓扑感知时，扩展才有回报；否则新增 GPU 只会相互等待。应依托 NVLink/NVSwitch 带宽、现代集合通信和面向网络结构的放置，争取接近线性的加速。

具体而言，利用 NVLink/NVSwitch 域（如 NVL72）实现近线性扩展，并选择适配网络结构的并行策略。使用拓扑感知放置、更新的 NCCL 集合通信（如 PAT）和遥测数据，验证是否有效利用每 GPU 约 1.8 TB/s 的双向带宽；随规模扩展规划分层通信。以下是通过互连和拓扑优化利用多 GPU 扩展的建议：

面向高速全互连拓扑设计

例如，在拥有 72 张完全互连 GPU 的 NVL72 NVSwitch 集群上，任意 GPU 均可与其他 GPU 以完整 NVLink 5 速度通信。网络层面，NVLink Switch 域是无阻塞的；但应用层吞吐量会随并发流量和路径调度而变化，因此在假设每对 GPU 已饱和前，应使用 DCGM NVLink 计数器和 Nsight Systems 轨迹验证。可采用数据并行、张量并行和流水线并行等在较弱互连上可能受限的策略来利用该拓扑。

采用拓扑感知调度

在可能时，始终将多 GPU 作业共同放置在一个 NVLink Switch 域中。将作业的全部 GPU 保留在 NVL72 网络内，可使通信密集型负载接近线性扩展。跨 NVLink 域或标准网络混用 GPU 会引入瓶颈，紧耦合任务应避免这种做法。

利用高带宽

应认识到，NVLink 5 每张 GPU 每个方向可达 900 GB/s，相比前代使单 GPU 带宽翻倍。一个 NVL72 机架提供约 130 TB/s 的机架内总聚合带宽。这可显著降低通信等待时间；在 1.8 TB/s 条件下，即使数十 GB 梯度数据也可能在数毫秒内完成 all-reduce。应设计梯度同步、参数分片等训练算法，充分利用这种相对充裕的通信预算；实际带宽仍应以工作负载测量为准。

采用现代集合通信算法

使用针对 NVSwitch 优化的最新 NVIDIA NCCL 库。具体而言，可启用为 NVLink Switch 拓扑引入的并行聚合树（PAT）算法。它可利用 NVL72 拓扑，比其他树形/环形算法更高效地执行归约，从而进一步降低同步时间。

考虑细粒度并行

具备全带宽全互连时，可考虑此前不可行的细粒度模型并行。例如，当每张 GPU 与其他 GPU 都有 1.8 TB/s 双向吞吐量时，跨多 GPU 的逐层并行或张量并行可能很高效。过去可能会避免过多跨 GPU 通信，而 NVL72 允许更激进地划分工作且不轻易触及网络限制；实际效果仍受模型和流量模式影响。

监控是否饱和

尽管 NVL72 极快，性能分析时仍应关注链路利用率。若应用因极端 all-to-all 操作使 NVSwitch 饱和，可能需通过聚合梯度等方式限制通信。使用 NVIDIA 工具或 NVSwitch 遥测确认通信是否在 NVLink 容量范围内，并在必要时调整模式；例如可错开 all-to-all 交换以避免网络争用。DCGM 提供 NVLink 计数器，可帮助验证链路平衡并发现集合通信中的热点。

规划未来扩展

注意 NVLink Switch 可扩展到单机架之外：利用二级交换机，一个连接域最多可达 576 张 GPU。若以该超大规模运行，应规划分层通信，先使用本地 NVL72 的机架间集合通信，仅在必要时再使用机架间互连。这有助于优先最大化机架内 NVLink 使用，确保先利用最快链路，再退回机架间 InfiniBand 跳转。

识别联邦与分布式优化机会

对于跨异构环境的部署（如多云或边缘到云的设置），应采用自适应通信协议和动态负载均衡策略。这可在分布式系统中最小化延迟并最大化吞吐量，即使资源能力和容量不一致也能保持稳健性能。

操作系统与驱动优化

OS 抖动、NUMA 未命中和驱动不匹配会悄然吞噬吞吐量并造成难以通过调优消除的波动。强化软件栈（大页、亲和性、一致的 CUDA/驱动、持久化）可建立稳定、高性能的基线。

运行精简、面向 HPC 调优的 Linux。设置 NUMA/IRQ 亲和性，启用 THP 和较高 memlock 限制；保持各节点 NVIDIA 驱动/CUDA 一致；隔离系统抖动，调优 CPU 库和存储，正确设置容器限制，并及时更新 BIOS/固件/NVSwitch 网络以获得可预测吞吐量。以下是应在环境中探索的主机、OS 和容器优化：

使用针对 HPC 调优的 Linux 内核

确保 GPU 服务器运行配置为高性能计算的近期稳定 Linux 内核。禁用消耗 CPU 或 I/O 的非必要后台服务。使用“performance”CPU governor，而非“on-demand”或“power-save”，使 CPU 核保持高时钟以供给 GPU。

为性能关键负载禁用 swap

在训练服务器上禁用 swap 以避免页面抖动；若必须保留 swap，则使用 mlock 或 cudaHostAlloc 锁定关键缓冲区，确保其驻留在 RAM 中。

通过积极预分配避免内存碎片

为频繁使用的张量预分配大块连续内存，以减少运行时分配开销和碎片。这种主动策略可在长时间训练中实现更稳定、高效的内存管理。

调优 CPU 库环境变量

微调 OMP_NUM_THREADS、MKL_NUM_THREADS 等参数，使其更匹配硬件配置。调整这些变量可减少线程争用并提高 CPU 受限操作的并行效率。

面向 NUMA 感知设计

对于多 NUMA 服务器，将 GPU 进程/线程固定到本地 NUMA 节点的 CPU。使用 numactl 或 taskset 等工具，将每个训练进程绑定到离其分配 GPU 最近的 CPU；同样，将内存分配绑定到本地 NUMA 节点（numactl --membind），使 GPU DMA 的主机内存来自最近的 RAM。这可避免代价高昂的跨 NUMA 内存流量，后者可能使有效 PCIe/NVLink 带宽减半。

为网络和 GPU 任务使用 IRQ 亲和性

将 NIC 中断显式绑定到与 NIC 同一 NUMA 节点的 CPU 核；同样将 GPU 驱动线程固定到专用核心，包括 nvidia-persistence 服务守护进程等长期运行服务的线程。该策略可最小化跨 NUMA 流量，并在高负载下稳定性能。

启用透明大页

以 always 或 madvise 模式启用透明大页（THP），使大内存分配使用 2 MB 页面。这可在框架分配数十或数百 GB 主机内存时减少 TLB 抖动和内核开销。检查 /sys/kernel/mm/transparent_hugepage/enabled 以确认 THP 是否激活。启用 THP 后，进程会为大分配使用大页；若负载对延迟敏感且观察到抖动，优先使用 madvise 模式。

提高最大锁定内存

配置 OS 以允许大量页锁定内存分配。GPU 应用常为更快传输锁定内存——设置 ulimit -l unlimited 或较高值，使数据加载器可分配页锁定缓冲区而不触及 OS 限制。这可避免失败或回退到可分页内存，后者会拖慢 GPU DMA。

使用最新的 NVIDIA 驱动和 CUDA 栈

在所有节点上保持 NVIDIA 驱动和 CUDA runtime 处于经过测试的稳定版本范围内的新版本。新驱动可带来性能改进，也是新 GPU 计算能力所必需。确保所有节点具有相同驱动/CUDA 版本，以避免多节点作业发生不匹配。启动时为 GPU 启用持久化模式（nvidia-smi -pm 1），使驱动保持加载并避免 GPU 重新初始化延迟。在所有节点更新 NVIDIA 驱动和工具包，以获取 bug 修复和性能改进。

使用 MIG 配置时启用 GPU 持久化

启用持久化模式后，GPU 保持“预热”并可随时使用，可降低作业启动延迟。若使用 Multi-Instance GPU（MIG）分区，这尤其关键：没有持久化时，MIG 配置会在每个作业后重置；保持驱动活跃则能保留切片。使用 MIG 时应始终配置持久化模式。

隔离系统任务

在每台服务器上专门保留一个或少量核心用于 OS 日常任务，如中断处理和后台守护进程。这样，负责供给 GPU 的主 CPU 线程不会被中断。可通过 CPU isolation 或 cgroup 固定来实现。消除 OS 抖动可确保吞吐量一致。

优化系统 I/O 设置

若负载执行大量日志记录或检查点，应使用有利于吞吐量的选项挂载文件系统。可为数据磁盘使用 noatime，并为流式读取增加文件系统预读。确保为 NVMe SSD 正确设置磁盘调度器，使用 mq-deadline 或 noop 以降低延迟波动。

执行定期维护

保持 BIOS/固件更新以获得性能修复。某些 BIOS 更新可改善 PCIe 带宽，或修复 GPU 的输入输出内存管理单元（IOMMU）问题。还应定期检查 NIC 和适用的 NVSwitch/Fabric 固件更新，以及 NVIDIA 提供的 Fabric Manager 升级等。微小的固件调整有时可解决隐蔽瓶颈或可靠性问题。

调优 Docker 和 Kubernetes 配置以获得最高性能

在容器中运行时，添加用于共享内存的 --ipc=host 等选项，并设置 --ulimit memlock=-1 以避免内存锁定问题。这可确保容器化进程访问内存时不受 OS 施加的限制。

GPU 资源管理与调度

更智能的放置与分区可在不购买新硬件的情况下提高利用率，并为混合负载保持可预测性。应尊重拓扑，在合适场景使用 MPS/MIG，并控制时钟/功耗以减少争用和尾延迟。

调度时考虑 GPU/NUMA/NVLink 拓扑；对较小作业使用 MPS 或 MIG 提高利用率，同时保留 ECC 和持久化以保证可靠性。需要稳定性时锁定时钟或设定功耗上限，避免 CPU 过度订阅，并智能地打包作业以在无争用条件下最大化 ROI。以下是 GPU 资源管理与调度建议：

拓扑感知的作业调度

确保 Kubernetes、SLURM 等编排器将容器调度到遵守 NUMA 和 NVLink 边界的节点上，以最小化跨 NUMA 和跨 NVLink 域的内存访问。这种对齐可降低延迟并改善总体吞吐量。

多进程服务（Multi-Process Service，MPS）

在单张 GPU 上运行多个进程时启用 NVIDIA MPS 以提高利用率。MPS 允许来自不同进程的内核在 GPU 上并发执行，而非时间片轮转。当单个作业未充分饱和 GPU 时这很有用——例如，在一张 GPU 上使用 MPS 运行 4 个训练任务可使其工作重叠并提升总体吞吐量。

多实例 GPU（Multi-Instance GPU，MIG）

使用 MIG 将高端 GPU 分割为更小实例，供多个作业使用。若有小模型推理或大量实验等轻负载，可将 GPU 切片，为每个作业保证资源。例如，现代 GPU 可分成多个 MIG 切片（最多 7 个）。不要对紧耦合并行作业使用 MIG，因为它们受益于完整 GPU 访问。当作业规模小于整张 GPU 时，可部署 MIG 实现隔离并最大化 GPU ROI。

MIG 的持久化

保持持久化模式开启，以在作业之间保留 MIG 分区。这可避免重新分区开销，并确保后续作业无需延迟即可看到预期 GPU 切片。应在集群启动时配置 MIG 并保持启用，使调度可预测；因为动态修改 MIG 配置需要重置 GPU，可能中断正在运行的作业。需规划维护窗口，因为 GPU 重启后不会保留 MIG 设备分区。使用 NVIDIA MIG Manager 可在启动时自动重建所需布局。

GPU 时钟与功耗设置

若需要运行间一致性，可考虑使用 nvidia-smi -lgc/-lmc 将 GPU 时钟锁定到固定高频。默认情况下 GPU 使用自动加速，通常是最优选择；但固定时钟可避免瞬态降频。在功耗受限场景，可略微降频或设置功耗上限，让 GPU 保持在稳定的热/功耗包络内；若偶发降频是问题，这可能获得更一致的性能。

ECC 内存

除非有明确理由禁用，否则应在数据中心 GPU 上保持 ECC 启用以确保可靠性。其性能代价很小——内存带宽和容量可能损失几个百分点——但 ECC 可捕获否则会损坏长时间训练作业的内存错误。大多数服务器 GPU 出厂时默认启用 ECC；应保持开启以保护多周训练。

作业调度器感知

将 GPU 拓扑集成到 SLURM、Kubernetes 等作业调度器。需要低延迟耦合时，将调度器配置为在同一节点或同一 NVSwitch 组分配作业。使用 Kubernetes 设备插件或 SLURM Gres 为小作业调度 MIG 切片。GPU 感知调度器可避免单个作业跨越相距很远的 GPU 并遭受带宽问题。

CPU 过度订阅

调度作业时，应考虑每个 GPU 任务所需的 CPU 资源，如数据加载线程等。不要在一个节点上打包超过 CPU 承受能力的 GPU 作业。与其过载 CPU 导致所有 GPU 供给不足，不如让一张 GPU 空闲。监控每个 GPU 作业的 CPU 利用率，为调度决策提供依据。

为 NVSwitch 使用 NVIDIA Fabric Manager

在具备 NVSwitch 的系统（如 GB200/GB300 NVL72 机架）上，确保 NVIDIA Fabric Manager 正在运行。它管理 NVSwitch 拓扑与路由。没有它，多 GPU 通信可能无法充分优化，甚至在大型作业中失败。Fabric Manager 服务通常在配备 NVSwitch 的服务器上默认运行，但仍应确认已启用且正在运行，特别是在驱动更新后。

面向利用率的作业打包

通过智能打包作业最大化利用率。例如，在一个 4-GPU 节点上，若有两个 CPU 使用不多的 2-GPU 作业，在同一节点共同运行可节省资源；若位于同一计算节点或支持 NVLink 的机架中，还可使用更快的 NVLink 通信。相反，应避免共同放置后合计超过节点内存或 I/O 容量的作业。目标是在无争用条件下实现高硬件利用率。

I/O 优化

若数据跟不上，GPU 就会空闲——通常最大、最便宜的加速来自修复输入，而非数学计算。并行化、页锁定内存、异步传输和快速存储可确保模型持续得到供给。

通过并行化数据加载器、使用页锁定内存和异步传输、并将数据存储在快速 NVMe（最好配合 GPUDirect Storage）上来持续供给 GPU。合理进行条带化、缓存和压缩。测量端到端吞吐量，使 I/O 随集群规模扩展；异步写入检查点/日志。以下是数据流水线 I/O 优化建议：

并行加载数据

使用多个 worker/线程为 GPU 加载和预处理数据。默认的一到两个数据加载 worker 可能不足。通过 PyTorch DataLoader(num_workers=N) 等方式进行性能分析并增加数据加载进程/线程数，直至数据输入不再是瓶颈。高核心数 CPU 的存在就是为了供给 GPU，务必充分利用。

为 I/O 锁定主机内存

为数据传输缓冲区启用页锁定内存。许多框架提供类似 PyTorch DataLoader 的 pin_memory=True 选项，用于分配 GPU 可直接 DMA 访问的主机内存。使用页锁定内存可显著提高 H2D 拷贝吞吐量；结合异步传输可让数据加载与计算重叠。

重叠计算与数据传输

将输入数据流水化。GPU 正在计算 batch N 时，在 CPU 上加载和准备 batch N+1，并使用 CUDA stream 与非阻塞 cudaMemcpyAsync 在后台传输。这种双缓冲隐藏延迟——理想情况下 GPU 永不等待数据。确保训练循环使用异步传输；例如在 PyTorch 中，可用 non_blocking=True 将张量拷贝到 GPU。异步传输使 CPU 能在后台数据传输期间继续运行，从而通过重叠计算和数据传输提高性能。

使用快速存储（NVMe/SSD）

将训练数据存于快速本地 NVMe SSD 或高性能并行文件系统。机械磁盘会严重限制吞吐量。若可用，启用 GPUDirect Storage（GDS），使 GPU 能从 NVMe 或网络存储直接流式读取数据，绕过 CPU。这会在读取大型数据集时进一步降低 I/O 延迟和 CPU 负载。对于大型数据集，可让每个节点拥有数据的本地副本或分片。若使用网络存储，优先采用支持条带化的 Lustre 等分布式文件系统，或能并行服务许多客户端的对象存储。

调优 I/O 并发与条带化

避免单文件访问造成的瓶颈。若所有 worker 使用同一个大文件，可跨多个存储目标对其进行条带化，或将其拆分为块以供多台服务器服务。例如，将数据集拆为多个文件，让每个数据加载 worker 同时读取不同文件；这可最大化存储系统的聚合带宽。

优化小文件访问

若数据集由数百万小文件组成，应减轻元数据开销。每秒打开过多小文件会压垮文件系统的元数据服务器。解决方式包括将小文件打包进 tar 或 RecordIO 等较大容器，使用批量读取的数据摄取库，或确保客户端启用元数据缓存。这可降低每文件开销并加快 epoch 启动时间。

可用时使用客户端缓存

利用任何可用缓存层。若使用 NFS，可增加客户端缓存大小和持续时间；对于分布式文件系统，可考虑缓存守护进程，甚至手动将部分数据集缓存到本地磁盘。目标是避免从慢速源反复读取相同数据。若各节点在不同时间处理相同文件，本地缓存可大幅减少冗余 I/O。

明智地压缩数据

若 I/O 是瓶颈，可压缩存储数据集，但应使用 LZ4 或 Zstd 快速模式等轻量压缩。这会牺牲少量 CPU 以减少 I/O 数据量。若解压使 CPU 成为瓶颈，可考虑多线程解压或卸载到加速器。还可让一个线程读取压缩数据、另一个线程并行解压，使解压与读取重叠。现代 GPU 搭配 GPUDirect Storage 和 cuFile I/O 栈时，可利用 GPU 计算资源（或图像/视觉数据专用解码器）即时解压数据。

测量吞吐量并消除瓶颈

持续监控数据流水线吞吐量。若 GPU 利用率未接近 100%，且怀疑存在输入延迟，应测量磁盘读取 MB/s 以及数据加载核心的繁忙程度。dstat、NVIDIA DCGM 等工具可揭示 GPU 是否在等待数据。系统性地调优每个组件，例如增加预取缓冲区、网络缓冲区大小、优化磁盘 RAID 设置等，直到输入流水线供给数据的速度与 GPU 消耗速度一致。消除 I/O 停顿后，这些优化常能在相同硬件上将 GPU 利用率从约 70% 提升到 >95%。

为多节点扩展 I/O

在集群规模下，确保存储系统可承受聚合吞吐量。例如，8 张 GPU 每张消耗 200 MB/s，则每节点为 1.6 GB/s；100 个节点需要 160 GB/s。极少有中心化文件系统能持续提供该性能。可通过跨存储服务器分片数据、使用每节点缓存或将数据预加载到各节点本地磁盘来缓解。以存储空间换取吞吐量（如保存多份数据）通常值得，可避免昂贵 GPU 缺料。

最小化检查点与日志开销

高效写入检查点和日志。若可行，对检查点使用异步写入，或先写入本地磁盘再复制到网络存储，以避免训练停顿。压缩检查点或使用稀疏存储格式以减小大小。通过聚合迭代统计数据并仅每 N 次迭代记录一次，而非每次记录，限制逐步日志频率；这会大幅降低 I/O 开销。

还可使用 cuda-checkpoint 和 Checkpoint/Restore in Userspace（CRIU）挂起运行中的 GPU 进程，以持久化进程映像。准备恢复时，CUDA 驱动可恢复设备内存和 CUDA状态，甚至恢复到同一设备类型的其他 GPU。应将其视为模型 state-dict 或分片检查点文件的补充，而非替代品。

数据处理流水线

数据格式、布局和局部性决定流水线在规模化运行时是否顺畅。二进制格式、分片、缓存和高优先级线程能将 I/O 从瓶颈转为稳定的数据流。

将数据集转换为二进制或内存映射格式，跨存储和节点分片；提高线程优先级或将简单增强移到 GPU 以防止停顿。缓存热数据/KV 状态，积极预取和缓冲，并设置合适 batch 大小，使流水线从磁盘到设备始终顺畅。以下是改进数据处理的建议：

使用二进制数据格式

将数据集转换为 TFRecords、LMDB 或内存映射数组等二进制格式。这可减少处理数百万小文件的开销，并加速数据摄取。

调优文件系统

除使用 noatime 挂载文件系统并增加预读外，还应考虑跨多个存储节点分片数据，以分摊 I/O 负载并避免单台服务器成为瓶颈。

为 CPU 受限负载禁用超线程

对于高度 CPU 受限的数据流水线，禁用超线程可减少资源争用并带来更一致的性能。这对单线程性能关键的系统尤其有益。

提高线程优先级

使用 chrt 或 pthread_setschedparam 等工具提高数据加载和预处理 CPU 线程的调度优先级。赋予这些线程更高优先级，可确保以最低延迟向 GPU 供给数据，降低流水线停顿概率。

缓存频繁使用的数据

利用操作系统页面缓存或专用 RAM 磁盘缓存频繁访问的数据。这对 NLP 等应用尤其有益，其中某些 token 或短语会被反复访问，可减少冗余处理和 I/O 开销。

预取和缓冲数据

始终在需要某次迭代前提前加载数据。使用后台数据加载线程或进程，例如带 prefetch_factor 的 PyTorch DataLoader。对于分布式训练，使用 DistributedSampler 确保每个进程获得唯一数据，避免冗余 I/O。

并行化数据转换

若图像增强、文本 token 化等 CPU 预处理负担很重，应将其分发到多个 worker 线程/进程。进行性能分析以确保 GPU 等待时 CPU 不是瓶颈。若是，可增加 worker，或将部分转换移至 GPU；NVIDIA DALI 等库可在 GPU 上异步执行图像操作。

缓存模型状态与输出

使用 LLM 推理时，缓存频繁出现 token 的嵌入和 V 缓存有助于避免反复重新计算。同样，若 LLM 训练作业多次复用相同数据集（称为 epoch），应利用 OS 页面缓存或 RAM 存储热数据。

跨节点分片数据

在多节点训练中，为每个节点分配数据子集，避免所有节点从同一源读取完整数据集，从而横向扩展 I/O。可使用分布式文件系统，或手动分配分片使各节点读取不同文件。这不仅加速，还天然符合数据并行，因为每个节点处理自己的数据分片。DeepSeek 的 Fire-Flyer File System（3FS）是分布式数据集分片文件系统示例。其通过将数据集分片分布在每个节点的 NVMe SSD 上、同时尽量减少传统缓存，达到每秒数 TB 吞吐量；该设计以本地高速数据供给每张 GPU，避免 I/O 瓶颈。

监控流水线并调整 batch 大小

有时增大 batch 大小会将更多工作推给 GPU、降低 I/O 频率，从而提高总体利用率；但会影响收敛，因此只能增加到一定程度。相反，若 GPU 经常等待数据且无法加快 I/O，可能应减小 batch 以缩短每次迭代、减少空闲时间，或对较小 batch 做梯度累积，使数据读取更连续。应找到让 GPU 几乎始终忙碌的平衡点。

在 GPU 上应用数据增强

若增强操作简单但应用于海量数据，如添加噪声或归一化，可能值得在 GPU 上执行以避免饱和 CPU。数据加载期间 GPU 往往未充分利用，因此加载后用小型 CUDA 内核增强数据可能高效；但需注意不要将流水线串行化。使用 stream，在 batch N 训练时重叠 batch N+1 的增强。利用 NVIDIA DALI 等 GPU 加速库异步执行这些任务，有助于保持平滑、高吞吐的数据流水线。

关注端到端吞吐量（如每秒 token 数）

请记住，若数据流水线将吞吐量减半，加速模型计算并无帮助。始终进行端到端分析，而非只孤立分析训练循环。使用 Nsight Systems、Nsight Compute 测量内核时间线和停顿，或使用 PyTorch 分析器进行框架层归因。随后比较合成数据与真实数据的迭代时间，了解数据加载引入多少开销。目标是使开销低于理想值的 10%；若超过，应投入时间优化流水线，因为这常能为训练带来巨大的“免费”加速。

性能分析、调试与监控

无法优化未曾测量的内容；性能分析可揭示负载究竟受计算、内存、I/O 还是网络限制，从而针对正确问题修复。随着代码、驱动和数据演进，持续遥测和回归测试可防止性能收益流失。

具体而言，使用带 NVTX 的 Nsight Systems/Compute 和框架分析器，确定负载是否受计算、内存、I/O 或通信限制。减少 Python 开销、观察利用率空隙、平衡各 rank 的工作、追踪内存/网络/磁盘健康状况，并用性能回归测试和告警作为变更门槛。可按以下建议分析、监控和调试 AI 工作负载性能：

性能分析以发现瓶颈并进行根因分析

定期对训练/推理作业运行分析器。使用 NVIDIA Nsight Systems 获取 CPU 和 GPU 活动时间线；还可用 Nsight Compute 或 PyTorch 分析器深入查看内核效率。确定作业是计算受限、内存受限，还是在等待 I/O/通信，并据此优化。例如，内存受限负载应专注减少内存流量，而非实施计算受限型优化。还可结合机器学习驱动的分析预测并预防性能瓶颈，帮助实时自动化微调。使用 GPUDirect Storage 时，启用 GDS 跟踪以关联 cuFile 活动与内核空隙。

消除 Python 开销

分析训练脚本，识别过度循环或日志记录等 Python 瓶颈，并用向量化操作或优化库调用替换。最小化 Python 开销有助于确保 CPU 不会成为整体系统性能中的隐藏瓶颈。

测量 GPU 利用率与空闲间隙

持续监控 GPU 利用率、SM 效率、内存带宽使用等。若发现利用率周期性下降，应将其与事件关联。例如，每 5 分钟一次的利用率下降可能与保存检查点同步。这类模式指向错开检查点、使用异步刷新等优化机会。使用 DCGM 或守护模式的 nvidia-smi 随时间记录这些指标。

使用 NVTX 标记

使用 NVTX 区间或框架性能分析 API 为代码插桩，标记数据加载、前向传播、反向传播等不同阶段。这些标记会出现在 Nsight Systems 或 Perfetto 时间线上，帮助将 GPU 空闲时间或延迟归因到流水线的具体部分，也便于向开发者说明哪段代码需要关注。对于 PyTorch，可使用 torch.profiler.record_function()。

除 PyTorch 分析器外使用内核分析工具

对于性能关键内核，使用 Nsight Compute 检查 occupancy、吞吐量等内核级指标，或使用 Nsight Systems 分析 GPU/CPU 时间线及重叠情况。检查实际 occupancy、内存吞吐量和指令吞吐量，寻找内存带宽接近硬件最大值等内存瓶颈迹象，以识别内存受限负载。分析器的“Issues”部分通常会直接指出内核是否受内存或计算限制及其原因。使用这些反馈指导代码变更，例如全局加载效率低时改善内存合并访问。

检查 warp 分歧

使用分析器查看 warp 是否发生分歧，它可显示分支效率和分歧分支指标。分歧意味着 warp 中部分线程因分支而不活跃，会损害吞吐量。若影响显著，应重新审视内核代码，重构条件逻辑或数据分配以最小化 warp 内分歧，并确保每个 warp 处理一致的工作。

验证负载均衡

在多 GPU 作业中跨各 rank 进行分析。有时一张 GPU（rank 0）负责汇总统计和收集数据等额外工作，常会成为瓶颈。监控每张 GPU 的时间线；若某张 GPU 持续落后，应分散这些额外工作。例如，可让非零 rank 分担 I/O 和日志职责。确保所有 GPU/rank 负载相近，避免最慢 rank 拖累其余部分。

监控内存使用

随时间跟踪 GPU 内存分配与使用。确保不接近 OOM，否则框架可能意外将张量换出至主机，造成巨大减速。若内存使用逐次迭代上升，很可能发现了泄漏；此时使用 torch.cuda.memory_summary()、Nsight Systems 的 GPU 内存跟踪等工具分析详细分配。在 CPU 侧监控分页，因为进程常驻内存（RES）不应显著超过物理 RAM。若观察到分页，应减少数据集预加载量或增加 RAM。

监控网络与磁盘

对于分布式作业，使用 OS 工具监控网络和磁盘吞吐量，确保实际吞吐量符合预期。例如，若 100 Gbps 链路完全利用，应看到 12.5 GB/s（12.5 GB/s = 100 Gb/s ÷ 每字节 8 bit）。若达不到，网络可能是瓶颈或配置错误。同样监控训练节点的磁盘 I/O；若看到磁盘利用率 100% 的尖峰同时 GPU 空闲，可能需要更好地缓冲或缓存数据。

为异常设置告警

在生产或长时间训练场景中，为 ECC 错误、设备过热等 GPU 错误事件设置自动告警或日志，有助于识别异常缓慢的迭代。例如，NVIDIA DCGM 可监测健康指标；若 GPU 开始降频或发生错误，可触发操作。这样能立即捕获散热故障导致降频等性能问题，而非等作业结束后才发现。

执行回归测试

维护一组基准任务，在更改软件（包括 CUDA 驱动、CUDA 版本、AI 框架版本甚至训练代码）时运行。将性能与先前运行比较，尽早捕获回退。驱动更新或代码改动无意中降低吞吐量并不罕见；在标准负载上快速分析即可凸显问题以便调查。例如，某个内核可能意外不再使用 Tensor Core，这显然需要排查。

GPU 编程与 CUDA 调优优化

让内核与内存层次结构及硬件特性相匹配，才能取得显著且持久的收益。融合、Tensor Core、CUDA Graph 以及编译器路径（如 torch.compile 和 OpenAI Triton）可将启动开销转化为有效计算。

围绕内存层次结构优化：合并全局内存加载、分块载入共享内存、管理寄存器与占用率，并将传输（如 cp.async/TMA）与计算重叠。优先采用经过调优的库和 CUDA Graph，借助 torch.compile 与 OpenAI Triton 实现融合，并通过屋顶线分析和 PTX/SASS 检查验证可扩展性。以下是一些 GPU 与 CUDA 编程优化提示和技术：

理解 GPU 内存层次结构

请牢记 GPU 的分层内存结构：每线程的寄存器、每个块/SM 的共享内存与 L1 缓存、跨 SM 的 L2 缓存，以及全局 HBM。在较高层级中尽可能复用数据。例如，使用寄存器和共享内存复用数值，并减少对较慢全局内存的访问。好的内核会确保绝大多数数据要么位于寄存器中，要么通过合并访问和缓存从 HBM 高效加载。

合并全局内存访问

确保同一 warp 内的线程访问连续内存地址，使硬件能以尽可能少的事务完成服务。warp 线程的跨步或离散内存访问会使每个 warp 产生多次内存事务，从而实际浪费带宽。应重组数据布局或索引计算，使 warp 每次加载数据时都能通过一次宽内存事务完成。

使用共享内存复用数据

共享内存类似带宽极高、由开发者手动管理的缓存。将频繁使用的数据（如矩阵分块）载入共享内存，让线程在继续处理前多次操作这些分块。这种常见的分块技术可大幅减少全局内存流量。注意共享内存的 bank 冲突：应组织共享内存访问模式或填充数据，确保线程不会竞争同一 memory bank，否则访问会被串行化并降低性能。

优化内存对齐

尽可能将数据结构按 128 字节对齐，尤其是批量内存复制或向量化加载时。即使理论上已合并，未对齐访问仍可能迫使硬件执行多次事务。对全局内存 I/O 使用 float2、float4 等向量类型可让每条指令加载或存储多个值，但必须确保数据指针正确对齐到该向量大小。

尽量减少内存传输

仅在必要时向 GPU 传输数据，并尽量以大块传输。若可以，应将许多小传输合并为一次大传输。例如，如果每次迭代都要发送许多小数组，可将它们打包到一个缓冲区中一次发送。小而频繁的 cudaMemcpy 会成为瓶颈。若使用统一内存（Unified Memory），请使用显式预取（cudaMemPrefetchAsync）在需要前将数据调入 GPU，以避免关键计算阶段发生按需缺页。

避免过多的临时分配

频繁分配和释放 GPU 内存会损害性能。例如，在内核中频繁使用 cudaMalloc/cudaFree 或设备端 malloc 会带来额外开销。应复用内存缓冲区，或使用 PyTorch 等大多数深度学习框架提供的内存池（其实现了 GPU 缓存分配器）。若编写自定义 CUDA 代码，可考虑将 cudaMallocAsync 与内存池配合使用，或自行管理临时内存池，以避免反复分配/释放的开销。

平衡线程与资源使用

实现良好的占用率—资源平衡。增加线程以提高占用率有助于隐藏内存延迟，但若每线程使用过多寄存器或共享内存，占用率便会下降。调优内核启动参数（包括每块线程数），以确保有足够多正在执行的 warp 来掩盖延迟，但也不能多到使每线程缺少寄存器或共享内存。对于指令级并行性（ILP）高的内核，为提高占用率而减少寄存器使用反而可能损害性能。最佳点通常位于占用率区间中部，因为最大占用率并不总是理想选择。可使用 NVIDIA Nsight Compute 占用率计算器（Occupancy Calculator） 试验各种配置。

监测寄存器和共享内存用量

使用 Nsight Compute 等剖析工具持续监测每线程的寄存器和共享内存消耗。若观察到占用率低于 25%，可考虑增加每块线程数，以更充分利用可用硬件资源。不过，应通过详细的占用率报告和内核执行指标，确认此调整不会造成过多寄存器溢出。寄存器溢出会带来额外内存流量并降低整体性能。

将内存传输与计算重叠

尽可能将内存传输与计算重叠。在多个 CUDA 流中使用 cudaMemcpyAsync，在内核运行时进行预取。批量移动到共享内存时优先使用 Tensor Memory Accelerator；细粒度的分阶段复制和预取则使用 cp.async。这些方法通过把数据传输与计算重叠，可有效掩盖全局内存延迟，确保 GPU 核心无需等待内存操作完成而保持充分利用。

可行时使用批量预取

对于可预测的模式，可通过 PTX cp.async.bulk.prefetch.tensor.[1–5]d.L2.global*（或 prefetch.global.L2 系列）预取到 L2，并使用 TMA（例如 cp.async.bulk.tensor）将分块暂存到共享内存。也可用 cp.async 异步地将全局内存暂存至共享内存，使复制与计算重叠；还可在使用前显式将数据加载到寄存器中。这些主动方法可减少全局内存访问造成的延迟，确保关键数据恰好在需要时位于寄存器或共享内存等更快、延迟更低的存储中，从而最小化执行停顿并提高整体内核效率。

利用协作组

使用 CUDA 协作组，在部分线程之间实现高效的局部同步，而不是强制整个线程块的屏障。这项技术能对同步进行更细粒度控制，减少不必要的等待时间和开销。将共享数据或执行相关计算的线程编成组后，只需同步确实需要协调的线程，从而形成更高效的执行模式并提升整体吞吐量。

优化 warp 分歧

应组织代码，使一个 warp 内的线程尽量遵循相同执行路径。分歧可能使该 warp 的执行时间翻倍，例如半个 warp（16 个线程）走一个分支，另半个 warp（16 个线程）走另一个分支。若某些分支只被少量数据触发，可考虑对数据“排序”或分组，让 warp 处理一致的情况，使其全部为真或全部为假。使用 ballot、shuffle 等 warp 级原语可为某些问题构建无分支方案。将 warp 视为工作单元，力求全部 32 个线程以锁步方式执行相同工作，以获得最高效率。

利用 warp 级操作

适当时使用 CUDA 的 warp 内置函数，让线程无需经由共享内存即可通信。例如，使用 __shfl_sync 向 warp 中全部线程广播一个值，或执行 warp 级归约（如对整个 warp 的寄存器求和），而非让每个线程写入共享内存。这些内置函数绕过较慢的内存，可加速能在 warp 内完成的归约、扫描等算法。在 warp 内处理这些任务，便可避免共享内存和整块同步相关的延迟。

使用 CUDA 流实现并发

在单个进程/GPU 内，若独立内核未占满所有资源，可在不同 CUDA 流中启动它们以重叠执行。可让计算与计算重叠，例如一个流计算模型的一部分，另一个流启动独立内核（如 GPU 上的数据预处理）或异步 memcpy。注意依赖关系，并在需要时用 CUDA 事件同步。正确使用流可避免任何资源闲置，从而提高 GPU 利用率，尤其适用于较轻的内核。

优先使用库函数

尽可能使用 NVIDIA 针对核心数学和集合通信操作优化的库，如 cuBLAS、cuDNN、Thrust 和 NCCL。在分布式推理中进行点对点 GPU 数据移动时，可用时请使用 NIXL；需要 GPU 发起的细粒度传输时也可使用 NVSHMEM。这些库针对每代 GPU 架构都经过深度优化，性能通常接近理论“光速”峰值，因此无需自行重复实现。例如，除非具有非常特殊的模式，否则应使用 cuBLAS GEMM 完成矩阵乘法而不是自定义内核。库还会透明地处理新硬件特性。PyTorch（及其编译器）等 AI 框架在底层就使用了这些优化库。

为重复启动使用 CUDA Graph

若静态训练循环会启动数千次，可考虑使用 CUDA Graph 捕获操作序列并以图形式启动。这能显著降低每次迭代的 CPU 启动开销，尤其是在多 GPU 场景中：启动大量内核和 memcpy 会给 CPU 带来额外压力和延迟。

检查可扩展性限制

优化内核时，应定期检查其随问题规模增长以及跨架构的扩展表现。一个内核可能在小输入上拥有优异占用率和性能，却难以扩展到大输入，因为此时可能开始频繁扰动 L2 缓存或遭遇内存缓存驱逐。使用屋顶线分析，将实际 FLOPS 和带宽与硬件上限比较，确保没有遗漏可获得的性能。

检查 PTX 和 SASS 以进行高级内核分析

对于性能关键的自定义 CUDA 内核，请使用 Nsight Compute 检查生成的 PTX 和 SASS。此类深入分析可揭示内存 bank 冲突、冗余计算等问题，并引导你进行有针对性的底层优化。

使用 PyTorch 编译器

利用 PyTorch 的 torch.compile，通过 TorchInductor 将 Python 层操作融合为优化内核。编译器还可通过整合 CUDA Graph 降低启动开销。优化预热后，通常可获得约 10%–40% 的提升。这消除了解释器开销，并解锁编译器级优化。

实践中，启用 torch.compile 会自动组合内核，并更高效地利用 NVIDIA GPU 硬件（如 Tensor Core），已为许多模型带来显著加速（例如 20%–50%）。务必在你的模型上测试编译模式。它虽可大幅提高吞吐量，但部署前应确保兼容性和正确性。图稳定后，启用 CUDA Graph 以降低每次迭代的 CPU 开销；同时维持静态内存池，以满足指针稳定性约束。

为动态形状做好规划

若输入大小会变化，可用 torch._dynamo.mark_dynamic() 标注动态维度，或用 torch.export() 导出形状多态图，再进行编译。使用 torch.compiler.set_stance() 配合 "fail_on_recompile"，以及 torch._dynamo.error_on_graph_break()，控制重新编译行为，并在测试和 CI 中暴露有问题的形状频繁变化。可行时使用静态形状，以启用 CUDA Graph 并降低每次迭代的 CPU 开销。

通过 torch.compile 利用 Triton 内核

若 PyTorch 未能很好地融合某项操作，可考虑用 Triton 编写并整合自定义 GPU 内核。PyTorch 可通过 torch.library.triton_op 轻松注册自定义 GPU 内核。

可用时使用自动调优

启用库的自动调优功能以最大化底层性能。例如，在输入大小固定时设置 torch.backends.cudnn.benchmark=True。这会让 NVIDIA cuDNN 库尝试多种卷积算法，并为你的硬件选择最快的一种。一次性开销会换来可加速训练和推理的优化内核。若不要求严格可复现性，可关闭 cudnn.deterministic 以允许非确定性算法，从而解锁这些更快的实现。

利用只读路径

将常用常量或系数标记为只读，以便 GPU 将其缓存在专用的 L1 只读缓存中。在 CUDA C++ 中，可使用 const __restrict__ 指针提示数据不可变。在现代 GPU 架构上，编译器会为带 const __restrict__ 限定符的指针生成带缓存的全局加载。使用 AI 框架和库时，应确保查找表或静态权重位于设备上并被视为常量。此优化可减少这些值的全局内存流量和延迟，因为每个 SM 可从缓存快速读取，而非反复访问较慢的 DRAM。

内核调度与执行优化

启动开销和不必要的同步会造成闲置间隙，严重损害吞吐量。融合小内核并使用持久化/动态策略，能让设备保持忙碌并隐藏延迟。

通过最小化同步、融合小内核，并在反复启动相同工作时使用持久化内核，使设备保持忙碌。对于不规则任务，可考虑 GPU 动态并行，但应审慎使用以免增加开销。以下是改善内核调度和执行的提示：

最小化 GPU 同步调用

避免使 GPU 进度停滞的不必要全局同步。过度使用 cudaDeviceSynchronize() 或阻塞式 GPU 操作（如同步内存复制），会插入 CPU 与 GPU 均无法有效工作的空闲间隙。只在绝对必要时同步，例如传输最终结果或调试时。让异步操作排队，可保持 GPU 忙碌，并让 CPU 腾出时间准备后续工作，从而形成更连续的执行流水线。

融合小内核以摊销启动开销

若有许多微小 GPU 内核连续启动，应尽可能将其操作合并到一个内核中运行。每次内核启动都有数十微秒量级的固定成本；通过手动 CUDA 内核融合、XLA 融合，或借助 NVIDIA CUTLASS/Triton 等工具处理自定义操作，可提升吞吐量。融合内核将更多时间用于实际工作，较少时间耗在启动开销或内存往返上。这尤其适合可一次执行一串逐元素操作的推理或预处理流水线。先尝试 torch.compile(mode="reduce-overhead")：编译器能融合操作链，并将稳定区域封装到 CUDA Graph 中，从而降低 CPU 启动开销。对于未融合的热点，可考虑迁移到 Triton 内核，并在适用时使用异步 TMA 和自动 warp 专用化。

利用 GPU 动态并行进行 GPU 内部工作调度

使用 CUDA 动态并行，让 GPU 内核可直接从 GPU 启动其他内核而无需返回 CPU。在不可预测或迭代性工作中，例如算法需根据中间结果生成额外任务时，动态并行通过移除 CPU 启动瓶颈来降低延迟。例如，父内核可在设备上直接划分并启动子内核进行进一步处理。这使整个工作流留在 GPU 上，避免 CPU 介入并实现更好的重叠和利用率。不过应审慎使用，过度使用会引入自身开销。

为重复工作负载使用持久化内核

当工作负载涉及快速连续启动相同内核时（如处理工作队列，或处理具有相同计算的流式批次），可采用持久化内核策略。持久化内核只启动一次并保持活跃，在循环中复用线程处理许多工作单元，而不是为每个单元重新启动内核。这种方式以更复杂的内核设计换取显著更低的调度开销。保持内核存活可避免反复启动成本，并获得更高的持续占用率。高性能分布式训练和推理系统经常使用该技术，以最大化吞吐量并最小化迭代任务延迟。

评估线程块集群

使用线程块集群以保持数据接近并减少重复启动开销。在 Blackwell 上，最多 16 个线程块可组成一个集群（提高非可移植限制后）。在持久化风格的设计中，使用集群感知同步和共享内存驻留来改善局部性。借助 Nsight Compute 等内核级剖析工具，分析占用率与驻留之间的权衡。

算术优化与低精度/混合精度

低精度和稀疏性让你以比特数换取显著的速度和内存收益，且通常对精度影响微乎其微。混合精度、TF32/FP8/INT8 和融合缩放可利用硬件计算路径，提高单位成本吞吐量。

具体而言，使用混合精度（BF16/FP16）和 Tensor Core 可获得大幅收益；采用 TF32 可轻松加速 FP32；在质量允许时评估 FP8/FP4。利用结构化稀疏性、低精度梯度/通信和用于推理的 INT8/INT4 量化，并融合缩放/激活操作以保持精度。以下优化技术适用于提高算术计算性能并利用低精度/混合精度：

使用混合精度训练

训练时利用 FP16 或 BF16 加速数学运算并减少内存使用。现代 GPU 的 Tensor Core 可大幅加速 FP16/BF16 矩阵操作。为保持数值稳定性，应将最终累加、权重副本等关键部分保留为 FP32，而将大部分计算以半精度运行。这通常可带来约 1.5–3.5 倍加速（取决于模型和内核组合，matmul 密集型工作负载收益更大），精度损失很小；如今这已是大多数框架自动混合精度（AMP）的标准做法。

采用梯度累积与激活检查点

使用梯度累积可在不额外增加内存使用的情况下有效扩大批量大小；对于非常深的网络，可考虑激活检查点以减少内存占用。当训练的模型接近或超过 GPU 内存限制时，这些技术至关重要。

在较新硬件上优先选用 BF16 而非 FP16

若可用，应使用 BF16 而不是 FP16，因为它具有更大的指数范围且不需要损失缩放。现代 GPU 对 BF16 Tensor Core 的支持速度与 FP16 相同。BF16 可避免上溢/下溢问题，从而简化训练，同时仍享有半精度的性能优势。

利用 FP8、新型精度和缩放技术

在现代 GPU 上，FP8 Tensor Core 对计算受限内核提供约为 FP16 或 BF16 两倍的计算吞吐量，同时降低激活值和权重带宽。此外，FP4（NVFP4）Tensor Core 的吞吐量又是 FP8 的两倍；它结合微张量缩放（一种保持精度的误差校正技术）用于推理，可提高 token 吞吐量。训练时使用 FP8 与 NVIDIA Transformer Engine，并在需要时保持 FP16 或 FP32 累加器。推理时先评估 FP8，只有在校准显示质量满足任务要求后才采用 NVFP4。训练建议使用混合 FP8：前向激活值/权重使用 E4M3，梯度使用 E5M2；通常使用 256–1024 的延迟缩放窗口也有益。TE 可集成到 PyTorch，并受现代 GPU 硬件支持。应优先采用框架的 TE 内核，而不是临时编写的 FP8 自定义操作。端到端加速取决于内核组合、内存带宽和校准，因此需在你的模型和工作负载上验证精度与性能。

利用 Tensor Core 和 Tensor Memory Accelerator（TMA）

若可能，应确保自定义 CUDA 内核使用 Tensor Core 执行矩阵操作；为简化实现，可使用 CUTLASS 模板。借助 Tensor Core 和 TMA 将张量异步移动至共享内存，可显著加速 GEMM、卷积及其他张量操作，性能常接近 GPU 的峰值 FLOPS。确保数据按需要采用 FP16/BF16/TF32，且对齐到 Tensor Core 分块维度（8 或 16 的倍数）。

使用 TF32 轻松加速

对于 32 位矩阵乘法，可设置 torch.set_float32_matmul_precision("high")，为 PyTorch 中数值安全的操作启用 TF32（快速 FP32）。cuBLAS、cuDNN 等库会在现代 GPU 硬件上自动选择最佳 Tensor Core 代码路径。若以“highest”（而非“high”）强制完整精度 FP32，请务必了解其性能影响。

利用结构化稀疏性

现代 NVIDIA GPU 支持矩阵乘法的 2:4 结构化稀疏性，即按结构化模式将 50% 的权重置零，使硬件吞吐量翻倍。可通过剪枝模型来利用此特性。若能将权重剪枝至符合 2:4 稀疏模式，则这些层的 GEMM 可快约 2 倍。使用 NVIDIA SDK 或库支持应用结构化稀疏性，并确保采用稀疏 Tensor Core 路径。若模型能容忍或能在这种稀疏性下训练，便可获得近乎免费的加速；这通常需要使用稀疏正则化重新训练。

可行时降低梯度和激活值精度

即使保留较高精度的权重，也可考虑将梯度或激活值压缩至较低精度。例如，对梯度使用 FP16/BF16 或 FP8 通信；许多框架支持 FP16 梯度 all-reduce。同样，在激活检查点中以 16 位而非 FP32 存储激活值可节省内存。针对 FP8、FP4 优化器和量化梯度的研究仍在继续。这些方法可在降低内存和带宽成本的同时保持模型质量。在带宽受限环境中，梯度压缩尤具颠覆性。DeepSeek 曾通过压缩梯度在受限 GPU 上训练来展示这一点。

为推理使用定制量化

部署时应尽可能使用 INT8 量化。GPU 上的 INT8 推理极快且内存效率高。使用 NVIDIA TensorRT 或量化工具将模型量化为 INT8 并完成校准。许多神经网络（如 Transformer）可用 INT8 运行，精度下降可忽略不计；相对 FP16 的加速可达 2–4 倍。在最新 GPU 上，还应探索和评估某些模型的 FP8 或 INT4，以进一步提高推理吞吐量。

可行时融合缩放与计算操作

使用低精度时，记得融合操作以保留精度。例如，Blackwell 的 FP4“微缩放”建议为每组数值保留一个缩放因子。应在一次遍历中完成缩放和计算，而不是分多次遍历，以免造成精度损失。现有库已处理许多此类操作，应直接使用它们而不要从头实现。

高级调优策略与算法技巧

算法层面的改变通常能以减少工作量的方式，在投资回报率（ROI）上胜过硬件升级，而非只是更快地执行同样工作。自动调优、FlashAttention、通信/计算重叠和分片可在减少浪费的同时释放扩展能力。

具体而言，自动调优内核与层参数，替换为融合/FlashAttention 内核，并在分布式训练中将通信与计算重叠。使用流水线/张量并行和 ZeRO 分片扩展深度模型，并考虑异步更新或剪枝/稀疏性，以少量精度代价换取显著吞吐量收益。以下是一些高级性能优化和算法技巧：

自动调优内核参数

针对目标 GPU 自动调优自定义 CUDA 内核。正确的块大小、分块大小、展开因子等都会影响性能，且最佳设置常因 GPU 世代而异，如 Ampere、Hopper、Blackwell 及后续架构。使用自动调优脚本或 OpenAI Triton 等框架，甚至在预处理步骤中进行暴力搜索，以找到最佳启动配置。这可轻松带来静态“合理”设置会错失的 20%–30% 提升。在自动调优循环中使用 Triton 功能，例如设置 num_warps 和 num_stages、启用自动 warp 专用化，并测试异步 TMA 布局。共享内存暂存优先使用 tensor map descriptor API。迁移到不同硬件时应重新基准测试分块形状，因为最佳选择会随 GPU 世代变化。

在机器学习工作负载中使用内核融合

利用深度学习库提供的融合内核。例如，启用融合优化器会融合权重更新、动量等逐元素操作；还可使用融合多头注意力实现和融合归一化内核。NVIDIA 库以及 Transformer Engine、FasterTransformer 等开源项目为常见模式提供融合操作，如融合的 LayerNorm + dropout。这些操作可减少启动开销并更高效地使用内存。

使用 FlashAttention 等高内存效率注意力机制

为 Transformer 模型集成 FlashAttention 等高级算法。FlashAttention 采用分块、流式方式计算注意力，避免实体化大型中间矩阵，从而显著减少内存使用并提高速度，尤其适用于长序列。以 FlashAttention 替换标准注意力可同时改善吞吐量和内存占用，使相同硬件能够支持更大的批量或序列长度。

重叠通信与计算

在分布式训练中，应尽可能将网络通信与 GPU 计算重叠。例如，在梯度 all-reduce 中，每层梯度一就绪便异步启动 all-reduce，同时下一层仍在计算反向传播。若实现得当，这种流水线可完全隐藏 all-reduce 延迟。使用异步 NCCL 调用或 PyTorch Distributed Data Parallel（DDP）等原生支持重叠的框架库，确保 GPU 不会闲置等待网络。

为深度模型使用流水线并行

当模型大小迫使你使用张量并行或流水线并行跨 GPU 划分时，可使用足够多的微批次以保持所有流水线阶段忙碌。利用 NVLink/NVSwitch 在阶段间快速传送激活值；通过交错调度重叠并减少流水线气泡。一些框架会自动完成这类调度。NVL72 互连在此尤其有帮助：即使通信密集型流水线阶段也可按数 TB/s 的速度交换数据，最大限度减少流水线停顿。

利用分布式优化器分片

使用 Zero Redundancy Optimizer（ZeRO）等节省内存的优化策略：它将优化器状态、梯度等张量分片到各 GPU，而不是复制到每个 GPU。通过分散内存和通信负载，这种方式可扩展到极大模型。它通过降低每 GPU 内存压力、避免交换到 CPU，并在分块处理时减少通信量来提高吞吐量。DeepSpeed、Megatron-LM 等许多框架提供此类分片。对大模型应加以利用，以在不发生 OOM 或因交换而减速的情况下保持高速度。

可行时异步训练

若适用，可考虑异步更新。例如，可使用陈旧随机梯度下降（SGD），其中工作器并不总是等待彼此共享更新。这种方法可提高吞吐量，但需要仔细调优以免影响收敛。若实现得当，异步训练能带来巨大的性能收益。

引入稀疏性与剪枝

大模型通常存在冗余。训练时使用剪枝技术引入稀疏性，可在推理时利用；若受支持，在训练中也可部分利用。现代 GPU 硬件支持加速的稀疏矩阵乘法（2:4），未来 GPU 很可能会扩展这一能力。即使保持稠密训练、仅为推理剪枝，较小模型也会运行得更快且占用更少内存，从而提高模型部署的成本效益。探索彩票假设、蒸馏或结构化剪枝，在缩减模型大小的同时保持精度。

分布式训练与网络优化

在集群规模下，网络会成为限制因素。若不加处理，网络会破坏线性扩展并推高成本。RDMA/巨型帧、分层集合通信、亲和性和压缩可保护带宽并控制延迟。

可用时使用 RDMA（InfiniBand/RoCE）；若使用以太网，则调优 TCP 缓冲区、启用巨型帧，并选择现代拥塞控制。对齐 NIC/CPU 亲和性，调整 NCCL 线程/缓冲区（以及受支持时的 SHARP/CollNet），压缩或累积梯度，并测试网络以发现丢包或错误配置。请按以下指导优化多 GPU、多节点模型训练等分布式环境的网络：

可用时使用 RDMA 网络

为多节点集群配备 InfiniBand 或 RoCE，以获得低延迟和高吞吐量。确保 NCCL 和 MPI 在训练中使用 RDMA；NCCL 会自动检测 InfiniBand，并在可用时使用 GPUDirect RDMA。RDMA 绕过内核网络栈，相比传统 TCP 可显著降低延迟。若只有以太网，则在支持 RDMA 的 NIC 上启用 RoCE，以获取类似 RDMA 的性能。在 NVLink 域系统（NVL72、GB200/GB300 等）上，可行时让集合通信保持在互连网络内；主机网络留给跨岛链路。使 NCCL 拓扑提示与 NVLink/NVSwitch 域对齐。

使用以太网时调优 TCP/IP 协议栈

对于基于 TCP 的集群，增大网络缓冲区。提高 /proc/sys/net/core/{r,w}mem_max 和自动调优限制（net.ipv4.tcp_{r,w}mem），以允许更大的发送/接收缓冲区。这有助于跑满 10/40/100 GbE 链路。在所有节点和交换机上启用巨型帧（MTU 9000），以降低每包开销、提高吞吐量并减少 CPU 使用率。对广域或拥塞网络，还可考虑 BBR 等现代 TCP 拥塞控制。

为 NIC 分配 CPU 亲和性

将网络中断和线程固定到与 NIC 位于同一 NUMA 节点的 CPU 核心。这可避免网络流量的跨 NUMA 代价，并使网络栈的内存访问保持本地化。检查 /proc/interrupts 并使用 irqaffinity 设置，确保例如 NUMA 节点 0 上的 NIC 由 NUMA 节点 0 的核心处理。这可提高网络性能和一致性，尤其是在高包速率下。

针对环境优化 NCCL 环境变量

针对大型多节点作业试验 NCCL 参数。例如，将每 GPU 的 NCCL CPU 线程数 NCCL_NTHREADS 从默认的 4 提高到 8 或 16，可在增加 CPU 使用的代价下驱动更高带宽。将每 GPU 的缓冲区大小 NCCL_BUFFSIZE 从默认 1 MB 提高到 4 MB 或更多，可改善大消息吞吐量。若集群使用支持 SHARP 的交换机，请安装 NCCL SHARP 插件并设置 NCCL_COLLNET_ENABLE=1 启用 CollNet，然后按文档使用 SHARP_COLL_LOCK_ON_COMM_INIT=1、SHARP_COLL_NUM_COLL_GROUP_RESOURCE_ALLOC_THRESHOLD=0 等 SHARP 插件变量。只有归约足够大且网络支持 SHARP 卸载时，才应期待加速。

为慢速网络使用梯度累积

若由于扩展了过多由中等性能互连连接的节点而使网络成为瓶颈，可使用梯度累积，执行更少但更大的 all-reduce 操作。在同步前跨若干小批次累积梯度，使 N 个批次只通信一次，而非每批次一次。这以少量额外内存和模型精度调优为代价，显著降低网络开销；当增加更多 GPU 因通信成本而产生递减收益时尤其有帮助。

优化 all-reduce 拓扑

确保为集群拓扑使用最佳 all-reduce 算法。NCCL 会自动选择环形或树形算法；但在混合互连上（每节点 GPU 通过 NVLink 连接、节点间通过 InfiniBand 或以太网连接），分层 all-reduce 可能有益。分层 all-reduce 会先在节点内执行，再跨节点执行。大多数框架默认会进行基于 NCCL 的分层聚合，但应通过剖析确认。在传统 MPI 设置中，也可考虑手动执行相同的两级归约：先节点内，再节点间。

避免网络过度订阅

在多 GPU 服务器上，应确保 GPU 的合计流量不会使 NIC 过度订阅。例如，八个 GPU 在 all-reduce 期间很容易产生超过 200 Gbps 的流量，只有一张 100 Gbps NIC 会形成限制。若扩展到每节点许多 GPU，可考虑每节点多张 NIC 和 200/400 Gbps InfiniBand。同样，若 NIC 与 GPU 共享同一 PCIe 根复合体，还需注意 PCIe 带宽限制。

压缩通信

与单节点内存相同，可考虑压缩用于网络传输的数据。技术包括 16 位或 8 位梯度压缩、量化跨节点流水线传输的激活值，甚至 sketching 等更特殊的方法。若网络是最慢的组件，那么为压缩/解压数据而增加少量计算成本是值得的。NVIDIA NCCL 原生不压缩，但可在框架中集成压缩（如 Horovod 的梯度压缩或 PyTorch 的自定义 AllReduce hook）。这也是 DeepSeek 成功的一个关键：压缩梯度以应对受限的节点间带宽。

监测网络健康状况

确保没有隐性问题妨碍分布式训练。检查丢包（会表现为重试或超时：在 InfiniBand 上使用重发计数器，在以太网上检查 TCP 重传）。即使少量丢包，因触发拥塞控制也可能严重降低吞吐量。使用带外网络测试（如 iPerf 或 NCCL 测试）验证是否获得预期带宽和延迟；否则，应调查交换机配置、NIC 固件或 CPU 亲和性。

高效推理与服务

服务是成本与延迟之间的博弈：利用率的提高来自编排和批处理，而不仅是更大的 GPU。专用运行时、KV 缓存策略和预热可在不违反 SLO 的情况下保持高吞吐量。

借助自动扩缩容、微服务和动态/连续批处理按需编排，使 GPU 保持繁忙而不违反延迟 SLO。使用专用运行时（vLLM、SGLang、TensorRT-LLM），利用 NIXL 和 KV 缓存卸载实现解耦式服务，预热模型，并隔离资源以控制尾部延迟。请采用以下技术提高模型推理效率和性能：

高效编排动态资源

集成先进的容器编排平台，例如配合自定义性能指标的 Kubernetes。这可根据实时使用模式和吞吐量目标动态扩缩容并平衡工作负载。

为推理采用无服务器架构

探索用于推理工作负载的无服务器架构和微服务设计：它们可高效处理突发流量，并在需求较低时缩容以减少闲置资源开销。

优化批处理与并发

针对推理工作负载，选择合适的批处理策略。优先采用动态或连续批处理，自动将传入请求组成批次。较大的批量通过保持 GPU 忙碌来提高吞吐量，但过大也会增加延迟。若一个流未占用全部 GPU 资源，还可并行运行多个推理流，例如两个并发推理批次以充分使用 GPU SM 和 Tensor Core。

在分布式推理中利用 NIXL

跨 GPU 或节点服务大模型时，使用 NVIDIA Inference Xfer Library 经由 RDMA 在预填充与解码工作器之间流式传输 KV 缓存。对于 NIXL，基于 Transformer 的大型 KV 缓存会在节点之间传输。NIXL 提供高吞吐、低延迟的 API，可在解耦式 LLM 推理集群中将 KV 缓存从预填充 GPU 流式传输到解码 GPU。它使用 GPUDirect RDMA 和最优路径完成此事，不涉及 CPU，从而降低跨节点解耦预填充/解码服务的尾部延迟。

必要时卸载 KV 缓存

若 LLM 的注意力 KV 缓存增长到超出 GPU 内存，请使用分层卸载。NVIDIA Dynamo 的 Distributed KV Cache Manager 可将访问较少的 KV 页卸载到 CPU 内存、SSD 或网络存储；TensorRT-LLM、vLLM 等推理引擎支持分页和量化 KV 缓存。复用缓存可降低内存压力和首 token 延迟。应验证端到端影响，因为卸载后的缓存未命中会引入额外 I/O 延迟。借助快速 NVMe 和计算—I/O 重叠，此法可在原本会超过 GPU 内存的序列上推理，且性能损失很小。若预期超长提示词或聊天，应确保推理服务器已配置使用此机制。卸载到磁盘总比完全失败更好。

高效服务模型

使用经过优化的模型推理系统（如 vLLM、SGLang、NVIDIA Dynamo 和 NVIDIA TensorRT-LLM）以低延迟、高吞吐量服务大模型。它们应实现量化、低精度格式、融合、高度优化的注意力内核及其他技巧，以最大化推理期间的 GPU 利用率。这些库还应处理张量并行、流水线并行、专家并行、上下文并行、推测解码、分块预填充、解耦预填充/解码、动态请求批处理等众多高性能功能。

监测并调优尾部延迟

在实时服务中，平均延迟和（长）尾部延迟（第 99 百分位）都很重要。剖析推理延迟分布；若尾部很高，找出离群值的原因，如意外的 CPU 介入、垃圾回收（GC）暂停或过多上下文切换。将推理服务器进程绑定到特定核心、与嘈杂邻居隔离，并在必要时使用实时调度，以获得更一致的延迟。

预热以避免冷启动延迟

将模型加载到 GPU 并运行几次虚拟推理，以预热 GPU。这样可避免第一条真实请求进入推理服务器时遭遇一次性的冷启动延迟。

为服务质量（QoS）高效划分资源

若在同一基础设施上运行训练和推理等混合异构工作负载，或运行不同架构的模型，应考虑划分资源，以确保延迟敏感的推理得到优先级。这可能意味着将部分 GPU 完全专用于推理，或在服务不需完整 GPU、但需要可预测延迟时，使用 MIG 为推理服务提供有保障的 GPU 分片。若可能，应将推理与训练部署在不同节点上，因为训练时繁重 I/O 或突发通信可能引入抖动。

利用 Grace CPU 进行推理预处理

在 Grace Blackwell 系统中，服务器级 CPU 可在与 GPU 相同的内存空间内极快地处理分词、批次整理等预处理任务。将此类任务卸载到 CPU，由它在 GPU 可直接使用的共享内存中准备数据。这样可减少缓冲区重复，并利用强大的 CPU 处理推理流水线的一部分，使 GPU 专注于计算更密集的神经网络计算。

为边缘 AI 和延迟关键部署谨慎调优

借助专用边缘加速器，并优化中心服务器与边缘设备之间的数据传输协议，将性能调优延伸至边缘。这有助于为时间敏感型应用实现超低延迟。

多节点推理与服务

将预填充/解码解耦并分片模型，可凭借更高占用率处理更大的上下文和更多用户。连续批处理及分层内存/卸载即使在长提示词和高并发下也能维持流动。

具体而言，在设备间解耦预填充与解码，持续跨请求汇集 token，并通过张量/流水线并行分片超大模型。为超长上下文添加分层内存/卸载，以少量延迟换取大幅更高的容量，从而在不发生 OOM 的情况下服务更多请求。以下性能提示适用于多节点推理与服务：

解耦推理流水线

将推理工作流划分为不同阶段：包括使输入提示词通过全部模型层的“预填充（prefill）”阶段，以及逐 token 生成输出的迭代“解码（decode）”阶段。将这些阶段分配给不同资源，以便独立扩展。这种两阶段方法可避免较快任务受较慢任务瓶颈限制。对大语言模型，一种策略是运行完整模型以编码提示词，然后按阶段处理自回归解码，并可能为每阶段配置专用工作器。通过解耦流水线，可确保 GPU 持续处理它最擅长的任务部分，避免队头阻塞，即一次长生成任务阻塞其后其他任务的情况。

为 LLM 使用连续批处理

超越简单的请求批处理，使用连续批处理策略以最大化高负载下的吞吐量。传统动态批处理将传入请求分组并作为批次处理，以提高 GPU 利用率；连续批处理更进一步，会实时动态合并和拆分跨请求的 token 序列。vLLM 等系统实现 token 池化：任何线程一准备好生成下一个 token，便与其他就绪线程组成新批次。这种方法始终保持 GPU 高占用率，并大幅减少空闲期，尤其在服务许多具有不同序列长度的并发用户时，可获得显著更高的 token 吞吐量和更好延迟一致性。

跨 GPU 和节点高效分片模型

对于大到无法放入单张 GPU 内存的模型，可通过将模型划分到多个 GPU 甚至多台服务器上，采用模型并行推理技术。这可通过张量并行实现：将每层权重和计算划分到各设备；或通过流水线并行实现：将模型层划分为托管在不同 GPU 上的片段，按顺序让数据流经它们。虽然模型分片会因数据在分片间流动而引入通信开销和一些延迟，却可部署原本无法服务的万亿参数模型。确保 GPU 间具有 NVLink、InfiniBand 等高速互连，并尽可能使通信与计算重叠。关键在于平衡负载，使所有设备并行工作，且没有单一阶段成为瓶颈。

为扩展上下文卸载内存

使用分层内存策略，以支持所需内存超过 GPU 可用内存的推理工作负载。服务超大模型或长序列上下文（如很长的多轮对话和大型文档）时，应加入内存卸载。GPU 内存紧张时，可将访问频率较低的数据（如旧的注意力 KV 缓存条目或不常访问的模型权重）移到 CPU RAM 甚至 NVMe 存储。现代推理框架可自动换出这些张量，并在需要时动态换回。虽然缓存未命中会引入额外延迟，但可防止内存不足错误并处理极端情况。合理地卸载和预取数据，是以少量速度换取服务大工作集请求的能力，从而在内存约束下实现更好的整体吞吐量。

功耗与散热管理

每瓦性能是一等指标：热或功耗降频会抹去调优收益并缩短硬件寿命。功率上限、高效装箱和主动冷却可稳定时钟频率，同时降低能源开销。

除速度外，还应跟踪每瓦性能和温度：为内存受限工作负载限制功率或降低时钟，可在吞吐量损失很小的情况下提高效率。主动管理冷却，整合任务以使 GPU 接近满载运行，监测每 GPU 功耗，并在可降低成本时按能源价格/可再生能源安排作业。以下是管理 AI 系统功耗和散热特性的提示：

可行时使用高效且环保的能源

在跟踪性能的同时跟踪并优化能耗。除管理功率和温度限制外，还应监测能源使用指标，并考虑同时改善性能和可持续性的技术。例如，根据可再生能源可用性实施动态功率上限或迁移工作负载，可降低运营成本和碳足迹。这种双重关注可降低运营成本，并支持负责任、环保的 AI 部署。

监测温度与时钟频率

运行期间密切关注 GPU 温度和时钟频率。若 GPU 接近温度限制（某些情况下为 85°C），它们可能开始降低时钟频率，从而降低性能。使用 nvidia-smi dmon 或遥测数据查看时钟是否从最大值下降。若检测到降频，应改善冷却、提高风扇速度、改善气流，或略微降低功率限制以保持稳定的热包络。目标是在不因温度导致波动的情况下实现一致性能。

使用感知能源的动态功耗管理

现代数据中心日益采用感知能源的调度，根据实时能源成本和可再生能源可用性调整工作负载。结合自适应功率上限和动态时钟缩放，可在降低运营成本和碳足迹的同时优化每瓦吞吐量。

针对每瓦性能进行优化

在功率预算受限（或能源成本高）的多 GPU 部署中，应考虑为效率调优。许多工作负载，尤其内存受限的工作负载，可在略微降低 GPU 时钟时运行，性能损失可忽略，功耗却明显降低。例如，若内核受内存限制，将 GPU 锁定在较低时钟可节电而不损害运行时间，从而提高每瓦吞吐量。使用 nvidia-smi -pl 测试若干功率限制，查看每瓦吞吐量是否改善。对某些模型，将功率限制从 100% 降至 80%，可在少用 20% 电力的情况下获得几乎相同的速度。

使用自适应冷却策略

若运行环境的冷却或能源可用性存在变化，应与集群管理集成以调整工作负载。例如，若成本受此影响，可将重型作业安排在一天中较凉爽的时段或可再生能源供应充足时运行。一些场所实施策略，将非紧急作业排队到电价较低的夜间运行。这不会改变单个作业的性能，却能显著降低成本。

整合工作负载

应让 GPU 高利用率运行，而不是让许多 GPU 低利用率运行。就每瓦完成的工作而言，繁忙 GPU 比闲置或轻度使用的 GPU 更节能，因为其基础功耗得到了更好摊销。除非要优化最短墙钟时间，否则让一个 GPU 以 90% 利用率先后运行作业，可能优于两张 GPU 各以 45% 利用率并行运行。应规划调度，在不使用时关闭或闲置整个节点，而非让大量硬件以低利用率运行。

高效配置冷却

对于风冷系统，重负载运行时可考虑将 GPU 风扇设为较高的固定速度，以预先冷却 GPU。一些数据中心始终以最大转速运行风扇以改善一致性。确保数据中心进风温度符合规格；定期检查服务器 GPU 是否有灰尘或阻塞物，堵塞的散热片会大幅降低冷却效率。对于水冷系统，确保流量最优且水温受控。

谨慎监测功耗

使用工具监测每 GPU 功耗。nvidia-smi 会报告瞬时功耗，有助于了解工作负载的功率特征。功耗尖峰可能与特定阶段相关：例如，all-reduce 阶段的计算负载和功耗可能较低，而稠密层会使负载和功耗测量出现尖峰。了解这一点后，可调整作业顺序以平滑功耗。在受限供电线路上运行集群时，这一点很重要。在功率受限场景中，可能需避免在同一节点同时运行多个功耗尖峰型作业，以免触发功率限制。

提高长时间运行作业的韧性

若运行数月之久的训练作业或 7×24 推理作业，应考虑温度对硬件寿命的影响。持续以 100% 功率和温度上限运行，随时间推移可能略微增加故障风险。实际中，数据中心 GPU 就是为此类韧性设计的；但若希望更加稳妥，将功率目标设为 90% 可在减速很小的情况下减少组件压力。这是在更长训练时间与更少硬件磨损之间的权衡，尤其当硬件将长期复用于多个项目时。
